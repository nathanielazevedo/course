The LIMS is where a sample's results are supposed to end up. Getting them there — from the raw output an instrument actually produces to a structured record a person or system can query later — is its own step, and one that's easy to underestimate.

### Raw output is rarely usable as-is

An instrument's native output is built around its own internal format, not the lab's data model: a plate reader might output a grid of raw intensity values labeled only by well position, with no reference to which sample was actually in each well; an imager might produce a folder of image files per plate, with metadata about exposure settings but nothing linking a given image to a sample ID. Before any of this becomes a usable result, it has to be joined against the identity information covered earlier in this chapter — this is where a plate's barcode, scanned and recorded during the run, gets matched up with the well-by-well data an instrument reports at the end of it.

### Parsing: turning a file into structured data

**Parsing** is the process of reading an instrument's raw output format and extracting the specific values that matter — a number from a fixed column position in a text file, a field from a proprietary binary format, a value buried in a vendor-specific XML structure. Every instrument model, and often every software version of the same instrument, can have a subtly different output format, which is why parsing logic is usually instrument-specific and has to be revalidated whenever a vendor updates their software.

### Validation before anything is trusted

Parsed data isn't automatically correct data. A well that failed to read (an instrument error, a bubble in the well) can produce a value that looks numerically plausible but is scientifically meaningless — a **flag** or **error code** the instrument reported alongside the number, easy to discard if the parsing step only looks at the numeric column. Validation checks that values fall within physically sensible ranges, that every expected well actually has a value, and that any instrument-reported error flags are captured and carried forward rather than silently dropped — because a missing or wrong value that goes unflagged looks identical, downstream, to a real result.

### Automated capture versus manual transcription

The whole reason this matters as an automation topic, not just a data-management one, is the alternative: a person manually reading numbers off an instrument's screen and typing them into a spreadsheet. That transcription step is a well-documented source of error — a mistyped digit, a row copied to the wrong sample — that automated capture eliminates entirely, but only if the parsing and identity-matching described here are built correctly. Automating the capture badly (matching the wrong barcode to the wrong plate of data) is arguably worse than a careful manual transcription, because it fails silently and looks exactly as authoritative as a correct automated result.

With results correctly captured and linked to sample identity, the final section of this chapter looks at getting all of these systems — instruments, scheduler, LIMS, ELN — to actually talk to each other as one coherent whole.
