Every system covered in this course so far — instruments, drivers, the scheduler, the LIMS, the ELN — does its own job well in isolation. None of them are useful in isolation, though; the actual value of an automated lab comes from these systems working as one connected whole. This final section is about what makes that connection possible, and what makes it fail.

### The integration problem

**Integration** is the work of getting separate systems, often from different vendors with no shared design, to exchange information correctly. A scheduler needs to tell the LIMS a run has started; the LIMS needs to tell a reader's software which sample identities correspond to which wells; a captured result needs to flow from an instrument's parsing step, covered in the last section, into the LIMS record it belongs to. None of these connections come for free — each is a specific integration that has to be built, tested, and maintained.

### Standards versus custom connections

Some of this connection work is handled by the standardized instrument protocols covered earlier — SiLA 2, OPC-UA — which give a driver a predictable way to expose data to whatever's asking for it. But standards at the instrument-control layer don't automatically solve integration at the data layer: a LIMS and an ELN from two different vendors, or a custom scheduler and a commercial LIMS, often still need a **custom interface** built specifically to translate one system's data model into the other's expectations. Where a standard exists and both sides support it, integration is comparatively cheap; where it doesn't, someone has to build and maintain a bespoke translation layer.

### Why interoperability is the goal, not just integration

**Interoperability** is a step beyond one-off integration: it's the property of systems being able to exchange information *without* a custom-built bridge for every single pairing, because they agree on a shared format or protocol in the first place. An integration connects two specific systems; interoperability means any system that speaks the shared standard can connect to any other one that does, without bespoke work for each new pair. This is exactly why standards matter as much as they do throughout this course — every custom integration is a one-time cost paid again for every new system added, while a shared standard pays that cost once.

### What breaks when integration is done poorly

A poorly integrated system doesn't usually fail obviously — it fails the way capturing instrument data poorly does: silently. A scheduler that doesn't correctly notify the LIMS when a run starts leaves that run's results with no home to land in. A translation layer that maps one system's field slightly wrong produces data that looks complete and correct but is quietly attached to the wrong sample. Because these failures are invisible at the moment they happen, they're usually only discovered much later — during an audit, a re-analysis, or when someone notices a result that doesn't make sense — by which point the actual cause can be difficult to reconstruct.

This closes the chapter on data, samples, and LIMS — identity, chain of custody, LIMS and ELN, capturing instrument data, and the integration work that ties every system in this course together.
