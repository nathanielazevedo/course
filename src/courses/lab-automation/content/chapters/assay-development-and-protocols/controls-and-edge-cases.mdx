An optimized, decomposed, automated method still needs one more thing before it can be trusted: proof that it's actually working correctly on any given run, and a plan for what happens when something about that run isn't quite normal. That's the job of controls and edge cases.

### Controls, revisited for automation

Positive and negative controls were introduced back in the laboratory-fundamentals chapter as a way to confirm an experiment worked. In an automated method, controls take on an extra role: they're the mechanism that catches a *systemic* problem — a bad reagent lot, a miscalibrated instrument, a scheduling error that silently corrupted timing — before it invalidates real sample data. A method that runs perfectly on its intended steps but produces a failing negative control has still failed, and a well-built automated method checks its own controls automatically rather than relying on someone to notice after the fact.

### What an edge case actually is

An **edge case** is any input or condition a protocol's main path wasn't designed around: an empty well where a sample should have been, a sample so viscous the standard liquid class mishandles it, a plate barcode that doesn't match any record the LIMS expects. A protocol validated only against typical, well-behaved samples looks robust right up until it meets the first sample that isn't typical — and in a large enough run, an atypical sample is not a remote possibility, it's a near-certainty somewhere in the plate.

### Designing for edge cases instead of hoping they don't happen

The reliable approach isn't trying to imagine every possible edge case in advance — that's impossible — it's building a method that fails *safely and visibly* when it meets one it wasn't specifically designed for, rather than either crashing unpredictably or silently producing a plausible-looking wrong result. This connects directly back to error recovery from the scheduling chapter: an edge case detected early (a missing sample flagged before it's processed as if it were present) can be isolated and handled, while one that goes undetected propagates through every downstream step as if it were normal data.

### Anticipating the most common edge cases by category

Certain categories of edge case recur across almost every assay: missing or insufficient sample volume, a sample outside the expected concentration range, a reagent or plate that fails an identity check, and an instrument reporting an error mid-step. Building explicit handling for these recurring categories — rather than treating each new run's surprises as one-off problems — is what separates a method that degrades gracefully from one that requires a person on standby for every single execution.

Controls and edge-case handling establish that a method behaves correctly on any *given* run. The final section of this chapter asks the broader question: does it behave correctly the *same way*, every time, reliably enough to trust across the life of the assay?
