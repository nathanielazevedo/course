A method that ran correctly once, on one plate, on one day, hasn't actually proven much. Validation and reproducibility are about establishing — with evidence, not assumption — that a method produces trustworthy results consistently, across the conditions it will actually be used under.

### Validation: proving the method measures what it claims to

**Validation** is the deliberate process of testing a method against known answers to confirm it produces correct results, not just plausible-looking ones. This typically means running the method against samples with a known, independently established outcome — a reference standard, a previously characterized sample — and confirming the automated method's result matches what's already known to be true. A method that has never been checked against a known answer hasn't been validated; it's only been observed to run without crashing, which is a much weaker claim.

### Reproducibility: getting the same answer every time

**Reproducibility** is a related but distinct property: does the method give the same result when run again, on a different day, by a different instrument of the same model, or by a different operator setting it up? A method can be accurate on one particular run and still be poorly reproducible if small, uncontrolled variations between runs produce meaningfully different results — which defeats much of the point of automating in the first place, since consistency was one of the core motivations back in the automated-laboratory chapter.

### Where reproducibility actually breaks

Reproducibility failures rarely trace back to the automated steps executing incorrectly — they usually trace back to something the method assumed was constant but wasn't: a reagent lot that behaves slightly differently from the one used during development, an instrument of the same model with a subtly different calibration, an environmental condition (ambient humidity, room temperature) the original validation never accounted for varying. Identifying these hidden dependencies is often the hardest part of establishing reproducibility, because the method's own logic can be entirely correct while still producing inconsistent results due to an external factor no one thought to control.

### Validation is not a one-time event

A method validated once, at its original volume and reagent lot, doesn't stay validated forever without further checking. Every change covered earlier in this chapter — miniaturizing a volume, optimizing a wash count, swapping a reagent supplier — potentially invalidates the original validation, because each change is a claim that the method still measures the same thing, and that claim needs its own evidence. This is why validation and change control are treated as an ongoing discipline in regulated environments rather than a box checked once during initial development — a theme the later chapter on quality and compliance returns to directly.

This closes the chapter on assay development and protocols — translating manual protocols, decomposing them into steps, optimizing and miniaturizing them, planning for controls and edge cases, and validating that the whole result holds up reliably.
