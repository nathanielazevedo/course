Once a driver has a transport to talk over, it needs an agreement on *what the bytes mean*. That agreement is the **protocol**: how a command is packaged, how the device replies, and how both sides know a message started and ended. Almost every instrument protocol is a variation on one pattern — send a command, wait for a response.

### The request–response loop

The fundamental exchange is simple: the computer sends a **command**, the instrument sends back a **response**. Nothing else happens until that response arrives. A session is just this loop repeated.

### Framing: where does a message begin and end?

Bytes arrive as a stream, so both sides need a rule for chopping that stream into messages — this is **framing**. The common schemes:

- **Delimiter** — a special character marks the end. The classic is a carriage return `\r` or newline `\n` (`ABS 450\r`). Read until you see it; that's one message.
- **Length prefix** — the message starts with a number saying how many bytes follow. Read that many; that's the message. Common in binary protocols.
- **Fixed length** — every message is exactly N bytes.

Without framing, the receiver can't tell where one reply stops and the next begins — a frequent source of "it works until it doesn't" bugs.

### Text vs. binary

Protocols come in two flavors. **ASCII (text)** protocols send human-readable strings like `ABS 450\r` — easy to read, easy to debug with a terminal, and forgiving. **Binary** protocols pack values into raw bytes — compact and fast, but unreadable without the spec and easy to get wrong. Older and simpler instruments lean text; high-throughput or data-heavy ones lean binary.

### Status, errors, and checksums

A response is more than data. It usually carries **status**: a short **ACK** (acknowledged) or **NAK** (not acknowledged), or a numeric **error code** when something went wrong (`ERR 12` — lid open). A driver must check status on *every* command, not assume success — silently ignoring an error is how a run drifts into nonsense.

Where transmission can be corrupted (long serial cables, noisy environments), messages include a **checksum** — a small value computed from the message contents. The receiver recomputes it and rejects the message if they disagree, catching garbled bytes before they're acted on.

### The hard part: waiting for completion

A read is quick, but a centrifuge spin or an incubation takes minutes. The command returns long before the *action* finishes. Two patterns handle this:

- **Polling** — the driver repeatedly asks "are you done?" (`STATUS?` → `BUSY` … `BUSY` … `DONE`) until the device reports completion. Simple, and works on the dumbest devices.
- **Events / unsolicited messages** — the device sends a message *on its own* when it finishes, so the driver doesn't have to keep asking. More efficient, but only if the device and transport support it.

Most real drivers send a command, confirm the ACK, then poll status until the operation completes — turning a slow physical action into a clean "done" the scheduler can wait on. Hiding exactly this messiness is why the standardized protocols in the next sections exist.
