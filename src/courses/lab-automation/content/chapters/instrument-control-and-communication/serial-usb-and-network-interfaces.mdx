A driver speaks a device's command language, but those commands have to travel over a physical wire. That wire — the **interface** — determines how fast data moves, how far it can travel, how many devices can share it, and how the computer even finds the instrument. Three families dominate the lab: serial, USB, and network.

### Serial (RS-232 and RS-485)

**Serial** is the oldest and, even now, the most common instrument interface. Data goes out one bit at a time over a few wires. The classic form is **RS-232**: a point-to-point link between one computer and one device, showing up on the PC as a **COM port** (`COM3`, `/dev/ttyUSB0`).

Serial is simple and extremely reliable, which is why decades-old instruments still use it. Its defining setting is the **baud rate** — the bit speed, e.g. 9600 or 115200 — which *both ends must agree on* along with a few framing parameters (data bits, parity, stop bits). Get those wrong and you get garbage.

Plain RS-232 connects exactly one device. Its industrial sibling **RS-485** allows **multidrop**: many devices share one bus, each with an address — useful for chaining simple peripherals.

### USB

**USB** is the modern desktop connector: much faster than serial, hot-pluggable, and able to power small devices. Instruments connect to USB in two common ways:

- As a **virtual COM port** (USB-CDC): the device looks *exactly* like a serial port to software, so the same serial driver code works. This is extremely common — many "USB" instruments are really serial devices wearing a USB plug.
- Through a **vendor driver**: the manufacturer ships a Windows driver and an SDK (often a DLL) you call functions in, rather than sending raw bytes.

USB is convenient but distance-limited (a few meters) and PC-centric — it assumes a host computer sitting close by.

### Network (Ethernet / TCP-IP)

A **network** interface gives the instrument its own **IP address** on the lab's Ethernet. Software opens a connection to that address and a **port** number and exchanges messages — typically over **TCP**, which guarantees ordered, reliable delivery.

Networking unlocks things the others can't:

- **Distance** — the instrument can be in another room or another building.
- **Multiple clients** — more than one computer can reach it (with care about who's in control).
- **Higher-level protocols** — the modern standards later in this chapter (SiLA 2, OPC-UA) all run over the network.

The cost is more setup: IP addresses, firewalls, and ports to manage.

A useful realization: the **transport** is mostly separable from the **commands**. The same command set (`ABS 450\r`) might be sent over a serial cable on an old unit and over a TCP socket on a newer one. A well-built driver isolates the transport so that swapping serial for network doesn't change how the commands are formed — which is exactly the subject of the next section.
