A scheduler decides that a plate should now be read for absorbance. But it has no idea how to actually make a particular plate reader do that — and it shouldn't have to. Every instrument speaks its own private language, and the job of this layer is to hide those differences so the rest of the system can issue one clean command and trust it will happen.

### The problem: every device is different

Buy two plate readers from two vendors and they will not accept the same commands. One wants the text `ABS 450\r` over a serial port; the other wants a JSON message over the network; a third wants you to call functions in a Windows DLL the vendor ships. They do the same *job* but expose completely different *controls*.

If the orchestration layer talked to each device directly, every method would be welded to specific hardware. Swap a reader for a newer model and you'd rewrite the protocol. That's the coupling a driver exists to break.

### A driver translates

A **driver** is software that turns a generic, high-level command into the exact bytes or function calls one specific device understands — and translates the device's replies back into generic results.

> *read plate at 450 nm* → driver → `ABS 450\r` on COM3 → reader runs → `0.382,0.401,...` → driver → a tidy array of well values

The driver is the only piece of software that knows the device's dialect. Everything above it speaks in intentions; the driver speaks in the device's native commands.

### Device abstraction is the shared contract

A driver solves *one* device. **Device abstraction** solves a whole *class* of devices. It defines a common interface — a contract — that every device of a given type promises to fulfill, regardless of vendor.

A plate-reader interface might promise three operations: `open()`, `read(wavelength)`, `close()`. Each vendor's driver implements that same interface in its own way. The scheduler calls `read(450)` and does not know or care whether a Tecan, a BioTek, or a Molecular Devices reader is behind it.

### Why this layering pays off

- **Interchangeability** — swap one reader for another by changing which driver is loaded, not by rewriting the assay method.
- **Reuse** — a method written against the interface runs on every device that implements it.
- **Isolation** — when a vendor changes its firmware commands, only that one driver changes. Nothing above it notices.
- **Testing** — you can supply a fake "simulator" driver that implements the interface but talks to no hardware, and test a whole method on a laptop.

This is the same idea operating systems use for printers and disks: a stable interface on top, swappable drivers underneath. The rest of this chapter works *down* from here — the physical interfaces a driver talks over (Section 02), the command-and-response patterns it speaks (Section 03), and the standards that aim to make the driver itself unnecessary (Sections 04–05).
