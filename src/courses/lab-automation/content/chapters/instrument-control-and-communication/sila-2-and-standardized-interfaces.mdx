Everything so far has a hidden cost: every instrument has its own commands, its own framing, its own quirks, so every instrument needs its own hand-written driver. Integrate a lab of thirty devices and you've written or bought thirty drivers, each a small maintenance burden. **SiLA 2** is the lab-automation industry's answer — a standard that lets one generic client talk to any compliant device.

### What SiLA is

**SiLA** stands for *Standardization in Lab Automation*. SiLA 2 is an open standard that defines not just a wire format but a whole model for how lab instruments describe and expose their capabilities. If a device is "SiLA-compliant," a SiLA client can connect and use it **without a custom driver** — the device tells the client what it can do.

It's built on mainstream, modern technology rather than bespoke serial commands:

- Communication runs over the **network** using **gRPC** (an efficient RPC framework over HTTP/2).
- Messages are encoded with **Protocol Buffers**, a compact, well-specified binary format.
- Connections are secured with **TLS** encryption by default.
- Devices announce themselves on the network through **zero-config discovery** (mDNS/DNS-SD), so a client can *find* available instruments automatically.

### Servers, clients, and Features

SiLA inverts the usual relationship. The **instrument is the server**; the orchestration software is the **client**. The client connects to the server and asks what it offers.

What it offers is organized into **Features** — self-contained descriptions of a capability, written in a formal **Feature Definition Language (FDL)**, an XML document. A Feature bundles three things:

- **Commands** — actions the device can perform (e.g. `MeasureAbsorbance`).
- **Properties** — values you can read (e.g. `CurrentTemperature`), some of which update live.
- **Defined errors** — the specific failures a command can raise, named and documented.

### Observable commands solve the "is it done?" problem

Recall the awkwardness of polling a slow operation from the previous section. SiLA builds the answer into the standard with **observable commands**: a long-running command (`MeasureAbsorbance`, a long spin) can stream **progress updates** and an **estimated time remaining** back to the client while it runs, then deliver the final result. The client subscribes instead of polling. Short actions use plain **unobservable commands** that just return a result.

### Why it matters

- **No bespoke drivers** — a SiLA client can operate any SiLA server because the device is self-describing. This is the central win.
- **Vendor independence** — swap a compliant device for another and the client adapts to the new Feature set rather than needing new integration code.
- **Modern and secure by default** — network transport, encryption, and discovery are part of the standard, not bolted on.

SiLA 2 is a clean redesign of the earlier **SiLA 1** (which was SOAP/XML-based); the move to gRPC and a formal Feature model is what makes 2 practical. SiLA targets the **device-control** layer specifically. The next section looks at OPC-UA, which comes from the industrial world and addresses the *larger* picture of tying a whole facility together.
