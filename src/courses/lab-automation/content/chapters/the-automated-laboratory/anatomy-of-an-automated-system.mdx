An automated system is not one machine — it's several kinds of parts working together, each with a different job. Recognizing which part you're looking at is the first step to understanding how any automated lab is put together.

### The parts and what each one owns

- **Instruments** — the devices that do the actual lab work: liquid handlers, plate readers, thermal cyclers, centrifuges, washers, sealers. Each one performs a narrow, specific action on labware placed in front of it.
- **Labware** — the plates, tubes, tip boxes, and reservoirs that move between instruments carrying samples and reagents. Labware is the thing being acted on; it has no logic of its own.
- **Transport** — the means by which labware physically moves from one instrument to the next: a robotic arm, a conveyor, or a human moving plates by hand in a semi-automated setup.
- **Drivers** — the software that speaks each instrument's native language, turning a request like "read absorbance at 450 nm" into the exact bytes that instrument expects.
- **The scheduler** — the software that decides what happens when: which instrument runs next, which plate goes where, and how to keep everything from colliding in time or space.
- **Data and LIMS** — the layer that records what happened: which sample went where, what the instruments measured, and whether the run succeeded.

### Why the split matters

Each part can change without breaking the others, as long as the interfaces between them stay stable. Swap a plate reader for a newer model, and only its driver needs to change — the scheduler still just asks for "read absorbance," unaware of what's underneath. Add a new instrument to the deck, and the scheduler only needs to know its capabilities and timing, not its internals.

This separation is what makes a system *maintainable*. A lab that instead wires every instrument's quirks directly into one big control script ends up with a system where changing any one thing risks breaking everything else. The anatomy described here — instruments, labware, transport, drivers, scheduler, data — is the same shape almost every automated lab takes, whatever specific hardware fills each role.

### A minimal system still has every part

Even a single liquid handler running one script by itself has all six parts — they're just small or combined. The liquid handler is the instrument; its deck positions are the labware locations; its built-in arm is the transport; its onboard software is the driver; a simple sequential script is the scheduler; a log file is the data layer. Scaling up doesn't add new *kinds* of parts, it grows each one: more instruments, a real robotic arm instead of a built-in one, a scheduler that juggles conflicts, a LIMS instead of a log file.

Seeing the anatomy this way sets up the next section's question directly: given that any of these parts can be simple or elaborate, when is building — or buying — the elaborate version actually worth it?
