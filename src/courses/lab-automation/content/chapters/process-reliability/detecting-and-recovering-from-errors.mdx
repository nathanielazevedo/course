Knowing the categories of failure, from the previous section, is only useful if the system can actually notice one happening and respond to it. This section is about the mechanics of that detection and response — one level broader than the scheduler-level recovery covered earlier in this course, since not every failure happens neatly inside a single running method.

### Detection has to be built in, not assumed

An automated system does not automatically know when something has gone wrong — it only knows what it was explicitly told to check. A pipette that fails to aspirate any liquid doesn't announce that fact unless something (a pressure sensor, a weight check, a downstream read confirming a signal) is specifically watching for it. This is the same principle from the very first chapter of this course, restated at the level of an entire running process: automation handles exactly the conditions it was built to detect, and nothing else.

### Layers of detection

Detection happens at several levels, from the most immediate to the most delayed:

- **Instrument-level sensing** — a device's own sensors report a problem directly (a pressure sensor detecting a clog, a limit switch detecting an arm didn't reach its target position). Fastest, but limited to whatever the instrument itself can sense.
- **Driver-level checks** — the driver verifies a command's acknowledgment and status code, catching failures the instrument reported but that would otherwise be ignored (the same status-checking discipline from the command-and-response section).
- **Method-level verification** — a control well, a barcode re-scan, or an expected value range check built into the protocol itself catches problems the instrument's own sensors have no way to know about, like a chemically failed reaction.
- **Post-run review** — a person or an automated analysis examines completed results afterward and flags anomalies no earlier layer caught, the last line of defense before bad data reaches a real conclusion.

### Recovery strategies, generalized

The retry, skip, and escalate responses covered in the scheduling chapter apply here too, but process reliability adds a broader consideration: a **graceful degradation** strategy, where a system continues operating at reduced capacity rather than stopping entirely — finishing a run using a backup reagent lot, or continuing without one non-critical sensor that failed, rather than halting a whole overnight run over a problem that doesn't actually threaten the result. Deciding what qualifies as safe to degrade around, versus what genuinely requires a full stop, is a judgment call made in advance, during method design, rather than improvised in the moment.

### Why detection speed and recovery cost trade off

Faster detection layers are cheaper to build and react to a problem almost instantly, but catch a narrower slice of what can actually go wrong; slower layers catch far more but let a problem run longer before anyone notices, sometimes across an entire overnight batch. A well-designed system uses several layers together specifically because no single layer is both fast and comprehensive — the fastest layers catch the cheapest-to-fix problems immediately, while slower layers serve as a backstop for whatever slips through.

Detection and recovery keep a single failure from becoming a disaster. The next section zooms out further, to what it actually takes to keep a system running unattended for the long walk-away stretches introduced back in the automated-laboratory chapter.
