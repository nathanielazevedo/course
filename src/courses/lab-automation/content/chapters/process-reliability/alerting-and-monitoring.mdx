A system running unattended still needs a way to reach a person when something exceeds what it can handle on its own. Alerting and monitoring are the two halves of that connection — one watching continuously, the other speaking up only when it matters.

### Monitoring: watching continuously, saying nothing most of the time

**Monitoring** is the ongoing collection of a system's state — instrument status, consumable levels, timing versus plan, error counts — whether or not anything is currently wrong. Most of what monitoring collects is never looked at directly; its real value is as a **historical record**, useful after the fact for diagnosing a failure (was this instrument already drifting for days before it finally errored?) and for spotting slow trends before they become a real problem, connecting directly to the gradual mechanical drift covered earlier in this chapter.

### Alerting: speaking up only when it matters

**Alerting** is the deliberate act of interrupting a person — a notification, a page, an alarm — specifically because something needs their attention now rather than being reviewable later. The entire value of an alert depends on it being rare enough to trust: a system that alerts on every minor fluctuation trains the person receiving those alerts to ignore them, which defeats the purpose the very first time an alert actually matters.

### Setting the threshold correctly is the whole problem

The hard part of alerting isn't the notification mechanism — it's deciding exactly where the line sits between "worth interrupting someone for" and "worth logging quietly." Too sensitive, and alert fatigue sets in, the same trust-eroding problem described above. Too lax, and a real problem sits unaddressed for hours because nothing ever crossed the threshold that would have flagged it. Getting this right usually means tuning thresholds against real historical data from monitoring — the same data collected passively during normal operation becomes the evidence used to calibrate what "abnormal" actually looks like for that specific system.

### Escalation: not every alert deserves the same response

Beyond a single yes/no threshold, mature alerting systems distinguish **severity** — a reagent running low soon is worth a routine notification a person can act on during business hours; an arm that's stopped mid-motion with a gripped plate needs someone paged immediately, day or night. Routing every alert through the same channel, at the same urgency, either buries the truly urgent ones in routine noise or turns every minor notice into a middle-of-the-night page nobody wants to receive.

### Why alerting connects directly to walk-away time

An alert that fires but reaches no one accomplishes nothing — the previous section's honest accounting of walk-away time only holds if a genuinely urgent alert reliably reaches an actual person during that unattended stretch. This is why alerting infrastructure (redundant notification channels, confirmed delivery, an on-call schedule) is treated as seriously as the detection logic that triggers it — a perfect detection system with a broken notification path fails exactly as badly as no detection at all.

Alerting and monitoring keep a person informed without needing to watch constantly. The final section of this chapter turns to the ongoing, scheduled work that keeps the system itself from needing those alerts in the first place: maintenance.
