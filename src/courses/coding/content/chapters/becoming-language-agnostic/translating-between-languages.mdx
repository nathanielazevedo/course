Once you're comfortable in more than one language, a natural next situation arises constantly: porting an idea, an algorithm, or an entire small program from one language to another. Done carelessly, this produces exactly the kind of code this section is about avoiding — technically working, but wrong in a way that's hard to name precisely.

### Translating intent rather than syntax

The instinct when porting code is to translate line by line, construct by construct — this loop becomes that loop, this class becomes that class. This works, in the narrow sense that the resulting code often runs correctly, but it consistently produces code that reads as obviously foreign in its new language, because it's translating the previous language's *specific syntax* rather than the *intent* that syntax was expressing. The better approach, built directly on everything Chapter 1 established about recognizing concepts beneath syntax: understand what the original code is actually trying to accomplish — its intent — and then ask how *this* language, using its own idioms, would naturally express that same intent.

### Idiomatic code

**Idiomatic code** is code that reads the way an experienced user of a specific language would naturally write it — using that language's particular strengths and conventions, rather than forcing patterns borrowed wholesale from a different language's habits. A `for` loop manually building up a list by appending to it one element at a time is a direct, line-by-line translation from a language without strong list-comprehension support; the idiomatic Python equivalent is a comprehension (`[transform(x) for x in items if condition(x)]`, directly connecting back to Chapter 4's higher-order functions), because that's how Python itself expresses "transform and filter a collection," not because the loop version is wrong — it's just foreign to how Python code is actually written and read by people fluent in it.

### Why direct translations often produce bad code

A direct translation frequently ports over not just the *logic* but also the specific *idioms* and workarounds of the source language — including ones that exist purely to compensate for that language's own particular limitations, limitations the target language may not even share. Manually managing an index variable to loop through a collection (a genuine necessity in older C-style code, or in a language without iterators, Chapter 3) translated directly into Python or JavaScript carries over ceremony neither language actually needs, because both provide clean iteration (`for item in items`, `for (const item of items)`) as a first-class, idiomatic feature specifically so you don't have to manage an index by hand — the workaround the original code needed simply doesn't apply anymore, but a line-by-line translation faithfully reproduces it anyway.

### A concrete example

Porting a Java-style "getter and setter for every field" class directly into Python produces exactly this kind of foreign-feeling code — `get_name()` and `set_name()` methods wrapping a private field, faithfully reproducing Java's encapsulation convention (Chapter 6) even though Python's `@property` decorator (Chapter 6's coverage of properties) achieves the identical actual goal — controlled, potentially validated access to a field — while looking and reading like ordinary attribute access (`user.name`, not `user.get_name()`) everywhere it's used, which is how experienced Python developers actually expect a class's interface to read.

### The real skill

Translating well between languages is really the same fundamental skill Chapter 1 introduced at the very start of this course, applied in reverse: instead of recognizing which concept unfamiliar syntax represents, it's recognizing which concept your existing code represents, and then finding *that same concept's* most natural, idiomatic expression in the new target language — not the most literal, mechanical one. This is, in a real sense, the entire course's central claim distilled into a single practical skill: languages differ enormously in surface form, but the concepts underneath transfer completely, and genuinely fluent translation always happens at the level of those concepts, never at the level of literal syntax.
