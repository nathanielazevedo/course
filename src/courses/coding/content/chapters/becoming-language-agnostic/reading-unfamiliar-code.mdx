Learning a new language's concepts and syntax (the previous two sections) is one skill; actually reading a real, unfamiliar codebase written by someone else, in a language you may or may not know well, is a related but distinct one. This section is about the second skill specifically — a practical approach for making sense of code you didn't write, quickly.

### Finding entry points

Every program has an **entry point** — the actual place execution begins: a `main` function, an HTTP route handler that fires when a request arrives, a UI component's render method, an event listener (Chapter 7's event-driven programming) waiting on a specific trigger. Before trying to understand a codebase broadly, find where execution actually *starts* for the specific behavior you're trying to understand — reading files in alphabetical or directory order, with no sense of where execution genuinely begins, is one of the least effective ways to build a mental model of an unfamiliar system.

### Following data flow

Once you've found a relevant entry point, the most productive next step is usually **following data flow** rather than reading every line in order: pick one specific piece of data (a user ID from an incoming request, a value from a form) and trace where it actually goes — which function receives it, what that function does with it, where it gets passed next, what eventually happens to it. This works because it mirrors how this entire course has approached nearly every topic: values (Chapter 2) moving through functions (Chapter 4), transformed at each step, is the fundamental shape of computation this course has returned to again and again, and it remains the most reliable lens for understanding code you didn't write, regardless of which language it happens to be in.

### Understanding dependencies

Before diving into a specific file's logic, it's worth quickly answering a broader structural question first: what does this code actually depend on (Chapter 9's imports and modules), and what depends on it? A function buried deep in a dependency chain used by dozens of other places in the codebase demands more caution when changing than an isolated one used nowhere else — understanding this dependency structure up front, even briefly, tells you how much blast radius a given piece of code actually has before you've read a single line of its internal logic.

### Recognizing patterns

Everything covered throughout this course — the paradigms from Chapter 7, the error-handling styles from Chapter 8, the architectural patterns from Chapter 14 — exists precisely so you can recognize a **pattern** in unfamiliar code rather than puzzling out its intent line by line from scratch. A function riddled with `if err != nil` checks is unmistakably following Go's errors-as-values convention (Chapter 8), even in a codebase you've never seen before; a class hierarchy with an abstract base and several overriding subclasses is unmistakably polymorphism at work (Chapter 6); a chain of `.filter().map().reduce()` is unmistakably functional-style data processing (Chapter 4, Chapter 7). Recognizing "oh, this is *that* pattern" instantly transfers everything you already know about that pattern's behavior and tradeoffs onto this specific, unfamiliar piece of code — which is precisely the payoff of having spent fourteen chapters building a vocabulary of named, recognizable patterns in the first place, rather than encountering every new codebase as a completely blank slate with nothing to draw on.

### Bringing it together

Reading unfamiliar code well isn't really a separate skill from everything else this course has covered — it's the direct, practical application of it: find where execution starts, follow a specific piece of data through the functions it passes through, understand roughly how central or peripheral this code is to the rest of the system, and actively look for the named patterns this entire course has spent so much effort making recognizable. Approached this way, "unfamiliar language" stops being nearly as intimidating a phrase as it initially sounds — because most of what actually makes code readable was never really about the specific language at all.
