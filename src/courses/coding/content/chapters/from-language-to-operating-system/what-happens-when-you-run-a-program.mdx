This course has spent twelve chapters mostly inside the language — values, control flow, functions, memory, objects, paradigms. This chapter steps outside it, to the moment code stops being purely a language exercise and starts asking the operating system for something real: a running process, a file, a network connection. It starts with the most basic question of all — what actually happens when you type a command and hit enter?

### Executables

An **executable** is a file the operating system knows how to load and run — for a compiled language (Chapter 10), this is the direct output of compilation and linking: machine code in a format the OS recognizes (an `.exe` on Windows, an ELF binary on Linux), along with metadata describing what the program needs to run (which shared libraries to dynamically link, where its entry point is). For an interpreted language, "running the program" more precisely means launching the interpreter as the actual executable, with your source file passed to it as an argument — `python app.py` is really "run the `python` executable, and have it interpret `app.py`," not "run `app.py` directly" the way `./my_compiled_program` genuinely is.

### Processes, revisited

When you run an executable, the operating system creates a new **process** (Chapter 11) to run it in — allocating a private memory space, setting up an initial stack, and, for a dynamically linked binary (Chapter 10), loading whatever shared libraries it depends on before your code's first instruction ever executes.

### Memory allocation

Before your code's first instruction runs, the operating system has already reserved memory regions for the stack and set up the initial layout the process's heap allocator will use to satisfy future dynamic allocations (Chapter 5) — none of this is something your code explicitly requests; it's part of what "creating a process" means at the OS level, done automatically as a precondition for the program to run at all.

### Program startup

Between "the OS created the process" and "your `main` function starts running," most languages run their own startup sequence: a runtime environment (Chapter 1) initializes itself — setting up a garbage collector for managed languages, initializing the standard library's internal state, and, for languages with module-level top-level code (Chapter 9), actually running that code as each module is first imported. This is exactly why a Python script can appear to "do something" before its own explicit logic starts — a module-level `print()` statement anywhere it imports runs during this startup sequence, as a direct consequence of Chapter 9's point that importing a module executes its top-level code.

### Why this matters

Understanding this sequence demystifies a lot of otherwise-confusing behavior: why a missing shared library causes a failure before your program's own code ever runs (dynamic linking, Chapter 10, happens during process creation, before `main`); why "the process take a moment to start" is a real, measurable cost distinct from anything your own code does (memory allocation, runtime initialization, dynamic linking all happen first); and why the next section — system calls — is the mechanism your running process actually uses from this point forward, every single time it needs anything from the operating system that created it.
