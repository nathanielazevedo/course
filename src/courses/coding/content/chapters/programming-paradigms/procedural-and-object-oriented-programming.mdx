Every language nudges you toward organizing programs in a particular way — a **paradigm**, a general strategy for structuring code and thinking about computation. This chapter surveys the major ones, starting with the two most historically dominant: procedural and object-oriented programming, both of which most of this course's earlier chapters have already been implicitly building toward.

### Procedural programming

**Procedural programming** structures a program as a sequence of operations — steps executed in order, organized into procedures (functions) that can be called from other procedures, operating on data that's usually passed around explicitly rather than bundled with behavior. It's the most direct mapping from "how a CPU actually executes instructions" to source code, which is exactly why it was the dominant paradigm in early, performance-critical software.

```c
struct Account { double balance; };

void deposit(struct Account *acc, double amount) {
    acc->balance += amount;
}

void withdraw(struct Account *acc, double amount) {
    if (amount > acc->balance) { /* handle error */ return; }
    acc->balance -= amount;
}
```

Notice `Account` here is pure data (a struct, Chapter 6's final section) and `deposit`/`withdraw` are separate functions that happen to operate on it — data and behavior are deliberately kept apart, the opposite of what object-oriented programming does next.

### C as a classic example

C is the clearest example of procedural programming taken seriously as a whole-language design: no classes, no inheritance, no methods — just structs for data and functions that operate on them, called explicitly, in a straightforward top-to-bottom sequence (with the control-flow tools from Chapter 3 to branch and loop through that sequence). Its continued dominance in operating systems, embedded systems, and performance-critical libraries is a testament to how far this comparatively simple model actually goes.

### Object-oriented programming

**Object-oriented programming (OOP)** — the entire subject of Chapter 6 — takes the opposite stance: bundle data and the behavior that operates on it together, into objects, and structure a program as those objects collaborating by calling each other's methods. Where the procedural example above has `deposit` reaching into an `Account` from the outside, an object-oriented version has `Account` own `deposit` as its own method, responsible for its own state.

```java
class Account {
    private double balance;

    void deposit(double amount) { balance += amount; }
    void withdraw(double amount) {
        if (amount > balance) throw new IllegalArgumentException();
        balance -= amount;
    }
}
```

### Java and C# as classic examples

Java and C# are the clearest examples of object-oriented programming taken as a whole-language design philosophy — in Java specifically, *everything* is technically a method on some class, even a program's `main` entry point, because the language doesn't allow free-floating functions outside a class at all. This is a deliberate design stance, not an accident: it reflects a belief that structuring almost everything around objects, encapsulation, and message-passing between them produces more maintainable large systems, particularly for the kind of large, long-lived enterprise software Java was built for.

### Neither is "correct"

Both paradigms are still in wide, serious use today, and neither has definitively "won" — procedural code remains the right choice where directness and minimal overhead matter most (systems programming, performance-critical code), and object-oriented structuring remains valuable wherever a program's complexity comes primarily from managing many interacting, stateful entities. Most real languages today, as the final section of this chapter covers, let you mix both freely rather than forcing a single paradigm on your entire codebase.
