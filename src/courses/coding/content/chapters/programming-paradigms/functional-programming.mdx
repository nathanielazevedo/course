Functional programming takes a third, quite different stance from both procedural and object-oriented programming: instead of structuring a program around sequential steps or around objects with mutable state, structure it around composing pure functions (Chapter 4) that transform data without changing anything else. Chapter 4's section on higher-order functions was already a preview of this paradigm's core habits — this section makes the full philosophy explicit.

### Pure functions, revisited as a discipline

Functional programming treats purity (Chapter 4: output depends only on input, no side effects) not as an occasional nice-to-have, but as a default discipline applied as broadly as possible. A functional codebase tries to push side effects (writing to a file, making a network call, printing) to the thin outer edges of the program, keeping as much of the actual logic as possible as pure, side-effect-free transformations that are trivially easy to test — call the function with the same input, get the same output, every time, with nothing else to set up or verify.

### Immutability

**Immutability** — never modifying data in place, always producing a new value instead — is functional programming's other core habit, directly extending the immutable-by-default philosophy Chapter 6 touched on for structs and records. Rather than `list.append(item)` (mutating in place), functional style favors `newList = list + [item]` (producing a new list, leaving the original untouched). This eliminates an entire category of bugs where one part of a program mutates data another part is still relying on — because nothing is ever mutated, that scenario simply can't occur.

```javascript
// imperative / mutating
function addTax(items) {
  for (const item of items) item.price *= 1.08;
  return items;
}

// functional / immutable
function addTax(items) {
  return items.map(item => ({ ...item, price: item.price * 1.08 }));
}
```

### Function composition

As Chapter 4 covered, **function composition** — building larger transformations by chaining smaller ones together — is functional programming's primary tool for structuring an entire program: instead of a sequence of imperative steps mutating shared state, a functional pipeline reads as `validate → transform → summarize`, each stage a pure function feeding the next, with the overall behavior emerging from how the pieces compose rather than from a step-by-step mutation trace.

### Avoiding shared state

Because pure functions don't read or write anything outside their own input and output, functional code structurally avoids **shared mutable state** — the exact thing that makes concurrent programming (Chapter 11) so hard to get right in other paradigms. Two pure functions running truly in parallel can never interfere with each other, because neither can observe or change anything the other depends on; this is a large part of why functional idioms have become increasingly prominent even in traditionally imperative languages as multi-core hardware has made concurrency a mainstream concern rather than a specialized one.

### Functional programming in practice

Few mainstream languages are purely functional (Haskell is the best-known example that commits fully); most — Python, JavaScript, C#, Java, Rust — are multi-paradigm languages (the closing section of this chapter) that let you adopt functional habits selectively: immutable data where it helps, `map`/`filter`/`reduce` pipelines instead of manual loops, pure functions wherever side effects genuinely aren't needed, while still allowing mutation and objects where those remain the clearer tool.
