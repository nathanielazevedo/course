The earlier sections in this chapter covered branching, looping, and escaping normal flow as separate tools. This closing section pulls them together and pushes further into **structured pattern matching** — the modern synthesis where a single construct can branch, destructure, and bind in one motion, and where knowing which control-flow shape to reach for is itself a skill worth building deliberately.

### Matching on shape, not just value

A `switch` compares a value against other values. Pattern matching compares a value against a *shape*, which can be far richer: "is this a list with exactly two elements?", "is this a `Some` wrapping a number greater than zero?", "is this an object with a `status` field equal to `"error"`?" Rust's `match` is the clearest example:

```rust
match response {
    Ok(value) if value > 0 => println!("positive: {value}"),
    Ok(_) => println!("non-positive"),
    Err(e) => println!("failed: {e}"),
}
```

Each arm is testing structure (`Ok` vs. `Err`), optionally adding a further condition (the `if value > 0` guard), and binding a name (`value`, `e`) to part of the matched data — three things a plain `switch` can't do at once.

### Destructuring as control flow

JavaScript and Python don't have a full `match` in every version, but destructuring assignment does related work: `const { status, message } = response;` combined with a following `if (status === "error")` is doing, across two lines, roughly what a `match` arm does in one. Python 3.10's `match` statement closes this gap directly, supporting the same shape-and-bind pattern as Rust's.

### Exhaustiveness as a safety net

The real payoff of pattern matching over a chain of `if`/`else if` shows up when the set of possibilities is fixed and known — an enum, a `Result` type, a small set of variants. A compiler that enforces exhaustiveness will refuse to compile a `match` that doesn't handle every variant, turning "I forgot to handle the error case" from a runtime bug discovered in production into a compile-time error caught before the code ships. This is one of the most concrete, measurable safety benefits a language feature can offer, and it's a large part of why Rust and other modern languages lean on it so heavily.

### Choosing the right control structure

With this chapter's full toolkit in view — `if`, `switch`/`match`, `for`, `while`, `break`/`continue`/`return`, recursion — the practical skill is picking the right one for the shape of the problem, not defaulting to whichever you learned first:

- A fixed, small set of known cases to test against a value → `switch`/`match`, especially with a language that checks exhaustiveness.
- An unknown number of repetitions bounded by a condition → `while`.
- A known collection to walk → `for`/`foreach`.
- A problem defined in terms of a smaller version of itself (trees, nested structures) → recursion.
- A composite value you need to branch on *and* extract data from at the same time → pattern matching.

None of these choices is really about performance in most everyday code — it's about which construct lets the next person reading the code (very possibly you, in six months) see the intent immediately rather than reverse-engineer it from a generic loop or a long `if` chain.
