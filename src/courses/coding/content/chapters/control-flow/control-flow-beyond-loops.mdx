Branching and looping cover most control flow, but real code frequently needs to escape the normal top-to-bottom, in-order path entirely — stop a loop early, skip to the next item without finishing the current pass, or hand a value back to whoever called the current function. This section covers those escape hatches.

### `break`

`break` immediately exits the nearest enclosing loop, regardless of what the loop's own condition says. It's the right tool when you've found what you were looking for and continuing to iterate would be pure waste:

```python
for item in inventory:
    if item.id == target_id:
        found = item
        break
```

Without `break`, this loop would keep scanning every remaining item even after finding the one it wanted — correct, but needlessly slow on a large collection.

### `continue`

`continue` skips the rest of the current iteration and jumps straight to the loop's next pass, without exiting the loop entirely. It's the tool for "skip this one, keep going" rather than "stop entirely":

```python
for item in orders:
    if item.status == "cancelled":
        continue
    process(item)
```

This reads more clearly than wrapping the entire rest of the loop body in an `if not cancelled:` block, especially once there are several conditions worth skipping on.

### `return`

`return` exits a function immediately, optionally handing a value back to the code that called it. Unlike `break`, which only exits a loop, `return` exits the entire function, unwinding out of any loops or conditionals it happens to be nested inside at the moment it executes. This is covered more fully in Chapter 4, but it belongs here too because it's fundamentally a control-flow construct — a way of jumping out of the normal sequence of execution based on a condition.

### Early exits

An **early exit** — returning, breaking, or throwing as soon as a function has the information it needs, rather than accumulating that logic into a single exit point at the end — is a deliberate style choice, not just a shortcut. Code that exits as soon as it can tends to be flatter and easier to read than code that nests every subsequent check inside the `else` of the previous one.

### Guard clauses

A **guard clause** is an early return specifically used to handle an invalid or edge case up front, before the main logic of a function:

```python
def process_order(order):
    if order is None:
        return None
    if not order.items:
        return None
    # main logic, now guaranteed a valid, non-empty order
    ...
```

Without guard clauses, this same logic would nest three levels deep inside `if order is not None: if order.items: ...`, growing harder to read with every additional check. Guard clauses trade a few extra exit points for flatter, more linear code — and they're one of the most consistently recommended style patterns across otherwise very different language communities, because the benefit doesn't depend on any language-specific feature.
