Every loop covered so far repeats by going back to the top. **Recursion** repeats a different way: a function calls itself, with a smaller version of the same problem, until it reaches a case simple enough to answer directly. It's a different mental model for the same underlying goal — repetition — and some problems (anything shaped like a tree, or "this problem contains a smaller version of itself") are dramatically more natural to express recursively than with a loop.

### Recursive thinking

The trick to recursive thinking is trusting the function to solve the smaller problem correctly, and focusing only on how to combine that smaller answer into the current one. Computing a factorial: `factorial(n)` is `n * factorial(n - 1)` — you don't need to trace through every level by hand; you need to believe that `factorial(n - 1)` already works, and figure out what to do with its result.

```python
def factorial(n):
    if n <= 1:
        return 1          # base case
    return n * factorial(n - 1)   # recursive case
```

### Base cases

A **base case** is the condition simple enough to answer directly, without recursing further — `n <= 1` above. Every recursive function needs at least one; without it, the function calls itself forever (or, in practice, until it exhausts available memory — the next point). The base case is what turns "repeat" into "repeat a bounded number of times."

### Stack frames

Each recursive call adds a new **stack frame** (Chapter 5 covers this fully) to the call stack — its own local variables, its own copy of the parameters, its own place to resume once the call it made returns. `factorial(5)` isn't one function invocation; it's five nested ones, each waiting on the one below it to finish before it can compute its own `n * factorial(n - 1)`. This is why deep, unbounded recursion causes a **stack overflow** — each waiting frame consumes memory, and there's a limit to how many can exist at once.

### Recursion vs. iteration

Anything expressible recursively can also be expressed with a loop and an explicit data structure standing in for the call stack, and vice versa — the two are formally equivalent in what they can compute. The choice between them is almost always about clarity and the shape of the problem, not raw computational power. Traversing a tree (a folder structure, an HTML DOM, a parsed AST from Chapter 1) is usually far more natural recursively — "process this node, then recursively process each of its children" — than as an explicit loop with a manually managed stack of nodes to visit.

### Tail recursion

**Tail recursion** is a recursive call that is the very last operation in a function, with nothing left to do after it returns. Some languages (Scheme, and to varying degrees Rust and JavaScript engines) can perform **tail-call optimization**, reusing the current stack frame for the next call instead of pushing a new one — eliminating the stack-overflow risk for that specific recursive shape. Rewriting `factorial` to be tail-recursive means threading the accumulated result through as a parameter rather than computing it after the recursive call returns:

```python
def factorial(n, acc=1):
    if n <= 1:
        return acc
    return factorial(n - 1, n * acc)   # nothing left to do after this call
```

Not every language guarantees this optimization happens, though — it's worth checking before relying on it for deep recursion.
