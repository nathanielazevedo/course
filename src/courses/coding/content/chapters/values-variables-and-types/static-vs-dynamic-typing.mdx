Every value has a type — a number, a string, a list — but languages differ sharply in *when* they check that a value's type matches what an operation expects. That single design decision, checked before the program runs versus checked while it runs, is what "static vs. dynamic typing" actually means, and it's one of the most consequential splits between languages you'll use.

### What a type actually represents

A **type** is a category of values that share a set of valid operations and a representation in memory: `int` supports arithmetic, `string` supports concatenation, and the language (or the programmer) is expected to keep values used in ways that match their type — you can't meaningfully divide a string by a boolean. A type system is the set of rules a language uses to track and enforce which types values have and which operations are valid on them.

### Compile-time checking

In a **statically typed** language — Java, C, Rust, Go, TypeScript — every variable's type is known before the program ever runs, either because the programmer wrote it explicitly or because the compiler inferred it from context. The compiler checks that every operation is valid for the types involved *before* producing a runnable program, and rejects the code with a compile error if it isn't. `let x: number = "hello";` in TypeScript never runs — it fails during compilation, because assigning a string where a number was declared is caught before execution begins.

### Runtime checking

In a **dynamically typed** language — Python, JavaScript, Ruby — a variable can refer to a value of any type, and that type is only checked at the moment an operation actually happens, while the program runs. `x = "hello"` then later `x = 5` is completely legal — `x` isn't tied to a type, only the specific value it currently holds is. This means a type mismatch (`"5" + None` in Python) isn't caught until execution actually reaches that line — which might be seconds into running the program, or might be a rarely hit branch that doesn't surface for months.

### Type inference

Both static and dynamic languages can use **type inference** — the compiler or interpreter figuring out a type without it being written explicitly. `let x = 5` in Rust or TypeScript doesn't require writing `: number`; the compiler infers it from the literal `5` and still enforces it statically from that point on. Inference is a convenience feature layered on top of a type system's fundamental static-or-dynamic nature — it doesn't change which category a language falls into.

### Duck typing

**Duck typing** — "if it walks like a duck and quacks like a duck, treat it as a duck" — is a dynamic-typing idiom where code cares only about whether an object supports the operations it needs, not its declared type. A Python function that calls `.read()` on its argument will happily accept any object with a `.read()` method, regardless of what class it belongs to, because the check happens at the moment `.read()` is called, not before.

### Gradual typing

**Gradual typing** lets a fundamentally dynamic language opt into static checks incrementally — TypeScript adds a static type layer on top of JavaScript that's checked at compile time but erased before the code actually runs (JavaScript itself stays fully dynamic underneath); Python's type hints (`def add(a: int, b: int) -> int`) are optional annotations checked by separate tools like `mypy`, not enforced by the Python interpreter itself. Gradual typing is a popular middle ground: it gives large dynamic codebases some of static typing's safety without forcing a full rewrite.
