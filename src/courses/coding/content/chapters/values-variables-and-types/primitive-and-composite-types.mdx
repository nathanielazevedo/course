Every type a language offers falls into one of two broad categories: **primitive types**, the small set of basic building blocks a language provides natively, and **composite types**, structures built by combining primitives (and other composites) together. Recognizing which category a type belongs to tells you a lot about how it behaves — how it's stored, how it's compared, whether it's passed by value or by reference.

### The primitives

Almost every language provides some version of the same handful of primitives:

- **Integers** — whole numbers, often with a fixed bit-width (`int32`, `int64`) in statically typed languages, or arbitrary precision in Python.
- **Floating-point numbers** — numbers with a fractional part, represented approximately (Chapter 9 covers the representation itself).
- **Characters** — a single unit of text; some languages (C) have a distinct `char` type, others (Python) treat a single character as just a string of length one.
- **Strings** — sequences of characters, sometimes treated as primitive (Python), sometimes as a composite built from characters under the hood (C, where a string is really an array of `char`).
- **Booleans** — true or false.

Primitives are usually stored directly, compared by value (two `5`s are equal because they're the same number, not because they're "the same object somewhere in memory"), and immutable — you can't change a `5` into a `6`; you can only make a variable refer to a `6` instead.

### The composites

Composite types are built by combining values, and every language offers some version of these:

- **Arrays** — fixed-size, ordered, typically same-type sequences (common in statically typed languages).
- **Lists** — ordered, typically resizable sequences (Python's `list`, JavaScript's `Array`, which is actually more list-like than a strict C-style array).
- **Maps** — key-to-value associations (Python's `dict`, JavaScript's `Map` and object literals, Java's `HashMap`).
- **Sets** — unordered collections of unique values, with fast membership checks.
- **Structs** — fixed collections of named fields, common in C, Go, and Rust.
- **Tuples** — fixed-size, ordered groupings of values, often of different types, usually immutable.
- **Objects** — the most general composite, bundling both data (fields) and behavior (methods) together, covered fully in Chapter 6.

Composites are typically stored by reference (previous section), compared by structure or identity rather than automatically by value (two lists with identical contents aren't always considered "equal" without an explicit comparison method), and often mutable.

### Why the distinction matters in practice

This split explains behavior that otherwise seems arbitrary. Passing a number into a function and modifying it inside doesn't affect the caller's variable, because primitives are copied by value — the function got its own independent `5`. Passing a list into a function and calling `.append()` on it *does* affect the caller's list, because composites are typically passed by reference — the function got a reference to the same underlying list, not a copy. This exact behavior — sometimes summarized loosely as "pass by value vs. pass by reference" — is really just a consequence of primitives being value types and composites being reference types, and Chapter 4 covers precisely how it plays out across function calls.
