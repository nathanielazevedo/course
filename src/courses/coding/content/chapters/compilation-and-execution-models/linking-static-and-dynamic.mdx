Compiling a single source file to machine code is rarely the last step for a real program — most programs are built from multiple compiled pieces (your own code, plus libraries) that need to be assembled into one runnable whole. **Linking** is that final assembly step, and the choice between its two major strategies shapes how a compiled program actually gets deployed and run.

### Object files

Compiling a single source file (in a compiled language like C, C++, Rust, or Go) doesn't usually produce a finished, runnable program directly — it produces an **object file**, containing machine code for just that one file, along with a table of symbols it defines (functions, global variables) and symbols it references but doesn't itself define (functions from other files or libraries it calls). A multi-file program compiles into multiple object files, each still incomplete on its own.

### Static linking

A **linker** combines these object files into one finished executable, resolving every reference to an external symbol by finding where it's actually defined and connecting the two. **Static linking** does this by copying the actual machine code of every library a program depends on directly into the final executable, at build time — the result is one self-contained binary with everything it needs already inside it, at the cost of a larger file size (since every dependency's code is duplicated into every program that uses it) and requiring a full rebuild any time a statically linked library needs to be updated, since the old copy is baked permanently into the already-built executable.

### Dynamic linking

**Dynamic linking** takes a different approach: instead of copying a library's code into the executable, the executable just records *that* it needs a particular library, and the actual connecting — loading the library's code and resolving those references — happens later, when the program is actually launched (or, in some setups, on the linker's very first reference to a not-yet-loaded piece of it). This produces a smaller executable (no duplicated library code inside it) and allows a shared library to be updated once, independently, with every program that depends on it automatically picking up the update the next time it runs — at the cost of the target machine needing a compatible copy of every dynamically linked library actually present and correctly versioned, which is exactly the class of deployment problem often described as "DLL hell" on Windows or missing shared-library errors on Linux.

### Shared libraries

A **shared library** — a `.so` file on Linux, a `.dylib` on macOS, a `.dll` on Windows — is a single compiled library that multiple programs can dynamically link against simultaneously, with the operating system loading only one copy of it into memory even if a dozen running programs all depend on it. This is where dynamic linking's real payoff shows up at the system level: instead of every installed program on a machine carrying its own private copy of, say, a common cryptography library, one shared copy serves every program that needs it, saving both disk space and memory, and letting a security patch to that one shared library protect every program depending on it as soon as it's updated.

### Choosing between them

Modern practice often blends both deliberately: statically linking a program's less commonly shared, more tightly coupled dependencies (for a simpler, more portable, single-file deployment — exactly what Go's toolchain defaults to, and what Rust commonly does for its own dependencies) while dynamically linking widely shared system libraries (the C standard library itself, on most platforms, is dynamically linked even by programs that statically link everything else) — balancing the deployment simplicity static linking offers against the storage and update efficiency dynamic linking provides at the operating-system level.
