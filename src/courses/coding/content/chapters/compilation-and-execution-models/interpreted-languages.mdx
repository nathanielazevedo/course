Where the previous section's languages translate everything before anyone runs the program, interpreted languages translate and execute together, live, each time the program actually runs — the tradeoff Chapter 1 introduced conceptually, now examined through the two clearest real-world examples.

### Python

Classic Python execution actually involves a small compilation step most people don't think of as "compiling": the CPython interpreter first compiles source `.py` files into bytecode (cached as `.pyc` files), and *that* bytecode is what the interpreter actually walks and executes, one instruction at a time, rather than re-parsing raw source text on every run. This is why Python is more precisely described as "bytecode-interpreted" rather than purely interpreting source text directly — but from a deployment perspective, it behaves like a classic interpreted language regardless: there's no separate ahead-of-time build step producing a standalone binary, and a compatible Python interpreter needs to be present wherever the code runs, exactly as Chapter 1's section on runtime environments described.

### Shell scripting

Shell scripts (Bash, Zsh, PowerShell) are interpreted even more directly — a shell reads a script largely line by line, translating and executing each command as it goes, with essentially none of the upfront whole-file analysis a language like Python's bytecode compilation performs. This is exactly why a shell script can fail partway through with a syntax error on a *later* line, after already having executed several earlier lines successfully — the interpreter genuinely hadn't looked ahead at that later line yet, in sharp contrast to Chapter 1's point about how Python's `SyntaxError`s are typically caught before any execution begins, because Python's compilation-to-bytecode step processes the whole file up front before the interpreter starts running any of it.

### The practical tradeoffs, revisited

Interpreted execution's core appeal remains what Chapter 1 described: immediacy — edit a file, run it, no separate build step in between — which is exactly why scripting, rapid prototyping, and automation tasks lean so heavily on interpreted languages. The cost is repeated translation-adjacent work on every run (even with Python's bytecode caching, the interpreter still has to walk and execute that bytecode fresh every single execution, with none of ahead-of-time compilation's one-time optimization work carried over between runs) and a hard dependency on the right interpreter being installed and available wherever the code needs to execute.

### Where the line actually blurs

It's worth being precise that "interpreted language" is really a statement about how a language is *typically* run, not an unchangeable property of the language itself — Python has multiple implementations (PyPy notably includes a JIT compiler, covered in the next section), and there's no reason in principle a sufficiently motivated project couldn't build an ahead-of-time compiler for Python or Bash. In practice, though, the ecosystem, tooling, and typical deployment story around a language are what actually determine whether you experience it as "compiled" or "interpreted" day to day — which is exactly why this section (and the next, on JIT compilation) is organized around real, dominant implementations rather than abstract language specifications alone.
