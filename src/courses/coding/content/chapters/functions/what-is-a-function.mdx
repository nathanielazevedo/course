Every meaningful piece of logic in a program eventually gets wrapped in a **function** — a named, reusable block of code that takes input, does something with it, and (usually) produces output. Functions are the primary tool every language gives you for managing complexity: instead of one enormous sequence of statements, a program becomes a collection of small, named, individually understandable pieces that call each other.

### Input

A function's **input** is the data it receives to work with, expressed as **parameters** — placeholders in the function's definition that get filled in with actual values (**arguments**) each time it's called. A function with no parameters still has an implicit kind of input: whatever state it reads from outside itself, covered below under side effects.

```python
def discount_price(price, percent_off):
    return price * (1 - percent_off / 100)
```

Here `price` and `percent_off` are parameters; calling `discount_price(50, 20)` supplies `50` and `20` as arguments.

### Transformation

The **transformation** is the actual logic — the sequence of operations the function performs on its input to arrive at a result. This is the part most people picture when they think of "the function," but input and output matter just as much, because they define the *contract* the function makes with whoever calls it: give me this, I'll give you back that.

### Output

A function's **output** is the value it hands back via `return` (Chapter 3 covers `return` as a control-flow construct; this is the same mechanism, viewed from the function-design side). Not every function has to return something meaningful — a function whose entire purpose is to cause a side effect (printing, writing a file, sending a network request) might return nothing at all, which most languages represent with a specific "no value" type (`None` in Python, `void` in Java and C, `()` in Rust).

### Side effects

A **side effect** is any change a function makes to something outside its own local scope — modifying a global variable, writing to a file, printing to the console, mutating an object passed in as an argument. A function with no side effects, whose output depends purely on its input and nothing else, is called a **pure function** — call it twice with the same arguments and you get the same result every time, with no observable impact on anything outside it. Pure functions are dramatically easier to reason about, test, and run safely in parallel, which is why Chapter 7's section on functional programming builds an entire paradigm around maximizing them. Most real-world code is a mix: some functions are pure logic, others exist specifically to cause side effects, and being deliberate about which is which is one of the most valuable habits a programmer can build.
