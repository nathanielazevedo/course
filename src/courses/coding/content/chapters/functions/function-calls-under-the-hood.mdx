Calling a function looks like a single operation from the outside — `result = add(2, 3)` — but underneath, the runtime is doing real, mechanical work: setting aside memory, recording where to resume afterward, and tearing all of that back down once the function finishes. This section opens the hood on that machinery, which Chapter 5 covers in much more depth once memory itself is the topic.

### Call stacks

The **call stack** is the runtime's record of which functions are currently in progress, ordered by who called whom. When `main` calls `compute`, and `compute` calls `add`, all three are "in progress" simultaneously — `add` hasn't finished, so neither has `compute`, so neither has `main` — and the stack reflects exactly that nesting, with the most recently called function on top.

### Stack frames

Each entry on the call stack is a **stack frame** — a chunk of memory holding everything that specific function call needs: its parameters, its local variables, and the **return address**, the exact point in the calling function's code to resume at once this call finishes. When `add` returns, its frame is discarded entirely (popped off the stack), and execution resumes in `compute` exactly where it left off, as if the interruption never happened from `compute`'s perspective.

### Arguments and return values

When a function is called, its arguments are copied into its new stack frame as that function's parameters (the previous section's distinction between the two matters here — the parameter is the local copy inside the new frame). When the function returns, its return value is handed back to the calling frame, typically through a dedicated CPU register for simple values, before the callee's frame is torn down — the return value has to escape the frame before the frame is deleted, or it would be lost.

### Local variables

**Local variables** — anything declared inside a function body — live inside that function's stack frame and exist only as long as the frame does. This is precisely why a local variable "disappears" once its function returns: there's no more frame for it to live in. It also explains why recursion (Chapter 3) works correctly even though every recursive call uses the same variable *names* — each call gets its own frame, and therefore its own independent copy of those names, with no risk of one call's `n` colliding with another's.
