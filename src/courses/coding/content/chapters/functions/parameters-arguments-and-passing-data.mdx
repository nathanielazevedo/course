Not every parameter has to be filled the same way. Languages offer several distinct styles for supplying arguments to a function, and — separately — several distinct rules for exactly what gets handed over when an argument is passed. Both matter for predicting how a function call actually behaves.

### Positional arguments

**Positional arguments** are matched to parameters purely by order — the first argument fills the first parameter, the second fills the second, and so on. This is the default in most languages and works well until a function has enough parameters that remembering the correct order becomes its own burden.

```python
def create_user(name, email, age):
    ...

create_user("Ada", "ada@example.com", 32)  # positional
```

### Named arguments

**Named (or keyword) arguments** let the caller specify which parameter each value fills by name, independent of order — Python's `create_user(email="ada@example.com", name="Ada", age=32)` works identically to the positional call above, and reads more clearly at the call site, especially with several arguments of the same type where positional order alone is easy to get wrong.

### Default arguments

A **default argument** lets a parameter have a value it takes on when the caller doesn't supply one at all: `def create_user(name, email, age=18):` lets callers omit `age` entirely and get `18`. This is a convenience for the common case, without forcing every caller to know or care about a value they usually don't need to change.

### Variadic functions

A **variadic function** accepts an arbitrary number of arguments rather than a fixed count — Python's `def total(*numbers):`, JavaScript's `function total(...numbers)`, C's `printf`. Internally, the variadic parameter is usually collected into a single composite value (a tuple, an array) that the function body can iterate over, which connects directly back to Chapter 2's primitive-vs-composite distinction.

### Pass by value

**Pass by value** means the function receives a *copy* of the argument — changes made to the parameter inside the function have no effect on the caller's original variable. As Chapter 2 covered, primitives are almost universally passed by value: passing a number into a function and reassigning the parameter inside doesn't touch the caller's number.

### References

**Passing a reference** means the function receives something that points at the same underlying data as the caller's variable, rather than an independent copy. As covered in Chapter 2, composites (lists, objects, dictionaries) are typically passed this way — the function doesn't get its own list, it gets a reference to the *same* list the caller has.

### Object references

This is worth stating precisely, because it resolves a common point of confusion: what's passed by value is the *reference itself*, not the object. `def add_item(cart): cart.append(item)` mutates the caller's actual cart, because `cart` inside the function refers to the same list object. But `def replace_cart(cart): cart = []` does *not* affect the caller's cart at all — it just reassigns the local `cart` name (a copy of the reference) to point at a brand-new empty list, leaving the caller's original reference untouched.

### Why "pass by reference" is often misunderstood

Many languages — Python, Java, JavaScript — are accurately described as "pass by value, where the value happens to be a reference for objects," not "pass by reference" in the strict sense some other languages (C++ with `&` parameters, or Pascal) actually implement, where the *caller's own variable* can be reassigned from inside the function. The distinction matters exactly at the moment shown above: mutating through a reference is visible to the caller; reassigning the local reference is not, and mixing those two up is one of the most common sources of "why didn't my function's result show up outside it?" bugs.
