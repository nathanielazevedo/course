TypeScript and Java sit on opposite ends of a shared theme — both add substantial static analysis on top of a foundation, but from opposite directions: TypeScript layers types onto a language that was never designed with them, while Java was static and class-based from its very first release, decades before TypeScript existed.

### Adding static analysis to JavaScript

TypeScript (Chapter 1, Chapter 10) is JavaScript with an optional static type layer bolted on top, checked entirely at compile time and then stripped away completely before the code actually runs — a form of gradual typing (Chapter 2) and transpilation (Chapter 10) combined. This is a genuinely unusual position: TypeScript's type system has zero effect on runtime behavior at all — every type error it catches is purely a compile-time-only safety net, and the compiled output is ordinary, untyped JavaScript, subject to exactly the same dynamic, weakly typed runtime behavior covered in the previous section.

### Structural typing

TypeScript's type checker uses structural typing (Chapter 6) by default, matching JavaScript's own duck-typing-friendly spirit (Chapter 2): two types are considered compatible if they have the same shape, regardless of whether either was explicitly declared to implement the other.

```typescript
interface Point { x: number; y: number; }
function distance(p: Point) { /* ... */ }

const coord = { x: 3, y: 4, label: "origin" };
distance(coord);   // fine — coord has the required shape, extra fields are allowed
```

This fits naturally with JavaScript's underlying object model (the previous section's prototype chains) — checking shape rather than declared identity is a very natural fit for a language whose runtime never had a concept of nominal types to check against in the first place.

### JVM and static typing (Java)

Java, by contrast, has been statically and nominally typed (Chapter 6) from its first release — every variable's type is declared and checked at compile time, and satisfying an interface requires an explicit `implements` declaration, not just a matching shape. It compiles to bytecode that runs on the JVM (Chapter 10), giving it the portability ("write once, run anywhere") and automatic memory management (Chapter 5's garbage collection) that come with that model.

### Classical OOP

Java is one of the clearest examples of classical, class-based object-oriented programming (Chapter 6, Chapter 7) taken seriously as an entire language philosophy: every piece of code lives inside a class, inheritance and interfaces are core, first-class language features rather than optional patterns, and the language's evolution over decades has largely been about adding functional-style features (lambdas, streams) *on top of* that object-oriented foundation, rather than replacing it.

### Enterprise design

Java's design priorities — strong static typing to catch errors early in large codebases, a stable, backward-compatible standard library, the JVM's portability across enterprise server environments — directly reflect the large-scale, long-lived, multi-team software it was built for. This is exactly why Java remains dominant in banking systems, large corporate backends, and Android app development (which uses a JVM-compatible runtime): its design tradeoffs favor exactly the kind of predictability, tooling maturity, and long-term maintainability that matters most at that scale, even at some cost to the fast, exploratory iteration Python and JavaScript both prioritize more heavily.
