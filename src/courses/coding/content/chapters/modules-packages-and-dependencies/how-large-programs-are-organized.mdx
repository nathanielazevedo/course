Every example so far in this course could plausibly fit in a single file. Real programs can't — a production codebase might span thousands of files and millions of lines, and none of that is manageable without a deliberate structure for organizing it. This section covers the layers languages provide for that: files, modules, packages, and namespaces.

### Files

A **file** is the most basic unit of organization — one physical text file containing some subset of a program's source code. Splitting a program across files is partly about keeping any single file human-readable (nobody wants to scroll through a 20,000-line file to find one function) and partly the foundation everything else in this section builds on: modules, packages, and namespaces are all, ultimately, ways of organizing and referring to collections of files.

### Modules

A **module** is a unit of code — typically corresponding to one file, though not always — that can export some of what it defines (making it usable elsewhere) while keeping the rest private to itself. Python treats every `.py` file as a module automatically; JavaScript's ES modules use explicit `export`/`import` to control exactly what crosses a module's boundary. The core value of a module is a controlled interface: other code can use what a module exports, and nothing else, which is the same encapsulation instinct from Chapter 6 applied at the scale of a whole file instead of a single class.

```python
# math_utils.py
def square(x):
    return x * x

def _internal_helper(x):   # convention: leading underscore signals "not for external use"
    return x + 1
```

### Packages

A **package** groups multiple related modules together under one namespace, typically corresponding to a directory. Python's packages are directories containing an `__init__.py`; Java's packages (`com.example.utils`) map directly onto a directory structure and control both organization and (through access modifiers) visibility between packages. A package is essentially "a folder of modules that belong together conceptually," giving a large codebase a second, coarser level of structure above individual files.

### Namespaces

A **namespace** solves a different, narrower problem: preventing naming collisions. Two different libraries might both define a function called `parse` — without namespaces, importing both would create an ambiguous conflict over which `parse` a bare reference to that name actually means. C++'s `namespace`, C#'s `namespace`, and the effective namespacing that Python's and Java's package/module systems provide all let two identically named things coexist without conflict, as long as they're referred to through their distinguishing namespace (`json.parse` vs. `yaml.parse`) rather than bare names alone.

### How these layers work together

In practice, these four concepts stack: files are grouped into modules, modules are grouped into packages, and packages exist within namespaces that keep large codebases (and the external libraries they depend on) from colliding with each other by name. The next section, on imports, covers how code in one of these units actually reaches into another to use what it exports — the mechanism that makes this entire layered structure actually functional rather than just organizational.
