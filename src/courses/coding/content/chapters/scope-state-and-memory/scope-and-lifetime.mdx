Two questions come up constantly once a program has more than a handful of variables: *where* is this name visible, and *how long* does the value it refers to actually stick around? These are two related but genuinely separate concepts — **scope** and **lifetime** — and conflating them is a common source of confusion, especially once closures (Chapter 4) enter the picture.

### Global scope

A variable in **global scope** is visible from anywhere in the program, including inside functions defined far away from where it was declared. Global scope is convenient and, in any program past a small size, dangerous — any piece of code anywhere can read or modify it, which makes tracking down where a value actually changed a genuinely hard problem in a large codebase. Most style guides across every language recommend minimizing global state for exactly this reason.

### Local scope

A **local** variable is visible only within the function (or block) it's declared in. This is the default and the recommended norm — keeping a variable's visibility as narrow as possible limits how much code could possibly be responsible for a bug involving it, which is a huge practical win as programs grow.

### Block scope

**Block scope** ties a variable's visibility to the specific `{ }` block (an `if`, a `for` loop body) it's declared inside, not just the enclosing function. JavaScript's `let` and `const` are block-scoped; its older `var` is not — `var` is function-scoped, meaning a `var` declared inside an `if` block is still visible after that block ends, which surprises people used to block scoping and is a large part of why `let`/`const` were introduced.

### Function scope

**Function scope** ties a variable's visibility to the entire enclosing function, regardless of which nested blocks it passes through. This is what `var` does in JavaScript, and it's the default scoping rule in a number of older or more permissive languages — a variable declared anywhere inside a function is visible everywhere else in that same function.

### Lexical scope

**Lexical scope** (also called static scope) means a name's visibility is determined by *where it's written in the source code*, not by the runtime call sequence that leads to it executing — which is how essentially every mainstream language resolves scope today, and it's what makes closures (Chapter 4) predictable: a nested function can see the variables of the function it's textually written inside, regardless of who ends up calling it or when.

### Scope vs. lifetime

Scope answers "where is this name visible in the code?" — a purely textual, compile-time question. **Lifetime** answers "how long does the value actually exist in memory?" — a runtime question, covered fully in the next two sections on the stack and the heap. The two usually track together (a local variable's scope ends when its function returns, and so does its lifetime, since its stack frame is destroyed) but they can diverge sharply — a closure's captured variable is out of the scope where you can freely reference it by that exact name elsewhere in the code, yet its lifetime is extended well past when the enclosing function returned, precisely because the closure keeps it alive.
