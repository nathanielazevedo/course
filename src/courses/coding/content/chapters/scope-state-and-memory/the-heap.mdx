Everything the stack can't do well — hold data of unknown size, keep data alive past the function that created it, share one piece of data between multiple parts of a program — is exactly what **the heap** exists for. It's slower and more complex to manage than the stack, and that complexity is the direct cause of most of the memory-related bugs and language-design decisions covered in the rest of this chapter.

### Dynamic allocation

**Dynamic allocation** is requesting a block of heap memory of a specific size *while the program runs*, rather than having a fixed size baked in at compile time. When you write `new User(...)` in Java, `Box::new(value)` in Rust, or simply create a list in Python that grows as you append to it, the runtime is asking the heap allocator for a chunk of memory sized to fit that data — an operation that, unlike stack allocation, requires the allocator to actually search for and track available space, which is part of why heap allocation is measurably slower than stack allocation.

### Objects live here

As Chapter 2 established, composite types — objects, most collections — are typically stored on the heap and referred to through a reference held on the stack (or inside another heap object). This is exactly why a variable holding an object behaves the way it does when passed to a function or assigned to another variable (Chapter 4): the reference — a stack-sized, fixed-size pointer — is what's copied around, while the actual object data stays put on the heap, unaffected by how many references point at it.

### References, revisited

A **reference** into heap memory is what lets data outlive the function that created it. A stack frame's local variable disappears when the function returns, but if that local variable was a reference to heap data, and something else (a returned value, a variable in the caller, an object field) still holds a copy of that same reference, the heap data itself is untouched — it doesn't care that the original stack frame is gone, because it was never stored there in the first place.

### Shared data

Because a heap object can be referenced from more than one place at once — two variables, two objects, two threads — heap data is inherently **shared** in a way stack data structurally can't be. This is the source of both the heap's power (it's how two parts of a program can genuinely collaborate on the same data) and one of its sharpest risks: if one part of the program mutates shared heap data while another part is still relying on its old state, unexpected bugs follow — a topic Chapter 11's section on concurrency returns to directly, since it gets significantly harder once multiple threads touch the same heap data at once.

### The cost of the heap's flexibility

Because heap memory isn't automatically reclaimed the way a stack frame is (popping a frame is instantaneous and complete; heap data has no equivalent "the function that made this is done" signal), something has to decide when a piece of heap data is no longer needed and can be freed. That "something" — manual freeing, garbage collection, or ownership rules — is the entire subject of the next two sections, and it's arguably the single biggest philosophical difference between programming languages covered anywhere in this course.
