Chapter 4 introduced the call stack as the mechanism behind function calls. This section looks at **the stack** as a region of memory in its own right — what makes it fast, what it's good for, and what its one hard limit actually is.

### Function calls, revisited as memory

Every function call pushes a new stack frame, and every return pops one off (Chapter 4 covered this from the control-flow side). What makes the stack worth a dedicated section is *how* it manages memory: allocation and deallocation on the stack are just moving a single pointer — the "top of stack" marker — up or down. There's no searching for free space, no bookkeeping about what's still in use; the very last thing pushed is always the very first thing popped, a strict last-in-first-out discipline that makes stack memory operations some of the cheapest a CPU can perform.

### Local variables, again

Local variables (parameters and anything declared inside a function body) are stored in the current stack frame by default, in most languages, as long as their size is known ahead of time — a fixed-size number, a struct with a known layout. This is why local variables are so cheap to create and destroy: creating one is just writing into already-allocated frame space, and destroying it is simply popping the frame, no individual cleanup required.

### Stack frames as isolated workspaces

Each stack frame is its own isolated workspace — one function's local variables can't accidentally collide with another's, even if they share the exact same names, because they live in entirely separate frames (Chapter 4's recursion example demonstrated this directly). This isolation is part of what makes reasoning about a single function in isolation possible at all: you don't need to know what every other function in the program is doing with its own locals to understand what yours will do with its.

### Stack overflow

The stack's LIFO discipline and fixed, contiguous layout come with a real limit: each thread is typically given a fixed, relatively small amount of stack space (commonly around 1MB, though it varies by platform and language) when it starts. Push more frames onto it than that space allows — through excessively deep, non-tail-recursive function calls (Chapter 3), most commonly — and you get a **stack overflow**: the runtime detects the stack has grown past its allotted region and terminates the program (or throws a specific exception, in languages that catch this gracefully) rather than letting it corrupt adjacent memory.

```python
def infinite_recursion(n):
    return infinite_recursion(n + 1)  # no base case — grows without bound

infinite_recursion(0)  # RecursionError: maximum recursion depth exceeded
```

This connects directly back to Chapter 3's point about base cases: a stack overflow is very often the concrete, observable symptom of a recursive function missing one, or of a base case that's unreachable due to a logic error.

### Why the stack alone isn't enough

The stack's speed comes at a real cost: everything on it has a size known at compile time, and everything on it disappears the moment its function returns. Any data that needs to outlive its creating function, or whose size isn't known until the program is actually running (a list that grows to an unknown length, an object shared between multiple parts of a program), can't live on the stack at all — which is exactly the gap the next section, on the heap, exists to fill.
