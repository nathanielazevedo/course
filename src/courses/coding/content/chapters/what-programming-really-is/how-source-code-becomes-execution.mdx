The text you type in an editor is not what a CPU runs. Between your source file and a running program sits a pipeline — the same shape in every language, even though different languages stop at different points along it. Understanding this pipeline demystifies a lot of language trivia: why Python gives you a stack trace pointing at a specific line, why C won't even build if you misspell a keyword, why some errors show up before your program runs and others only show up while it's running.

### Source code and tokens

Source code is just a text file — a sequence of characters with no inherent structure a machine can act on yet. The first step, **lexing** (short for lexical analysis), scans that text and groups characters into **tokens**: meaningful chunks like `total`, `=`, `0`, `+`, `(`, `)`. A lexer doesn't understand grammar yet — it just recognizes "this run of characters is a number," "this one is an identifier," "this one is an operator," the same way you'd recognize word boundaries in a sentence before understanding what the sentence means.

### Parsing and the abstract syntax tree

**Parsing** takes that flat stream of tokens and imposes structure, checking it against the language's grammar rules and building an **abstract syntax tree (AST)** — a tree where each node represents a construct like "this is a function call," "this is a binary addition," "this is an if-statement with these branches." `total = price * quantity` becomes a tree with an assignment at the root, `total` as one child, and a multiplication node (with `price` and `quantity` as its own children) as the other. This is the point where a missing parenthesis or a misplaced keyword becomes a **syntax error** — the token stream doesn't form a valid tree under the language's grammar.

### From AST to execution

Once a language has a valid AST, it takes one of two broad paths, covered in full in the next section: it can be **compiled** — translated ahead of time into a lower-level form (often native machine code, sometimes an intermediate bytecode) that's saved and run later — or it can be **interpreted** — walked and executed directly, node by node, without ever producing a separate standalone artifact. Many modern languages blend both, and the next section is entirely about that distinction and the tradeoffs it implies.

### Why this pipeline matters day to day

This is not just trivia. It explains real, everyday behavior: a `SyntaxError` in Python happens during parsing, before a single line of your logic runs, which is why Python can catch a typo on line 400 even if line 1 never executes. A `NameError`, by contrast, only appears once execution actually reaches that line — because checking whether a name exists happens at runtime, not during parsing. Different languages draw this line between "caught before running" and "caught while running" differently, and that line is exactly what the rest of this course — types, errors, compilation models — keeps coming back to.
