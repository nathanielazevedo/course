Not every bundle of related data needs the full machinery of a class — inheritance, encapsulation, custom methods for every operation. Many languages provide a lighter-weight alternative purely for grouping data together: **structs**, **records**, and **data classes**, whose entire purpose is representing data plainly, without the behavioral baggage a full class implies.

### Data-oriented programming, in miniature

The core idea is separating "what shape is this data?" from "what can this thing do?" — a struct or record answers only the first question. A `Point` with `x` and `y` fields doesn't need custom methods to be useful; it needs to reliably hold two numbers and be easy to compare, copy, and pass around. This is a smaller-scale preview of the data-oriented programming paradigm covered fully in Chapter 7 — treating data as data first, and layering behavior on separately (as free functions that operate on it) rather than baking it directly into the type.

### Structs

**Structs**, most prominent in C, Go, and Rust, are fixed collections of named fields with no inheritance and (in C, and by default in Go) no methods at all — just data:

```rust
struct Point {
    x: f64,
    y: f64,
}

fn distance(a: &Point, b: &Point) -> f64 {
    ((a.x - b.x).powi(2) + (a.y - b.y).powi(2)).sqrt()
}
```

Rust and Go do let you attach methods to structs (`impl Point { ... }` in Rust), but the struct itself remains fundamentally a data definition — there's no inheritance between structs, which sidesteps the deep-hierarchy problems from earlier in this chapter entirely, by construction.

### Records

**Records** — Java's `record`, C#'s `record`, Python's `dataclass` — are a more recent addition to traditionally class-heavy languages, purpose-built to reduce the ceremony of a data-only class. Without a record, a plain Java class holding two fields still requires a hand-written constructor, `equals()`, `hashCode()`, and `toString()` to behave sensibly — dozens of lines for what is conceptually two fields. A record generates all of that automatically from the field declaration alone:

```java
public record Point(double x, double y) {}
```

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float
```

Both give you a constructor, sensible equality (comparing field values, not object identity — a deliberate departure from the identity-based default equality covered in the "What Is an Object?" section), and a readable string representation, all without writing any of that boilerplate by hand.

### Immutability by default

Many of these lightweight data types default to (or strongly encourage) **immutability** — once created, a record's fields can't be reassigned. Java's `record` fields are always final; Rust's structs are immutable unless explicitly marked `mut`; functional-style data classes across many languages follow the same convention. This connects to the same tradeoff functional programming makes more broadly (Chapter 7): immutable data is inherently safer to share across functions or threads, because nothing can silently change out from under code that's holding a reference to it.

### When to reach for a struct instead of a full class

The practical rule of thumb: if a type's entire purpose is holding a fixed shape of related data — a coordinate, a color, an API response — reach for a struct, record, or data class instead of a full class with encapsulated fields and custom accessors. Reserve full classes for cases where an object genuinely needs to protect its own invariants (a `BankAccount` that must never go negative) or where meaningful behavior is intrinsic to the type, not just data passing through it.
