Classes rarely exist in total isolation — a `SavingsAccount` and a `CheckingAccount` are both clearly kinds of `BankAccount`, sharing most of its behavior while adding or changing a little. **Inheritance** is the mechanism most object-oriented languages provide for expressing exactly that relationship, and **polymorphism** is what makes it actually useful in practice.

### Base classes and subclasses

A **base class** (or **superclass**, **parent class**) defines shared state and behavior; a **subclass** (or **derived class**, **child class**) extends it, inheriting everything the base class defines while adding its own fields and methods, or overriding inherited ones with its own version.

```python
class BankAccount:
    def __init__(self, balance=0):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount

class SavingsAccount(BankAccount):
    def __init__(self, balance=0, interest_rate=0.02):
        super().__init__(balance)
        self.interest_rate = interest_rate

    def apply_interest(self):
        self.balance += self.balance * self.interest_rate
```

`SavingsAccount` gets `withdraw` for free, without redefining it, and adds `apply_interest`, a method specific to itself. `super().__init__(balance)` calls the parent class's constructor to set up the inherited part of the object's state before adding the subclass's own.

### Polymorphism

**Polymorphism** — literally "many forms" — is the ability to treat objects of different subclasses uniformly through their shared base type, while each one still behaves according to its own specific implementation. A function that accepts any `BankAccount` and calls `.withdraw()` on it doesn't need to know or care whether it received a plain `BankAccount`, a `SavingsAccount`, or a `CheckingAccount` — it calls the same method name, and each object's own version (if it has overridden it) runs. This is what lets code written against a general type automatically work correctly with any more specific type, without modification, as long as that specific type honors the base type's contract.

```python
def process_withdrawal(account: BankAccount, amount: float):
    account.withdraw(amount)   # works identically for any BankAccount subclass
```

### The problems with deep inheritance

Inheritance is powerful, and it's also the single most over-recommended tool in early object-oriented education, because it's easy to reach for and hard to walk back once a hierarchy grows too deep or too tangled. A five-level-deep inheritance chain (`Employee` → `Manager` → `SeniorManager` → `RegionalDirector` → `VicePresident`) tightly couples every level to every level above it — changing behavior in `Employee` risks unexpectedly changing behavior four levels down, and understanding what any single class actually does requires reading its entire ancestry. This is exactly what motivates the next section's alternative — composition — and it's why "favor composition over inheritance" is one of the most widely repeated pieces of object-oriented design advice across very different language communities, not a fringe opinion.
