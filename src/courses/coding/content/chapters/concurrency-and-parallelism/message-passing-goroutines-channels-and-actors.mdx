Every synchronization tool covered earlier in this chapter — locks, mutexes, semaphores, atomics — solves concurrency by carefully controlling access to memory that multiple threads *share*. This section closes the chapter with a different philosophy entirely: instead of sharing memory and coordinating access to it, don't share memory at all — communicate by passing messages between independent units of execution instead.

### Go's concurrency model

Go's approach is captured in one of its most quoted design principles: "don't communicate by sharing memory; share memory by communicating." A **goroutine** is Go's lightweight unit of concurrent execution — far cheaper than an OS thread (thousands can run within a single program without the overhead full OS threads would impose), scheduled cooperatively by Go's own runtime rather than the operating system directly:

```go
func worker(jobs <-chan int, results chan<- int) {
    for j := range jobs {
        results <- j * 2
    }
}

go worker(jobs, results)   // launches a new goroutine
```

### Channels

A **channel** is a typed conduit for passing values between goroutines — instead of two goroutines directly reading and writing the same shared variable (which would need a mutex, as covered earlier), one goroutine sends a value on a channel, and another receives it, with the channel itself handling the necessary synchronization internally. This inverts the earlier approach: rather than protecting shared data with a lock, the data is only ever "owned" by one goroutine at a time, and ownership transfers explicitly through a channel send — there's no window where two goroutines could simultaneously touch the same value unsynchronized, because the channel itself is the only path between them.

### Message passing as a general strategy

**Message passing** is the general term for this style of concurrency: independent units of execution (goroutines, actors, processes) with their own private state communicate exclusively by sending each other messages, rather than reaching into each other's memory directly. This sidesteps race conditions structurally, the same way Rust's ownership model (Chapter 5) sidesteps memory-safety bugs — not by adding careful runtime coordination around shared access, but by making unsynchronized shared access impossible to express in the first place.

### Actors and independent state

The **actor model** — used prominently in Erlang, Elixir, and Akka (on the JVM) — generalizes this idea further: an **actor** is an independent unit with its own completely private state that no other actor can ever access directly, communicating only by sending asynchronous messages to other actors' **mailboxes** (a queue of pending messages waiting to be processed). Each actor processes its own mailbox one message at a time, sequentially, which means an individual actor's own state never needs internal synchronization at all — from that actor's own perspective, it's just handling messages one after another, even though the overall system, with potentially thousands of actors, is deeply concurrent.

### Distributed thinking

What makes the actor model and message passing especially valuable is that they scale naturally from "concurrency within one machine" to genuinely **distributed systems** across multiple machines — a message sent to a goroutine's channel and a message sent over a network to a process on a different physical server are conceptually the same operation (send a message, don't touch shared memory), which is precisely why message-passing-based systems tend to generalize to distributed architectures far more gracefully than shared-memory concurrency (locks and mutexes fundamentally require memory that's actually shared, which simply doesn't exist across separate machines) — a connection this course returns to when networking and distributed systems come up directly in Chapter 13.
