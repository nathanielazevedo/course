Doing more than one thing "at once" starts with understanding the two units an operating system actually gives you to work with: processes and threads. Everything else in this chapter — concurrency, parallelism, synchronization, async — builds on this foundation.

### Process isolation

A **process** is a running instance of a program, given its own private, isolated slice of memory by the operating system — one process cannot directly read or write another process's memory, and a crash in one process doesn't corrupt or bring down another. This isolation is a deliberate safety boundary: your web browser and your text editor run as entirely separate processes precisely so a bug in one can't reach into and corrupt the other's data.

### Memory spaces

Each process gets its own **memory space** (or address space) — its own private view of memory, including its own stack (Chapter 5) and heap (Chapter 5), independent of every other process's. This is *why* processes are safe to isolate from each other in the first place: there's no shared memory to accidentally corrupt across a process boundary, because each process's addresses genuinely refer to different physical memory than the same addresses would in another process.

### Threads

A **thread** is a unit of execution *within* a process — a single process can run multiple threads simultaneously, and unlike separate processes, all the threads within one process share that process's memory space: the same heap, the same global variables, the same open file handles. This sharing is threading's whole point — it lets multiple lines of execution genuinely collaborate on the same data without the overhead or complexity of the inter-process communication techniques (Chapter 13 touches on this) that separate processes would need to coordinate at all.

### Thread scheduling

The operating system's **scheduler** decides which thread actually gets CPU time at any given moment, switching between them rapidly (on a single CPU core, faster than any human could perceive) to create the *appearance* of many things happening simultaneously, even when the hardware genuinely has fewer cores than there are runnable threads. On a machine with multiple CPU cores, the scheduler can additionally run separate threads on separate cores at truly the same physical instant — the exact distinction between concurrency and parallelism the next section covers directly.

### Race conditions

Because threads within one process share memory, two threads reading and writing the same data at the same time without coordination can produce a **race condition** — the final result depends on the unpredictable, essentially arbitrary timing of which thread's operations happen to interleave in which order, rather than on any deterministic logic in the program itself. A race condition is one of the hardest classes of bug to reliably reproduce, precisely because its symptom depends on timing that can vary between runs, machines, and even individual executions of the exact same code — which is exactly the problem the synchronization tools covered later in this chapter exist to prevent.
