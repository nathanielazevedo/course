"Concurrency" and "parallelism" get used interchangeably in casual conversation constantly, and it causes real confusion, because they describe two genuinely different things — one about how a program is *structured*, the other about how it actually *executes* on hardware. Untangling them clears up a lot of confusion in the rest of this chapter.

### Doing multiple things (concurrency)

**Concurrency** is a property of how a program is *structured*: it's dealing with multiple tasks that are in progress during overlapping periods of time, making progress on each by interleaving between them, whether or not any two of them are ever executing at the literal same instant. A single CPU core, switching rapidly between three tasks — running a bit of task A, then task B, then task C, then back to A — is running those tasks *concurrently*, even though, at any single precise moment, only one of them is actually executing.

### Doing multiple things simultaneously (parallelism)

**Parallelism** is a property of *execution*: tasks that are physically running at the exact same instant, which requires genuinely separate hardware resources — multiple CPU cores, or multiple machines — to be true parallelism rather than just very fast switching that merely looks simultaneous from a human's perspective.

### Why the distinction matters

Concurrency is about *dealing with* multiple things; parallelism is about *doing* multiple things at literally the same moment. A single-core machine can absolutely be concurrent (rapidly switching between many tasks) while never being parallel (only one instruction genuinely executes at any given instant). A multi-core machine can be both: concurrent in how a program is structured, and parallel in how the hardware actually executes multiple threads of it simultaneously across separate cores. It's entirely possible — and common — to write concurrent code that never actually runs in parallel (a single-threaded event loop, covered later in this chapter, structures many tasks concurrently on exactly one thread) and equally possible to run genuinely parallel code that isn't concurrently *structured* in any interesting way at all (running the exact same independent calculation simultaneously across many cores, with no interleaving or coordination between the instances needed).

### A concrete example

Imagine a single chef (one CPU core) cooking three dishes by working on whichever one needs attention at each moment — stirring dish A while dish B simmers, then checking on dish C while dish A rests — genuinely making progress on all three "concurrently," despite doing only one physical action at any instant. Now imagine three separate chefs (multiple CPU cores), each cooking one dish independently and simultaneously — that's parallelism. A restaurant kitchen with three chefs, each juggling several dishes concurrently among themselves, is running both concurrently *and* in parallel at once — which is exactly the situation most real, modern multi-threaded software finds itself in on typical multi-core hardware.

### Why this matters for language design

This distinction is exactly why some concurrency models (JavaScript's single-threaded event loop, covered later in this chapter) can handle enormous numbers of concurrent tasks — thousands of pending network requests — using just one core, no true parallelism required at all, because most of that "concurrency" is really about efficiently interleaving waiting-on-I/O tasks rather than needing to execute compute-heavy work simultaneously. It's also exactly why other workloads — genuinely CPU-bound computation, like image processing across many files — need real parallelism (multiple cores actually crunching numbers at the same instant) to get faster, and no amount of clever concurrent structuring on a single core will speed that specific kind of work up at all.
