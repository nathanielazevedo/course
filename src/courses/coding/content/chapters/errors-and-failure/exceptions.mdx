Once a runtime error happens, a language needs a way to signal it and let some part of the program respond — deciding whether to recover, log it, or give up entirely. **Exceptions** are the mechanism most mainstream languages use for this, and they work by interrupting normal control flow and unwinding the call stack until something is prepared to handle the problem.

### `throw` and `try`

Code that detects a problem it can't itself resolve **throws** (or **raises**) an exception — a value, usually of a special error type, that signals what went wrong. Code that anticipates a problem wraps the risky operation in a `try` block, which lets it attempt the operation while being ready to respond if it fails:

```python
try:
    result = 10 / user_input
except ZeroDivisionError:
    print("cannot divide by zero")
```

### `catch`

A `catch` block (called `except` in Python) specifies what to do if an exception of a matching type occurs inside the corresponding `try` block. This is the actual recovery logic — logging the error, retrying, falling back to a default value, or re-throwing a different, more meaningful exception for calling code higher up to handle instead.

### `finally`

A `finally` block runs unconditionally after the `try`/`catch`, whether an exception was thrown or not — the standard place to put cleanup code (closing a file, releasing a lock, disconnecting from a database) that absolutely must run regardless of whether the operation succeeded:

```java
FileReader reader = null;
try {
    reader = new FileReader("data.txt");
    process(reader);
} catch (IOException e) {
    log.error("failed to read file", e);
} finally {
    if (reader != null) reader.close();  // always runs
}
```

### Exception propagation

If a `try` block doesn't catch the specific exception that occurs (or if there's no `try` at all around the point of failure), the exception **propagates**: it interrupts the current function immediately, unwinds up to whoever called it, and checks whether *that* code has a matching `catch` — continuing up the call stack (Chapter 5) until either something catches it, or it reaches the very top of the program uncaught, which typically crashes the program and prints a **stack trace**: a record of exactly which functions were active, in what order, at the moment the exception was thrown. This is precisely why a stack trace is so useful for debugging (Chapter 14 covers this directly) — it's a map of the call stack at the exact instant things went wrong.

### The cost of exceptions

Exceptions are convenient — they let error-handling code live far away from where an error actually occurs, without every intermediate function needing to explicitly check for and pass along a failure — but that convenience has a real cost: a function's signature alone doesn't tell you what exceptions it might throw (unless the language enforces this, as Java's checked exceptions attempt to), which makes it easy to forget an error case exists at all until it happens in production. This exact tradeoff — implicit, convenient exceptions versus explicit, visible error handling — is what the next section, on errors as values, takes a completely different position on.
