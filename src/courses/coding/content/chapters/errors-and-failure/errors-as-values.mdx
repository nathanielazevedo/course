Exceptions handle failure by interrupting normal control flow. Go — along with a growing number of languages influenced by it — takes a completely different position: treat an error as an ordinary **value**, returned from a function exactly like any other result, and require the caller to check it explicitly, right where the call happens, rather than letting it silently propagate elsewhere.

### Go's error model

A Go function that can fail returns two values: the actual result, and an `error` — `nil` if nothing went wrong, or a non-nil value describing what did:

```go
func readConfig(path string) (Config, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return Config{}, err
    }
    return parseConfig(data)
}
```

Calling this function forces you to look at both return values — `config, err := readConfig("app.yaml")` — and Go's convention (enforced by tooling and culture, though not the compiler itself) is to check `err` immediately, right after the call, before doing anything else with `config`.

### Explicit error handling

The practical consequence is that error handling is **visible at every call site** — there's no invisible path an error can take through the program; if a function can fail, its return type says so directly, and using its result without checking the error is a decision you make explicitly (even if that decision is, in practice, sometimes wrongly skipped). Compare this to an exception-based function, whose signature gives no hint at all about what it might throw unless the language forces you to declare it.

```go
config, err := readConfig("app.yaml")
if err != nil {
    log.Fatal(err)
}
useConfig(config)
```

### The tradeoff: verbosity for visibility

The obvious cost of this style is repetition — `if err != nil { return err }` (or its equivalent) appears constantly throughout real Go code, since every fallible call needs its own explicit check, and there's no equivalent to an exception silently bubbling several layers up on its own. Go's designers made this tradeoff deliberately: they consider the verbosity worth paying for the guarantee that no error can be silently ignored by accident the way an uncaught, unexpected exception sometimes can be — every possible failure is a value sitting right there in the code, impossible to structurally forget existed the way an undeclared exception can be forgotten.

### Errors as values beyond Go

This isn't unique to Go — it's the same underlying philosophy behind Rust's `Result` type (the next section covers this specifically) and it echoes in patterns like returning `null` or a sentinel value on failure in older C-style code, though those approaches lack the type-level guarantee that the error case has to be handled that Go's and Rust's approaches provide. The core idea connects directly back to Chapter 2's point about how a language represents absence: errors-as-values makes "this operation might not have succeeded" part of the ordinary type of a function's return value, rather than an invisible, separate control-flow path layered on top of it.
