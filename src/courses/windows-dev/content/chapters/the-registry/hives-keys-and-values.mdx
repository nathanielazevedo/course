The previous section introduced hives as the on-disk files behind the registry tree. This section is the map of that tree — the five root keys you'll actually see, which ones are real and which are just convenient views onto another one, and the value types you'll read and write.

### The five HKEYs

| Root key | Abbreviation | What it holds |
|---|---|---|
| `HKEY_LOCAL_MACHINE` | `HKLM` | Machine-wide settings: installed software, drivers, services — applies to every user |
| `HKEY_CURRENT_USER` | `HKCU` | Settings for the currently logged-on user only |
| `HKEY_USERS` | `HKU` | Every loaded user profile's settings, including HKCU's actual backing data |
| `HKEY_CLASSES_ROOT` | `HKCR` | File associations and COM registration — a merged view, not a real hive |
| `HKEY_CURRENT_CONFIG` | `HKCC` | The active hardware profile — a merged view, not a real hive |

Only three of these — `HKLM`, `HKU`, and a fourth, `HKEY_USERS\.DEFAULT`-adjacent construct — map to actual hive files loaded at boot. `HKCU` is not its own hive; it's a per-process view that points at `HKEY_USERS\<your SID>`, swapped automatically depending on which user's token the current process is running under. This matters practically: a service running as `LocalSystem` (Chapter 5) has an `HKCU` that resolves to `LocalSystem`'s profile, not to the interactive user's — a very common source of "the setting is there when I check manually, but the service can't see it," because the developer checked `HKCU` while logged in interactively and the service checks `HKCU` while running as a completely different account.

`HKCR` and `HKCC` are computed, merged views rather than real hives: `HKCR` combines `HKLM\SOFTWARE\Classes` with the current user's `HKCU\SOFTWARE\Classes`, with the per-user entries taking precedence — which is how a per-user file association override can exist without touching machine-wide settings at all.

### Redirection: `WOW6432Node` and the 32-bit/64-bit split

A 32-bit process running on 64-bit Windows sees `HKLM\SOFTWARE` transparently redirected to `HKLM\SOFTWARE\WOW6432Node` for most keys — the OS does this invisibly so 32-bit software doesn't have to know it's running under emulation, and doesn't collide with 64-bit software's registry entries in the same nominal path. This means the *same* registry path can resolve to genuinely different data depending on whether the calling process is 32-bit or 64-bit — a real trap when a 64-bit diagnostic tool is used to inspect settings written by a 32-bit application, or vice versa; the tool has to explicitly request the other view (`RegistryView.Registry32` / `RegistryView.Registry64` in .NET) to see it.

### Value types, and what they map to in C#

| Registry type | .NET representation |
|---|---|
| `REG_SZ` | `string` |
| `REG_EXPAND_SZ` | `string` with unexpanded `%ENV_VAR%` references |
| `REG_DWORD` | `int` |
| `REG_QWORD` | `long` |
| `REG_BINARY` | `byte[]` |
| `REG_MULTI_SZ` | `string[]` |

`REG_EXPAND_SZ` is worth calling out specifically: reading it through the standard API returns the raw, unexpanded string (`%ProgramFiles%\MyApp`) unless you explicitly request expansion — a subtlety the next section's code examples make concrete.
