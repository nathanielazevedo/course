The previous section mentioned that writing to `HKLM` without elevation throws `UnauthorizedAccessException` — for a modern, correctly-manifested app. But plenty of older software written before UAC existed writes to `HKLM` constantly and appears to work fine, non-elevated, on modern Windows. That apparent contradiction is **UAC Registry Virtualization**, a distinct mechanism from the WOW6432Node redirection covered earlier, and worth telling apart clearly since both get called "redirection."

### Two different things both called "redirection"

- **WOW64 redirection** (previous sections) is about **bitness** — a 32-bit process transparently sees a different physical location (`WOW6432Node`) than a 64-bit process asking for the same nominal path. It applies to both reads and writes, for every process running under WOW64, regardless of elevation.
- **UAC Registry Virtualization** is about **compatibility for legacy, non-manifested apps**. It applies only to writes, only under `HKEY_LOCAL_MACHINE\SOFTWARE` (and a couple of other specific locations), and only for processes Windows has judged to be "legacy" — specifically, 32-bit interactive applications with **no application manifest** at all, which pre-date UAC and were never updated to handle it.

### How virtualization actually works

When a qualifying legacy app, running non-elevated, attempts to write under `HKLM\SOFTWARE`, Windows doesn't fail the write — it silently redirects it to a per-user shadow copy under `HKEY_CURRENT_USER\Software\Classes\VirtualStore\MACHINE\SOFTWARE\...`. Subsequent reads from that same app, at that same nominal `HKLM` path, are transparently redirected too, so the app sees its own write reflected back and has no idea anything unusual happened. Other users on the same machine — or the same app running elevated — see the *real*, unvirtualized `HKLM` data, which can be different from what the non-elevated instance believes it wrote.

### Why modern apps opt out automatically

Registry virtualization is intentionally scoped to apps without a manifest, because a manifest is a declaration that the app knows about UAC and has been written to handle it correctly. As soon as an app ships an application manifest — even one that just declares `asInvoker`, the default level covered in Chapter 2 — virtualization turns off for that process entirely, and an unprivileged `HKLM` write goes back to failing normally with `UnauthorizedAccessException`. Every modern .NET app has an implicit or explicit manifest, so virtualization essentially never applies to C# code you write today; it exists purely as a compatibility shim for old, unmanifested native applications.

### Why this section matters even though it won't affect your own code

The practical reason to understand this is diagnosing *other* software's behavior, not writing around it yourself: if a legacy installer or utility appears to "successfully" write a setting to `HKLM` that a different user account or an elevated session can't see, checking `HKCU\Software\Classes\VirtualStore\MACHINE\SOFTWARE\...` for that same path is often exactly where the real data landed. `regedit` shows the "Compatibility" indicator in its view for virtualized keys, which is the fastest way to confirm this is what's happening rather than something being genuinely broken.
