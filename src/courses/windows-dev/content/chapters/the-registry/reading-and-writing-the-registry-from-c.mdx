`Microsoft.Win32.Registry` and `RegistryKey` are the managed API over everything the last two sections described. The API itself is small; the parts worth spending time on are the ones that map directly onto concepts already covered — typed values, redirection, and disposal of the underlying kernel handle.

### Opening a key and reading values

```csharp
using Microsoft.Win32;

using RegistryKey? key = Registry.LocalMachine.OpenSubKey(
    @"SOFTWARE\Contoso\MyApp");

if (key is not null)
{
    string? installPath = key.GetValue("InstallPath") as string;
    int version = (int)(key.GetValue("Version") ?? 0);

    // REG_EXPAND_SZ: request expansion explicitly
    string? expanded = key.GetValue(
        "DataPath",
        defaultValue: null,
        RegistryValueOptions.None) as string; // still unexpanded

    string? autoExpanded = Environment.ExpandEnvironmentVariables(
        key.GetValue("DataPath") as string ?? "");
}
```

`OpenSubKey` returns `null` rather than throwing if the key doesn't exist — a deliberate design that mirrors `TryGetValue`-style APIs elsewhere in .NET, and worth checking explicitly rather than assuming the key is always present, since most real-world causes of a missing key (an app that hasn't been installed, a setting that's never been changed from default) aren't exceptional conditions. `key` itself is a `SafeHandle`-backed `IDisposable`, exactly like the `Process` and `FileStream` handles from earlier chapters — the `using` isn't optional cleanliness, it's releasing a real kernel handle.

### Writing values

```csharp
using RegistryKey key = Registry.CurrentUser.CreateSubKey(
    @"SOFTWARE\Contoso\MyApp"); // creates if missing, opens if present

key.SetValue("InstallPath", @"C:\Program Files\MyApp", RegistryValueKind.String);
key.SetValue("Version", 3, RegistryValueKind.DWord);
key.SetValue("RecentFiles", new[] { "a.txt", "b.txt" }, RegistryValueKind.MultiString);
```

`CreateSubKey` is idempotent — creating an already-existing key just opens it, which makes "ensure this key exists with these values" code straightforward to write without a separate existence check.

### Writing to `HKLM` requires elevation; writing to `HKCU` doesn't

This follows directly from the ACL model in Chapter 3, applied to registry keys instead of files: `HKEY_LOCAL_MACHINE` subkeys are, by default, writable only by administrators, because they affect every user on the machine. `HKEY_CURRENT_USER` subkeys are writable by the owning user without elevation, since they only affect that user's own configuration. Attempting to `SetValue` under `HKLM` from a non-elevated process throws `UnauthorizedAccessException` — the same class of failure as the elevation-dependent process operations from Chapter 2, and subject to the same fix: either the app needs to run elevated, or the setting genuinely belongs under `HKCU` instead of `HKLM`.

### Choosing the right registry view

Following on from the previous section's redirection discussion, `RegistryKey.OpenBaseKey` lets you explicitly pick which view to open, independent of whether your own process is 32-bit or 64-bit:

```csharp
using RegistryKey hklm64 = RegistryKey.OpenBaseKey(
    RegistryHive.LocalMachine, RegistryView.Registry64);
using RegistryKey key = hklm64.OpenSubKey(@"SOFTWARE\Contoso\MyApp");
```

This is the fix for the "64-bit tool can't see a 32-bit app's registry entries" trap: without specifying `RegistryView.Registry64` (or `Registry32`) explicitly, `Registry.LocalMachine` follows whatever redirection applies to the *calling* process's own bitness, not necessarily the bitness of whatever wrote the data you're looking for.

### Watching for changes

Unlike the filesystem, there's no first-party `RegistryWatcher` in the BCL. Watching a key for changes requires P/Invoke against `RegNotifyChangeKeyValue` (Chapter 6) — a real gap compared to `FileSystemWatcher`, and part of why registry-based configuration is more commonly read once at startup than watched live for changes in typical application code.
