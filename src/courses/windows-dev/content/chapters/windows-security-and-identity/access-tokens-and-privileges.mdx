Chapter 2 introduced access tokens in passing — the thing a process holds that decides who it's running as, and the split-token mechanism behind UAC. This section is the token itself, in enough detail to make sense of the privileges it carries and how they differ from the ACL-based access rights covered elsewhere in this chapter.

### What an access token actually contains

An access token is a kernel object (Chapter 1's object model, again) attached to every process and thread, holding: the user's SID, every group SID that user belongs to (the previous section's mechanism), a list of enabled and disabled **privileges**, and an integrity level (covered below). Every process gets a **primary token** at creation, inherited from whatever created it — which is the same inheritance mechanism Chapter 2 described for elevation: a child process's primary token comes from its parent, not independently negotiated at each launch.

### Rights vs. privileges: two different security concepts with similar names

This distinction trips up a lot of developers because the vocabulary is so close: an **access right** (Chapter 3's ACLs, generalized to registry keys and other object types in this chapter) is *object-specific* — read access to *this* file, write access to *that* registry key, checked against a specific object's DACL. A **privilege** is *system-wide* — a capability that isn't about any single object at all, like `SeDebugPrivilege` (attach a debugger to any process, including ones you don't otherwise have access rights to), `SeShutdownPrivilege` (shut down the machine), or `SeBackupPrivilege` (read any file for backup purposes, bypassing its normal ACL entirely). Privileges are assigned to accounts through Local Security Policy or Group Policy, carried in the token as a list, and each one can be independently enabled or disabled within a token that holds it — holding a privilege and having it currently *enabled* are genuinely different states.

### Checking and enabling privileges from C#

```csharp
using System.Security.Principal;

var identity = WindowsIdentity.GetCurrent();
bool hasDebugPrivilege = identity.Claims.Any(
    c => c.Type == "http://schemas.microsoft.com/ws/2008/06/identity/claims/primarysid");
```

In practice, checking and toggling specific privileges (`SeDebugPrivilege` and similar) isn't well covered by the managed BCL at all — this is P/Invoke territory (Chapter 6) against `LookupPrivilegeValue`, `AdjustTokenPrivileges`, and `OpenProcessToken`. The shape is: open a handle to your own process's token, look up the privilege's numeric LUID by name, then explicitly enable it in the token before the operation that needs it — a privilege being present but *disabled* in the token is a common, confusing failure mode, since the process technically "has" the privilege (an administrator account is typically granted `SeDebugPrivilege`) but the specific operation still fails until it's been explicitly turned on for that token.

### Integrity levels: a second, independent axis of restriction

Beyond the user/group/privilege model, Windows (since Vista) layers **mandatory integrity control** on top: every process and securable object also carries an integrity level — `Low`, `Medium` (the default for most user processes), `High` (elevated processes), `System`. The rule is simple and one-directional: a process cannot write to an object with a higher integrity level than its own, regardless of what its DACL would otherwise allow. This is the actual mechanism behind sandboxing a browser's renderer process at `Low` integrity — even if the renderer somehow obtained a handle to a file the user's own account has full DACL permissions on, the integrity-level check blocks the write independently, a second, structurally separate line of defense from the ACL check covered next.
