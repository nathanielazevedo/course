Every mechanism so far in this chapter has answered "what is this identity allowed to do." This closing section answers a different question that sits in front of all of them: "is this piece of code actually what it claims to be, and should the system trust it at all before any of those permission checks even become relevant."

### What a code signature actually proves

Authenticode, Windows' code-signing system, attaches a digital signature to an executable or driver, computed from a cryptographic hash of the file's contents and signed with a certificate issued by a trusted Certificate Authority. It proves two specific, narrow things: **integrity** — the file hasn't been modified since it was signed, because any change would invalidate the hash — and **authenticity** — the signature was produced by whoever holds the private key for that certificate, whose identity the CA has (in theory) verified before issuing it. It does **not** prove the code is safe, well-written, or free of vulnerabilities; a legitimately signed piece of malware is still legitimately signed. Signature verification is a trust-and-tampering check, not a code-quality or intent check.

### Where this shows up for a C# developer

- **SmartScreen and "Unknown Publisher" warnings.** An unsigned or newly-signed executable downloaded from the internet triggers SmartScreen's reputation-based warning; a signature from a well-established certificate (with enough accumulated reputation) suppresses it. This is why a from-scratch installer, even one signed with a brand-new valid certificate, can still show a warning the first while — reputation is built over time and volume of installs, not granted instantly by having a valid signature at all.
- **Driver signing enforcement.** Modern 64-bit Windows refuses to load an unsigned kernel-mode driver at all under normal boot conditions — a hard requirement, not a warning, closing off a large historical malware vector (kernel drivers run with the highest possible trust).
- **AppLocker and WDAC.** Enterprise environments increasingly use publisher-based rules — "only run code signed by these specific certificates" — as an application allowlisting mechanism, which is a direct, practical use of everything this section covers: the signature is what the allowlist rule actually matches against.
- **The Mark of the Web.** A file downloaded from the internet gets tagged (via the Alternate Data Stream mechanism from Chapter 3) with its origin zone; Windows treats that file with extra caution — a security warning on open, or the SmartScreen check above — until that tag is explicitly cleared, independent of whether the file happens to be signed at all.

### Verifying a signature from C#

```csharp
using System.Security.Cryptography.X509Certificates;

X509Certificate2 cert = X509Certificate2.CreateFromSignedFile(path);
bool trusted = cert.Verify(); // checks the cert chain, revocation, and expiry
Console.WriteLine(cert.Subject);
```

`X509Certificate2.Verify()` walks the certificate chain up to a trusted root, checks it hasn't expired, and (network permitting) checks revocation status — an expired or revoked signing certificate fails verification even if the file's hash still matches exactly what was originally signed, which is a deliberate design choice: trust in a certificate is a point-in-time judgment the issuing CA can later retract.

### Signing your own application

For a .NET app you're shipping, signing is generally a build/deployment-pipeline step rather than something the application itself does at runtime — `signtool.exe` (part of the Windows SDK from Chapter 1's setup checklist) is the standard tool, typically invoked from CI against a certificate stored in a hardware security module or a cloud-based signing service rather than a plain file on disk, precisely because a leaked signing private key lets an attacker produce malware that passes every check this section describes as if it were legitimately yours.
