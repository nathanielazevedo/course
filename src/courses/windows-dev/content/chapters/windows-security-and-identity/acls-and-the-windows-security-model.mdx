Chapter 3 covered file DACLs in practical depth — ACEs, Allow vs. Deny, inheritance, ownership. Everything in that section generalizes to any securable Windows object — registry keys, services, processes, even the access token itself — because they all share one underlying structure: the **security descriptor**. This section is that unifying picture, plus the piece Chapter 3 didn't cover: auditing.

### The security descriptor: one structure behind every ACL check

Every securable object in Windows — files, registry keys, processes, services, kernel synchronization objects — carries a **security descriptor** with four parts: the owner SID, the primary group SID (largely a POSIX-subsystem legacy field on modern Windows, rarely meaningful in pure Windows workflows), a **DACL** (Discretionary Access Control List — the permissions covered in Chapter 3), and a **SACL** (System Access Control List — who gets *audited*, covered below). This is why `System.Security.AccessControl` has parallel types for different object kinds — `FileSecurity`, `RegistrySecurity`, `EventWaitHandleSecurity` — that all share the same conceptual shape and the same base classes, because they're all reading and writing the same kind of structure, just attached to a different object type.

### The SACL: auditing, not access control

Where the DACL decides *whether* an access succeeds, the SACL decides *whether that access gets logged* — an entirely separate list of entries, each specifying which operations by which principals should generate a security audit event, success, failure, or both. A SACL entry granting no one any access rights and a DACL entry granting the same are structurally identical ACE lists, but mean opposite things depending on which list they're in. Reading or writing a SACL itself requires `SeSecurityPrivilege`, distinct from the rights needed to read or write the DACL — a deliberate separation, since the ability to see or tamper with what's being audited is treated as more sensitive than the ability to manage ordinary access.

```csharp
// System.Security.AccessControl exposes SACL access analogously to DACL access
FileSecurity security = fileInfo.GetAccessControl(AccessControlSections.Audit);
security.AddAuditRule(new FileSystemAuditRule(
    "DOMAIN\\someuser",
    FileSystemRights.Write,
    AuditFlags.Success | AuditFlags.Failure));
```

Audit events generated this way land in the Security log, which Chapter 9's Event Log coverage picks up directly.

### The access check, as a single algorithm

Pulling together Chapter 3's file-specific rules and this chapter's tokens and integrity levels, an access check against any securable object follows roughly this order: first, the integrity-level check from the previous section (write access to a higher-integrity object is refused outright, before the DACL is even consulted); then the DACL is walked in order, and the first ACE that matches one of the caller's token SIDs — user or any group — for the requested right decides the outcome, Deny ACEs generally ordered ahead of Allow ACEs at the same specificity level (Chapter 3); if no ACE matches at all, access is denied by default — there's no implicit "allow if nothing says otherwise."

### Why this matters beyond files

Once this structure is recognized as generic, plenty of earlier chapters snap into a clearer picture: a service's SCM registration (Chapter 5) has its own security descriptor controlling who can start, stop, or reconfigure it, independent of the file ACL on its executable; a named pipe or a named mutex (Chapter 10) has one too, controlling who else can open a handle to it at all. "Can process A see/touch object B" is, structurally, the same question and the same mechanism no matter what kind of object B actually is.
