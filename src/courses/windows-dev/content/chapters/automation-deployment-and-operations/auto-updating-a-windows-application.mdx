Getting an application installed once, as the previous section covered, is half the deployment problem. This section is the other half: getting it to stay current on machines you no longer have direct access to, without asking a human to manually reinstall it — and the meaningfully different amount of work that takes depending on which packaging path the previous section led you down.

### MSIX: updating is mostly the platform's job

Chapter 8 already established that MSIX absorbs update-checking into the platform rather than leaving it to each app. For a Store-distributed MSIX app, this is close to zero-effort: the Microsoft Store checks for and applies updates on its own schedule, entirely outside the application's own code. For MSIX distributed outside the Store, an **App Installer** file (`.appinstaller`) declares an update source URL and check interval; Windows itself periodically checks that URL and applies newer packages it finds, again without the application needing to implement any update logic of its own — the closest thing in the Windows ecosystem to "update logic you don't have to write."

### MSI and plain executables: you're building this yourself

Everything MSIX gives you for free, an MSI-based or plain-executable-based app has to build: a way to check for a new version, a way to download it, and a way to actually replace running files — which is a genuinely awkward problem on Windows specifically, tying back to Chapter 3's file-locking model: a running executable's own file is locked while the process is executing, so an update mechanism can't simply overwrite `MyApp.exe` while `MyApp.exe` is the thing doing the overwriting.

### The standard pattern: a separate updater process

```csharp
// Running app detects an update is available, then:
var psi = new ProcessStartInfo("Updater.exe", $"--target \"{Environment.ProcessPath}\"")
{
    UseShellExecute = true,
};
Process.Start(psi);
Environment.Exit(0); // release the file lock on our own executable by exiting
```

The updater — a separate, small executable whose own file isn't the one being replaced — waits for the main process to actually exit (Chapter 2's process lifecycle: it can poll `Process.GetProcessById` or simply wait a moment after launching, since the main app calls `Environment.Exit` right after spawning it), then downloads and swaps the new files into place, then relaunches the main application. This two-process handoff — one process to detect and trigger, a separate process to actually perform the file replacement — is the standard shape almost every non-MSIX Windows auto-updater takes, precisely because no single process can replace its own running executable file directly.

### Established libraries, rather than hand-rolling this

Squirrel.Windows and Velopack (its actively maintained modern successor) are the commonly used open-source libraries that implement this pattern — delta updates (downloading only what changed between versions rather than the full package each time), atomic installation (the swap either fully completes or doesn't happen at all, avoiding a half-updated app), and the separate-updater-process handoff described above, all handled by the library rather than hand-rolled per application. For a plain-executable or MSI-distributed app, reaching for one of these is almost always a better use of time than re-implementing file-locking-aware update logic from scratch — this is exactly the kind of previously bespoke, error-prone code Chapter 8 described MSIX as absorbing into the platform, available here as a well-tested library instead for apps that aren't packaged as MSIX.

### Signing matters here too

Chapter 7's code-signing coverage applies directly to update packages, not just the original install: an update mechanism that downloads and executes a new version without verifying its signature is a direct code-execution vector for anyone who can intercept or spoof the update download — verifying the downloaded update's Authenticode signature (or, at minimum, its hash against a signed manifest) before replacing the running application's files is not an optional hardening step, it's the difference between an update mechanism and an unauthenticated remote code execution mechanism with a friendlier name.
