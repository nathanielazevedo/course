This final section of the course pulls together nearly everything covered so far into the pipeline that actually ships it: building, testing, packaging, signing, and deploying a C# Windows application automatically, on every change, rather than as a sequence of manual steps someone has to remember and execute correctly by hand.

### Why Windows CI specifically needs a Windows build agent

Chapter 1 established that Windows-specific APIs (Registry, WMI, WinForms/WPF/WinUI, COM interop) are only available when actually running on Windows — `net8.0-windows`-targeted code and anything depending on it genuinely will not build or run correctly on a Linux CI agent, unlike plain `net8.0` cross-platform code. GitHub Actions' `windows-latest` runner, Azure DevOps' `windows-latest` pool, or a self-hosted Windows build agent are the practical options — this single requirement is why "just use whatever CI runner is cheapest" isn't a safe default for this course's subject matter the way it might be for a purely cross-platform .NET library.

```yaml
# GitHub Actions, abbreviated
jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - run: dotnet build -c Release
      - run: dotnet test -c Release
```

### What a complete pipeline actually chains together

Pulling directly from this chapter's earlier sections: build and run tests, produce the installer artifact (WiX/MSI or MSIX packaging, from two sections ago) as a build output rather than a manual step, sign both the application binaries and the installer package (Chapter 7's code-signing coverage, applied here as an automated pipeline step against a certificate held in a secrets manager or HSM rather than a developer's own machine), and publish the signed, versioned artifact somewhere the update mechanism (previous section) or an installation process (Chapter 5's service registration included) can actually reach it.

```yaml
      - run: wix build Product.wxs -o dist/MyApp.msi
      - name: Sign
        run: signtool sign /fd sha256 /tr http://timestamp.digicert.com /td sha256 `
             /f $env:CERT_PATH /p $env:CERT_PASSWORD dist/MyApp.msi
        env:
          CERT_PATH: ${{ secrets.SIGNING_CERT_PATH }}
          CERT_PASSWORD: ${{ secrets.SIGNING_CERT_PASSWORD }}
```

The `/tr` timestamp server flag matters specifically because of Chapter 7's certificate-expiry point: a **timestamped** signature remains valid after the signing certificate itself expires, because the timestamp proves the signature was created while the certificate was still valid — an unsigned-by-timestamp build can appear to "break" (fail signature verification) months later purely because the certificate used to sign it has since expired, even though nothing about the binary itself changed.

### Testing what's genuinely hard to test without a real Windows environment

Some of what this course covered resists ordinary unit testing precisely because it depends on real OS state: Windows Service installation and lifecycle (Chapter 5), actual registry writes (Chapter 4), or file ACL behavior (Chapter 3) are all more honestly tested as integration tests running on a real (or real-enough, like a Windows container) environment than mocked out entirely — a unit test asserting your code *calls* `RegistryKey.SetValue` correctly is weaker evidence than an integration test that actually writes a real key in an isolated test hive and reads it back, precisely because so much of this course's subject matter is "does the OS actually behave the way the documentation says," not just "does your code call the right method."

### Deployment: pushing the artifact to where it needs to run

The last mile differs by what's being shipped: a desktop app's signed installer or MSIX package gets uploaded to a release page, an internal distribution point, or the Microsoft Store; a Windows Service's deployment (building on Chapter 5's installation steps) typically means copying the published output to the target machine and running `sc.exe create`/`Update-Service`-equivalent commands remotely — via PowerShell remoting (this chapter's first section, extended across machines) or a dedicated deployment tool — rather than manually logging into each server. The specific mechanics vary by organization and scale, but the throughline across this entire final chapter, and really the entire course, holds: nearly everything Windows-specific this course covered — services, the registry, ACLs, signing, the Task Scheduler, IPC — is something real production software automates end to end, not something a person does by hand on each machine, one at a time, hoping to remember every step correctly.
