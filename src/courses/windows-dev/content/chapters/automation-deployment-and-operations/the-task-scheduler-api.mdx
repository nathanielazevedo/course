Chapter 4 mentioned the Task Scheduler as the more capable alternative to a `Run` registry key, and Chapter 5 positioned it alongside Windows Services as the right tool for per-user, logon-scoped background work. This section is that tool in full — what it can trigger on, and how to drive it from C#.

### What Task Scheduler adds beyond "run this at logon"

A `Run` key entry (Chapter 4) does exactly one thing: launch a program when a user logs on. Task Scheduler generalizes that into a genuine trigger-and-action system: **triggers** far beyond logon — a specific time, a recurring schedule, system startup, a specific Event Log entry appearing (tying directly back to Chapter 9), the machine going idle, a network connection becoming available — combined with **actions** beyond just "start this program" (though that remains the most common one), constrained by **conditions** (only run on AC power, only run if a specific network is available) and **settings** (retry on failure, stop if it runs too long, run with highest privileges).

### Creating a scheduled task from C#

The Task Scheduler has a COM-based API underneath (`Microsoft.Win32.TaskScheduler`, a popular open-source wrapper, is the practical entry point most C# code actually uses rather than driving the raw COM interfaces directly — itself a real-world instance of Chapter 6's COM interop, wrapped for convenience the way `System.Management`'s WMI wrapper does for that COM surface):

```csharp
using Microsoft.Win32.TaskScheduler;

using TaskService ts = TaskService.Instance;
TaskDefinition td = ts.NewTask();
td.RegistrationInfo.Description = "Nightly cleanup";
td.Triggers.Add(new DailyTrigger { StartBoundary = DateTime.Today.AddHours(2) });
td.Actions.Add(new ExecAction("C:\\Tools\\Cleanup.exe", "--verbose"));
td.Settings.StopIfGoingOnBatteries = false;

ts.RootFolder.RegisterTaskDefinition("NightlyCleanup", td);
```

This registers a task that behaves exactly like one created through the Task Scheduler GUI or `schtasks.exe` — all three are, structurally, driving the same underlying COM/XML task definition, the same "multiple tools, one real underlying store" pattern Chapter 5 established for the SCM and Chapter 4 established for the registry.

### Running with elevated privileges — declaratively, not through a UAC prompt

```csharp
td.Principal.RunLevel = TaskRunLevel.Highest;
td.Principal.LogonType = TaskLogonType.ServiceAccount;
td.Principal.UserId = "SYSTEM";
```

This is a genuinely different elevation path than Chapter 2's `Verb = "runas"` — a scheduled task configured to run as `SYSTEM` or with `Highest` run level launches already elevated, with no UAC consent prompt at execution time at all, because the elevation decision was made (and requires administrator rights to configure) when the task was *registered*, not when it *runs*. This is exactly why Task Scheduler is a common vector for legitimately running unattended, elevated automation — a nightly maintenance script that needs administrator rights but has no interactive user present at 2 a.m. to click "Yes" on a UAC prompt — and, less legitimately, a technique malware and privilege-escalation attacks have historically abused for the same "elevated code, no prompt" property, worth being aware of specifically because it means scheduled task creation (and the registry key backing it, `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache`) is itself a security-relevant surface worth restricting who can write to.

### Task Scheduler vs. Windows Service, revisited concretely

Chapter 5 covered this at a conceptual level; with the mechanics now in view, the practical distinction sharpens: a scheduled task is fundamentally about *triggering a run* — start, execute, finish, possibly on a recurring schedule — while a service is about a *continuously running process* the SCM keeps alive and restarts on failure (Chapter 5's recovery options). A nightly report generator, a periodic cleanup job, or a one-time post-deployment step fits Task Scheduler's model naturally; a process that needs to be up and responsive continuously, listening on a port or a named pipe (this chapter's earlier sections), needs the service model instead — Task Scheduler has no equivalent to "restart this if it crashes while it's supposed to be idling and waiting."
