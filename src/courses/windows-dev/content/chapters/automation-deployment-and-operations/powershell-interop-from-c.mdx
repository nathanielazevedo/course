This closing chapter is about the last mile from "code that works" to "code that's actually running, deployed, and maintained on real machines." It starts here, with PowerShell — because a genuinely large amount of Windows automation, deployment tooling, and operational scripting is PowerShell, and knowing how C# and PowerShell actually relate (rather than treating PowerShell as just "another CLI to shell out to") opens up a more direct, more capable path.

### PowerShell is built on .NET — this isn't a coincidence

PowerShell (specifically PowerShell 7+, the modern, cross-platform, open-source line, as distinct from the legacy Windows PowerShell 5.1 built into every Windows install) is itself a .NET application, and its object pipeline passes real .NET objects between cmdlets, not text — a `Get-Process` result is a genuine `System.Diagnostics.Process`-adjacent object, not a text table parsed after the fact the way piping between Unix shell commands typically works. This is why PowerShell and C# interop cleanly in both directions: C# can host and drive PowerShell directly through the `System.Management.Automation` API, and PowerShell can load and call directly into any .NET assembly, including one you wrote yourself.

### Shelling out to `pwsh.exe`: the simple, lossy option

```csharp
var psi = new ProcessStartInfo("pwsh", "-NoProfile -Command \"Get-Service -Name Spooler\"")
{
    RedirectStandardOutput = true,
    UseShellExecute = false,
};
using var process = Process.Start(psi)!;
string output = await process.StandardOutput.ReadToEndAsync();
```

This is the Chapter 2 `Process` pattern, applied to launching PowerShell as a subprocess — straightforward, but lossy in exactly the way piping between two separate processes always is: the rich `.NET` objects PowerShell's pipeline uses internally get serialized to text for the redirected output, and parsing that text back into structured data in C# is real, brittle work (`ConvertTo-Json` on the PowerShell side helps, but it's still a serialization round-trip you're managing yourself).

### Hosting PowerShell directly: the richer option

```csharp
using System.Management.Automation;

using var ps = PowerShell.Create();
ps.AddCommand("Get-Service").AddParameter("Name", "Spooler");
Collection<PSObject> results = ps.Invoke();

foreach (PSObject result in results)
{
    var status = result.Properties["Status"]?.Value;
    Console.WriteLine($"Spooler status: {status}");
}
```

`System.Management.Automation` (the `Microsoft.PowerShell.SDK` NuGet package) runs PowerShell **in-process** rather than as a subprocess — no serialization round-trip, no text parsing, direct access to the same `PSObject` results a PowerShell script itself would see, with each property accessible by name rather than reconstructed from formatted text output. This is the right tool when a C# application needs to run PowerShell logic as a genuine, structured part of its own execution — an installer or management tool that needs to call cmdlets from modules like `ActiveDirectory` or `AzureAD` that have no direct C# equivalent, for instance, without paying the subprocess-and-text-parsing cost of shelling out.

### Calling C# from PowerShell: the reverse direction

```powershell
Add-Type -Path "C:\Tools\MyLibrary.dll"
[Contoso.MyLibrary.Helpers]::DoSomething()
```

`Add-Type` loads a .NET assembly directly into the running PowerShell process, after which any public type is callable exactly as shown — this is how a good deal of real-world Windows deployment and automation tooling is actually built: PowerShell scripts as the orchestration layer, calling into purpose-built C# libraries for anything that's more naturally expressed as compiled code (complex parsing, performance-sensitive work, P/Invoke-heavy Win32 interaction from Chapter 6) than as script.

### Writing a PowerShell cmdlet in C#

For the deepest integration, a C# class can *be* a cmdlet, not just something a script calls:

```csharp
[Cmdlet(VerbsCommon.Get, "ContosoStatus")]
public class GetContosoStatusCmdlet : PSCmdlet
{
    protected override void ProcessRecord()
    {
        WriteObject(new { Status = "Running", Uptime = TimeSpan.FromHours(3) });
    }
}
```

Packaged into a PowerShell module (a `.psd1` manifest referencing the compiled assembly), `Get-ContosoStatus` then behaves as a first-class cmdlet indistinguishable from a built-in one — participating fully in the pipeline, tab completion, and help system — which is the standard approach for shipping genuinely reusable Windows management tooling rather than a one-off script.
