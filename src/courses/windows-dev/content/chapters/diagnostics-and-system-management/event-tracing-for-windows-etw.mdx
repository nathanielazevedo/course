The Event Log is built for discrete, relatively infrequent, human-relevant occurrences — a service started, a connection failed. **ETW (Event Tracing for Windows)** solves a different problem: extremely high-volume, low-overhead tracing capable of capturing what's happening inside the OS and applications at a rate the Event Log was never designed for, without meaningfully slowing anything down.

### Why ETW exists as a separate system

ETW is the mechanism behind capturing tens of thousands of events per second — every disk I/O, every context switch, every .NET GC — with overhead low enough to run in production, all the time, on live systems, which the Event Log's structured-database-write model simply isn't built for. The core design that makes this possible: **providers** write events, but only if a **session** has actually enabled that provider and is actively listening — an ETW provider call in code that has no active session listening is a cheap, near-zero-cost check-and-return, not a write. This is fundamentally different from the Event Log, where a `log.WriteEntry` call always performs the write, listener or not.

### The .NET runtime is itself a rich ETW provider

Everything the CLR does internally — garbage collections, JIT compilation events, exceptions thrown, thread pool activity — is instrumented as ETW events under the `Microsoft-Windows-DotNETRuntime` provider, entirely independent of anything an application developer writes. This is genuinely useful without any code changes at all: capturing a trace with a tool like **PerfView** against a running .NET process (no code changes, no restart required — a session can attach live) surfaces GC pause times, allocation rates, and JIT overhead directly, which is a much deeper and more accurate picture than instrumenting the same information by hand with a stopwatch and log statements.

### Writing your own ETW events from C#

```csharp
using System.Diagnostics.Tracing;

[EventSource(Name = "Contoso-MyApp")]
public sealed class MyAppEventSource : EventSource
{
    public static readonly MyAppEventSource Log = new();

    [Event(1, Level = EventLevel.Informational)]
    public void RequestStarted(string requestId) => WriteEvent(1, requestId);

    [Event(2, Level = EventLevel.Error)]
    public void RequestFailed(string requestId, string error) => WriteEvent(2, requestId, error);
}

// Elsewhere in the app:
MyAppEventSource.Log.RequestStarted(requestId);
```

`EventSource` is .NET's managed wrapper for defining a custom ETW provider — `RequestStarted` and `RequestFailed` above become real, independently-enabled ETW events, filterable and collectible with the exact same tools used for the CLR's own built-in provider, without needing a session actively listening to pay any meaningful cost when no one's collecting.

### Capturing and reading traces

`dotnet-trace` (a .NET global tool) is the modern, cross-platform-friendly way to capture a trace from a running .NET process without needing PerfView's full Windows-specific tooling:

```bash
dotnet-trace collect --process-id <pid> --providers Contoso-MyApp
```

The resulting `.nettrace` file (or a converted `.etl` for Windows-specific tools) can be opened in PerfView, Visual Studio's diagnostic tools, or analyzed programmatically — the same underlying ETW data, read through whichever tool best fits the question being asked.
