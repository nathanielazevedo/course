Chapter 5 mentioned the Event Log as where a service's diagnostics belong once there's no console to write to. This section is that mechanism in full — the actual structure behind `builder.Logging.AddEventLog()`, and why it's the right home for durable, queryable diagnostic history rather than just "another place logs can go."

### Not a text file — a structured, queryable store

Unlike a rolling text log file, the Windows Event Log is a structured database (backed by `.evtx` files, but not meant to be read as plain text) where every entry carries a source, a level (Information, Warning, Error, Critical), a numeric event ID, a timestamp, and structured data fields — not just a free-text message string. This structure is what makes Event Viewer's filtering genuinely useful ("show me every Error from this source in the last 24 hours") rather than a `grep` over a text file, and it's what lets other tools (Chapter 9's later sections, monitoring agents, SIEM ingestion pipelines) query it programmatically without parsing free text at all.

### Logs and sources: where an event actually lands

Events are organized into named **logs** — `Application`, `System`, `Security` (the SACL-driven audit destination from Chapter 7), and any number of custom logs an application can register — and within a log, tagged with a **source**, the string identifying which component wrote the entry (your app's name, typically). Writing to the Security log requires the `SeAuditPrivilege`-gated path most application code never touches directly (Chapter 7's audit mechanism handles that); ordinary application diagnostics belong in `Application` or, for a component significant enough to warrant it, a custom log created specifically for that purpose.

```csharp
using System.Diagnostics;

if (!EventLog.SourceExists("MyService"))
    EventLog.CreateEventSource("MyService", "Application"); // requires admin rights, one-time setup

using var log = new EventLog("Application") { Source = "MyService" };
log.WriteEntry("Startup completed.", EventLogEntryType.Information, eventId: 1000);
log.WriteEntry("Failed to connect to database.", EventLogEntryType.Error, eventId: 5000);
```

`CreateEventSource` needs to run once, with administrator rights, typically as part of installation rather than at every application startup — attempting it repeatedly from an unprivileged running instance is a common source of confusing `UnauthorizedAccessException`s in code that assumes it can always self-register its own source.

### `ILogger` and the Event Log: the same sink Chapter 5 introduced

```csharp
var builder = Host.CreateApplicationBuilder(args);
builder.Logging.AddEventLog(settings =>
{
    settings.SourceName = "MyService";
});
```

Once wired up this way, ordinary `ILogger<T>` calls throughout the application — `_logger.LogWarning(...)`, `_logger.LogError(exception, ...)` — are automatically written to the Event Log with an appropriate severity mapping (`LogError` becomes `EventLogEntryType.Error`, and so on), with no separate `EventLog` object management needed anywhere else in the application's code. This is the practical reason to prefer `ILogger` over a raw `EventLog` instance directly: the same logging calls can simultaneously feed the Event Log, the console (during interactive `dotnet run` testing, per Chapter 5), and any other configured sink, from one consistent API.

### Reading events back

```csharp
using var log = new EventLog("Application");
foreach (EventLogEntry entry in log.Entries.Cast<EventLogEntry>().TakeLast(20))
{
    Console.WriteLine($"{entry.TimeGenerated} [{entry.EntryType}] {entry.Source}: {entry.Message}");
}
```

For anything beyond casual inspection, `Microsoft.Extensions.Logging`'s `EventLog` reading is thin — `wevtutil.exe` (query with structured XPath-like filters) or PowerShell's `Get-WinEvent` are the more capable tools for real querying, and the ones worth reaching for when diagnosing a problem interactively rather than iterating `EventLogEntry` objects in code.
