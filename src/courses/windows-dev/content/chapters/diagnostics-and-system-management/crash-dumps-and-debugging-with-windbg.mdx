Every mechanism so far in this chapter assumes the process is still running to observe. This closing section is for the case none of them cover: the process already crashed, and whatever happened is gone unless it was captured at the moment of failure — which is exactly what a **crash dump** is for.

### What a crash dump actually captures

A crash dump is a snapshot of a process's memory at a specific moment — typically the instant it crashed — written to a `.dmp` file. Windows Error Reporting (WER) can be configured to generate one automatically whenever a process crashes unhandled, without any code in the application itself requesting it:

```
HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps
DumpType (REG_DWORD) = 2   ; 2 = full dump, 1 = mini dump
DumpFolder (REG_SZ)  = C:\Dumps
```

This registry configuration (Chapter 4's mechanisms, applied to a genuinely practical operational use) is a common production setup: crashes on a server that has no one watching it interactively still leave behind a file that can be analyzed after the fact, rather than the failure simply vanishing along with the terminated process.

### Mini dumps vs. full dumps: what tradeoff the DumpType controls

A **mini dump** captures the essentials — thread stacks, loaded module list, exception information — small (typically kilobytes to low megabytes) and fast to generate, sufficient for diagnosing the large majority of crashes where the immediate call stack tells you what went wrong. A **full dump** captures the entire process address space, potentially gigabytes for a large application, letting you inspect the actual contents of any object, any local variable, any field, at the cost of size and the sensitive-data exposure that implies (a full dump of a process handling user data or credentials genuinely contains that data in plain, inspectable form — treating dump files with the same care as the data the process itself handles is not optional). The practical default: mini dumps for routine crash triage, full dumps reserved for the harder cases where a stack trace alone doesn't explain the failure and inspecting actual object state is necessary.

### Opening a dump in WinDbg

WinDbg (part of the Windows SDK from Chapter 1's setup checklist, or available as `WinDbg Preview` from the Microsoft Store) is the standard tool for actually analyzing a dump. For managed .NET crashes specifically, the **SOS** debugging extension (`.loadby sos coreclr` in modern .NET) is what makes WinDbg — a tool that natively understands native stacks and modules — able to walk managed stacks, inspect managed objects, and understand the CLR's own internal state:

```
0:000> .loadby sos coreclr
0:000> !clrstack          # managed call stack for the current thread
0:000> !dumpheap -stat     # summary of every managed object type on the heap
0:000> !pe                 # print exception details for the current exception
```

`!clrstack` is usually the first command run against a crash dump — it answers "where in managed code was this thread when it died," the direct managed equivalent of a native stack trace, and often enough on its own to diagnose the crash without needing to go further into heap inspection.

### `dotnet-dump`: capturing and analyzing without WinDbg at all

For .NET specifically, `dotnet-dump` (another global tool, sibling to `dotnet-trace` and `dotnet-counters` from earlier sections) can both capture a dump from a live process on demand and provide its own SOS-powered analysis interface, cross-platform, without requiring WinDbg or even a Windows-only environment for the analysis step:

```bash
dotnet-dump collect --process-id <pid>
dotnet-dump analyze core_20240101_120000
> clrstack
> dumpheap -stat
```

This is genuinely useful beyond crash-after-the-fact analysis too — `dotnet-dump collect` can capture a dump of a process that's still running but behaving badly (hung, leaking memory) for later analysis, without having to wait for or force an actual crash first.
