Chapter 1 introduced the idea that Windows was built assuming an interactive user at a graphical console. A Windows Service is the answer to the obvious follow-up question: what runs the things that need to run *without* a user logged in at all — before anyone signs in, after everyone signs out, or on a machine with no one signed in, ever?

### A process with no desktop, managed by the OS itself

A service is, underneath, an ordinary process — but one started by the OS itself (specifically, the Service Control Manager, next section) rather than by a logged-in user double-clicking something, and one that by default runs with **no desktop, no window station, and no interactive session** attached to it at all. This isn't a permissions restriction you can lift; it's a structural fact about how services are launched. Code that assumes it can show a message box or read `Console.ReadLine()` will not work as a service — there is no console or desktop for that code to attach to (Session 0 isolation, covered next, is the specific mechanism behind this).

### Why services exist instead of just "run at startup"

Chapter 4 covered the `Run` registry key as a way to launch something at logon. A service solves a different, harder problem: something that must be running **before any user logs in** (network infrastructure, drivers-adjacent components, anything another service depends on), that must **keep running across every logon and logoff** without restarting, that should **restart itself automatically if it crashes** (Section 5 of this chapter), and that runs under an identity chosen for the task rather than tied to whichever human happens to be signed in.

### Not every background process needs to be a service

It's worth being precise about when a service is actually the right tool, because it's easy to reach for one by default: an app that just needs to run while a specific user is logged in (a system tray helper, an autostart companion app) fits the `Run` key or the Task Scheduler (Chapter 11) fine, and is *simpler* to build, debug, and update than a service — it can show UI, it inherits the user's own permissions naturally, and it doesn't need the Service Control Manager machinery this chapter covers. Services earn their complexity specifically for machine-wide, logon-independent, must-survive-a-crash workloads: a monitoring agent, a local API that other machines depend on, a database engine, a print spooler.

### What a service can't easily do

The Session 0 isolation that lets a service run before any logon also means, on modern Windows (post–Vista's "Session 0 isolation" change), a service **cannot directly show UI on a user's desktop** — no message boxes, no windows, nothing the interactively logged-on user would actually see appear. Older services that displayed dialogs to whoever was logged in ("interactive services") were a genuine security problem — a non-elevated user's desktop showing a dialog from a `LocalSystem`-level process was an escalation vector — and Windows closed that off structurally rather than relying on services to behave. A service that needs to communicate with a logged-on user has to do it through IPC (Chapter 10) to a separate, ordinary user-mode app that *can* show UI.
