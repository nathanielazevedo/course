The last section mentioned that `AddWindowsService()` swaps in a lifetime that "speaks the SCM's protocol" when the app is launched by it. This section is about what's actually on the other end of that protocol — the **Service Control Manager (SCM)**, a system process (`services.exe`) that owns the entire lifecycle of every service on the machine, and the small state machine every service participates in whether it knows it or not.

### The SCM's database and the service's own state machine

The SCM maintains a database of every registered service — its executable path, startup type, dependencies, and current state — backed by, unsurprisingly, the registry: `HKLM\SYSTEM\CurrentControlSet\Services`. Each service key there is exactly what `sc.exe`, PowerShell's `Get-Service`, and the Services MMC console (`services.msc`) all read from and write to; there is no separate "service database" beyond this registry hive plus the SCM's in-memory tracking of which ones are actually running right now.

A service reports its own state transitions back to the SCM as it moves through this machine — it's a genuine two-way protocol, not the SCM guessing based on whether the process is still alive. This is why a hung service (process running, but never reporting it finished starting) shows as stuck in "Starting" rather than "Running": the SCM is faithfully reporting the last state the service told it, not inferring anything from process existence alone.

### Registering a service

```csharp
// One-time registration, typically done by an installer or a setup script —
// sc.exe is the direct CLI equivalent of what this does
using var scm = new ServiceController("MyService"); // requires it to already exist

// Creating it in the first place (via P/Invoke's CreateService, or sc.exe):
// sc.exe create MyService binPath= "C:\Services\MyService.exe" start= auto
```

```powershell
New-Service -Name "MyService" -BinaryPathName "C:\Services\MyService.exe" `
  -StartupType Automatic -DisplayName "My Service"
```

`.NET` has no first-party API for *creating* a service registration — that's `sc.exe`, PowerShell's `New-Service`, or (for an actual installer) P/Invoke against `CreateService` in `advapi32.dll`, following Chapter 6's interop pattern. `ServiceController`, the class shown above, is for **controlling** an already-registered service — starting, stopping, querying status — not for registering one in the first place.

### Controlling a service from C#

```csharp
using var sc = new ServiceController("MyService");
if (sc.Status != ServiceControllerStatus.Running)
{
    sc.Start();
    sc.WaitForStatus(ServiceControllerStatus.Running, TimeSpan.FromSeconds(30));
}
Console.WriteLine(sc.Status); // Running, Stopped, StartPending, etc.
sc.Stop();
```

`ServiceController` is itself a thin wrapper over the same SCM APIs `sc.exe` calls — `sc.Status` reflects exactly the state machine above, and `WaitForStatus` blocks (with a timeout you provide) until the service reports the target state, rather than polling naively.

### Startup types decide when, not whether, a service can run

A service's **startup type** — `Automatic`, `Automatic (Delayed Start)`, `Manual`, or `Disabled` — controls whether the SCM starts it at boot, not whether it's *allowed* to run at all; a `Manual` service can still be started on demand (by `ServiceController.Start()`, by another service that depends on it, or by a user via `services.msc`), it simply isn't started automatically. `Disabled` is the only setting that actually prevents the service from starting under any circumstance, which is why disabling a service — rather than just setting it to Manual — is the real fix when you need to guarantee it never runs.
