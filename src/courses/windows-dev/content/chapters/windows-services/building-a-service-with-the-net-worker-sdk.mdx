Chapter 1 introduced the Worker Service template as "a console app in disguise" — the shape most services start from. This section makes that concrete: the same code, tested as an ordinary console process, becomes an installable Windows Service with a small, well-defined set of additions.

### Start as a console app — genuinely

```bash
dotnet new worker -n MyService
```

```csharp
// Worker.cs
public class Worker : BackgroundService
{
    private readonly ILogger<Worker> _logger;
    public Worker(ILogger<Worker> logger) => _logger = logger;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            _logger.LogInformation("Working at {time}", DateTimeOffset.Now);
            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }
    }
}
```

`ExecuteAsync` is where the actual work lives, and `stoppingToken` is how the host tells it to wind down — more on that below. Run this with `dotnet run` and it behaves like any console app: logs to the terminal, exits on `Ctrl+C`. That's deliberate — you can develop and debug the entire logic of a service without installing it as one at all, which is a real advantage over editing-and-reinstalling a service on every change.

### The three additions that make it installable as a service

```csharp
// Program.cs
var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddWindowsService(options =>
{
    options.ServiceName = "MyService";
});

builder.Services.AddHostedService<Worker>();

var host = builder.Build();
host.Run();
```

`AddWindowsService()`, from the `Microsoft.Extensions.Hosting.WindowsServices` package, does the actual bridging work: when the process detects it was launched by the Service Control Manager (rather than interactively), it swaps in a `WindowsServiceLifetime` that speaks the SCM's start/stop/pause protocol (next section covers that protocol directly) instead of the console-oriented default lifetime. When run interactively — `dotnet run`, or double-clicking the exe — it's a no-op, and the app behaves exactly like the plain console app from the last step. This is what makes the same binary correctly serve both roles without an `#if` or a separate build.

Two more pieces the project file needs:

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <TargetFramework>net8.0-windows</TargetFramework>
  <!-- lets logging write to the Windows Event Log, covered in Chapter 9 -->
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="Microsoft.Extensions.Hosting.WindowsServices" Version="8.0.0" />
</ItemGroup>
```

### Handling stop requests correctly

The SCM expects a service to stop within a bounded time (roughly 30 seconds by default) once it's asked to — a service that ignores `stoppingToken` and keeps running is exactly what produces the "stopping..." spinner that eventually gives up in the Services console. The pattern above — checking `stoppingToken.IsCancellationRequested` in the loop and passing it into `Task.Delay` so the delay itself is cancelled promptly rather than run to completion — is the correct shape; a version of this loop that used `Thread.Sleep(30000)` instead of `Task.Delay(..., stoppingToken)` would leave the service unresponsive to a stop request for up to 30 seconds at a time.

### Logging: where it goes matters more for a service

`ILogger` calls that would print to a console window in an interactive run have nowhere to go once there's no console attached — which is the normal case for a running service. `Microsoft.Extensions.Logging.EventLog` (added via `builder.Logging.AddEventLog()`) routes the same `ILogger` calls to the Windows Event Log instead, which Chapter 9 covers as the actual durable, queryable place service diagnostics belong; relying on `Console.WriteLine` debugging that worked during `dotnet run` is a common first surprise once the same code is actually installed and running as a service.
