The previous sections covered building and controlling a service. This one is the practical loop of getting one actually installed and diagnosing it when it doesn't start the way you expect — which is a genuinely different debugging experience than an ordinary console app, for reasons that follow directly from Session 0 isolation.

### Publishing and registering

```bash
dotnet publish -c Release -r win-x64 --self-contained false -o C:\Services\MyService
```

```powershell
# Elevated PowerShell — registering a service requires administrator rights
sc.exe create MyService binPath= "C:\Services\MyService\MyService.exe" start= auto
sc.exe description MyService "Does the thing."
Start-Service MyService
```

The space after `binPath=` is not a typo — `sc.exe`'s argument parsing genuinely requires it; `binPath="C:\..."` with no space silently fails to parse correctly, a well-known and easy-to-hit gotcha. `sc.exe delete MyService` (service must be stopped first) is the corresponding uninstall step, worth scripting alongside `create` from the start so upgrading a service during development doesn't leave a stale registration around.

### Why "it works with dotnet run but not installed" happens

The single most common category of "the service won't start" problem traces back to something that was silently true during `dotnet run` and silently false once installed:

- **Working directory.** `dotnet run` executes with the project directory as the working directory; a service launched by the SCM has its working directory set to wherever `services.exe` happens to be, *not* the folder containing your executable. Code using relative paths to find a config file that worked during development fails once installed, unless you explicitly resolve paths from `AppContext.BaseDirectory` instead of assuming the current directory.
- **Identity.** As covered in Chapter 4, a service commonly runs as `LocalSystem`, `NetworkService`, or `LocalService` by default — not the developer's own account — so file, registry, and network permissions that worked interactively can be denied entirely once installed, especially `HKCU` reads, which resolve to a completely different profile.
- **No console.** As covered in the previous section, there's nothing to catch `Console.WriteLine` or an unhandled exception's default console output — a startup failure that would have been an obvious stack trace in the terminal instead shows up only as "Error 1053: the service did not respond in a timely fashion," with no further detail unless logging is wired up.

### Debugging a service that won't start

The Event Log (Chapter 9) is the first stop — unhandled startup exceptions and SCM-level failures (like `1053`) are both recorded there, and `builder.Logging.AddEventLog()` from the previous section is what puts your own diagnostic output there too. For step-through debugging, Visual Studio supports attaching to an already-running service process directly (`Debug` → `Attach to Process`, selecting the running service's process) — you can't `F5`-launch a service the way you launch a console app, since the SCM has to be the one starting it, but once it's running, ordinary breakpoint debugging works against it like any other process. A common workaround for early-startup issues specifically (before you can attach in time) is a short `Task.Delay` or a `Debugger.Launch()` call gated behind a config flag, giving you a window to attach before the code you actually want to inspect runs.

### Restart behavior on failure

A service's **recovery options** — configurable via `sc.exe failure` or the Services console's Recovery tab — decide what the SCM does if the service process exits unexpectedly (crashes, or exits with a non-zero code the SCM treats as a failure): restart it after a delay, run a program, or take no action, with separate settings for the first, second, and subsequent failures. This is genuinely different from the app-level retry logic you might write inside `ExecuteAsync` — recovery options handle the case where the *entire process* has died, which no amount of in-process exception handling can recover from, since there's no process left running to do the recovering.
