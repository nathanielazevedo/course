This closing section pulls together three configuration choices every real service needs made deliberately rather than left at their defaults: what happens when it fails, what it needs running before it, and whose identity it runs under.

### Recovery actions, in detail

The previous section introduced recovery options as the SCM's answer to a crashed service process. The actual configuration is three independent slots — first failure, second failure, subsequent failures — each with its own action and delay:

```powershell
sc.exe failure MyService reset= 86400 actions= restart/5000/restart/30000/run/60000
```

This configures: restart after 5 seconds on the first failure, restart after 30 seconds on the second, and run a specified recovery program after 60 seconds on the third and any further failure, with the failure count itself resetting to zero after 86400 seconds (24 hours) of continuous good behavior. The escalating delays are a deliberate pattern — a service crash-looping every few seconds from a bad config or a corrupted dependency benefits from backing off rather than hammering the same failure indefinitely, and the third-strike "run a program" slot is commonly wired to something that pages an on-call engineer or captures diagnostic state, on the theory that two automatic restarts is a reasonable number of free attempts before a human should know.

### Dependencies: ordering the SCM enforces for you

A service can declare other services (or, for driver-level dependencies, device driver groups) it depends on:

```powershell
sc.exe config MyService depend= Tcpip/MySharedService
```

The SCM guarantees a service's dependencies are already running before it attempts to start that service, and — the direction developers forget — refuses to stop a service that other running services still depend on, until those dependents are stopped first. This is meaningfully different from handling the ordering yourself inside `ExecuteAsync` with retry loops against a dependency that might not be up yet: declared dependencies are enforced by the SCM before your code runs at all, rather than being a race your own code has to survive.

### Choosing a service account

Three built-in identities cover most cases, in increasing order of network exposure:

- **`LocalService`** — minimal local privileges, presents no network credentials at all (connects to network resources anonymously). Right for a service that only touches local resources.
- **`NetworkService`** — similar local privileges to `LocalService`, but presents the *computer's own* machine account credentials when accessing network resources. Right for a service that needs to authenticate to another machine as "this computer," not as a specific person.
- **`LocalSystem`** — full local machine privileges, effectively unrestricted on the local machine, but (like `LocalService`) has no real network identity of its own. This is the account with the most local power and, correspondingly, the one to avoid defaulting to out of convenience — a compromised `LocalSystem` service is a compromised machine, full stop.

For a service that genuinely needs a specific network identity — authenticating to a database or another server as a particular account, rather than as the machine itself — a **Managed Service Account** (a domain account whose password Active Directory rotates automatically, so nothing in your deployment scripts ever has to know or store it) is the modern answer, ahead of a manually managed domain service account whose password someone has to remember to rotate and redeploy.

```powershell
sc.exe config MyService obj= "NT AUTHORITY\NetworkService"
```

### The guiding principle across all three

Recovery, dependencies, and account choice all point at the same underlying idea this chapter has been building toward: a service is meant to run unattended, for long stretches, without a human present to notice or fix things — which is exactly why the SCM, not your own code, is the layer responsible for restarting it, sequencing it against what it needs, and constraining what it's allowed to touch if something does go wrong.
