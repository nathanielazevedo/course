The previous section mentioned marshaling without defining it precisely. This section is that definition, made concrete: the actual rules the runtime follows to convert a C# value into something a native Win32 function can read, and back.

### Why marshaling has to exist at all

.NET's managed types and native C types don't share a representation. A managed `string` is UTF-16 with a length prefix and lives wherever the GC decides to put it, and the GC can move it during a collection. A native `LPWSTR` is a raw pointer to a null-terminated buffer of UTF-16 characters at a fixed address, with no length prefix at all. Calling a native function with a managed string means something has to bridge that gap — pin the string (or copy it) so it has a stable address for the duration of the call, and represent it as the raw pointer the native side expects. That bridging, for every parameter and the return value, is marshaling.

### Value types are simple; strings and structs are where it gets real

```csharp
[LibraryImport("kernel32.dll", StringMarshalling = StringMarshalling.Utf16)]
internal static partial IntPtr GetModuleHandleW(string? lpModuleName);

[LibraryImport("kernel32.dll")]
internal static partial uint GetLastError();
```

Primitives like `int`, `uint`, and `bool` map close to directly — `int` and a C `int` are the same bits, no real translation needed. `bool` is a notable exception worth watching for: a C# `bool` is one byte, but the Win32 `BOOL` type is a four-byte `int`, so an unmarked `bool` parameter can silently misalign whatever comes after it in a struct, or read/write the wrong bytes as a parameter — `[MarshalAs(UnmanagedType.Bool)]`, seen in the previous section's example, is what tells the marshaler to actually use the 4-byte convention.

**Strings** need `StringMarshalling` (or per-parameter `[MarshalAs]`) specified explicitly, because Win32 has two parallel families of most functions — an `A` (ANSI/multi-byte) suffix and a `W` (wide/UTF-16) suffix — and getting the encoding wrong doesn't necessarily fail loudly; it can silently corrupt non-ASCII text. Preferring the `W` functions with `StringMarshalling.Utf16` is close to always correct, since .NET strings are natively UTF-16 already, making that the marshaling path with the least conversion work and least room for encoding bugs.

**Structs** passed to native functions need `[StructLayout(LayoutKind.Sequential)]` (or `Explicit`, for unions or precisely controlled offsets) so the CLR lays out the fields in memory exactly like the C struct expects — without it, the CLR is free to reorder fields for its own efficiency, which native code reading raw memory at fixed offsets cannot tolerate:

```csharp
[StructLayout(LayoutKind.Sequential)]
internal struct POINT
{
    public int X;
    public int Y;
}
```

### Getting the actual OS error after a call fails

`SetLastError = true` (seen in the previous section) tells the marshaler to capture the thread-local Win32 error code immediately after the native call returns — immediately, because any subsequent managed code (even seemingly innocuous framework internals) could otherwise overwrite that same thread-local slot before you read it. `Marshal.GetLastWin32Error()` (or the newer `Marshal.GetLastPInvokeError()`) reads that captured value back; without `SetLastError = true` on the declaration, that call would return stale or meaningless data, since the marshaler never captured anything to begin with.

```csharp
if (!MessageBeep(0))
{
    int error = Marshal.GetLastPInvokeError();
    throw new Win32Exception(error);
}
```

`Win32Exception` translates that numeric code into the actual OS-provided error message, which is generally more useful to a human than the bare integer.
