With declaration and marshaling covered, this section is a worked example end to end — a real, moderately involved P/Invoke call that touches several earlier chapters at once, plus the handful of patterns that show up in almost every non-trivial Win32 call.

### A complete example: enumerating top-level windows

```csharp
using System.Runtime.InteropServices;

internal static partial class NativeMethods
{
    internal delegate bool EnumWindowsProc(IntPtr hWnd, IntPtr lParam);

    [LibraryImport("user32.dll")]
    [return: MarshalAs(UnmanagedType.Bool)]
    internal static partial bool EnumWindows(EnumWindowsProc lpEnumFunc, IntPtr lParam);

    [LibraryImport("user32.dll", StringMarshalling = StringMarshalling.Utf16)]
    internal static partial int GetWindowTextLength(IntPtr hWnd);

    [LibraryImport("user32.dll", StringMarshalling = StringMarshalling.Utf16)]
    internal static partial int GetWindowText(IntPtr hWnd, System.Text.StringBuilder lpString, int nMaxCount);
}

var titles = new List<string>();
NativeMethods.EnumWindows((hWnd, _) =>
{
    int len = NativeMethods.GetWindowTextLength(hWnd);
    if (len > 0)
    {
        var sb = new System.Text.StringBuilder(len + 1);
        NativeMethods.GetWindowText(hWnd, sb, sb.Capacity);
        titles.Add(sb.ToString());
    }
    return true; // continue enumeration
}, IntPtr.Zero);
```

`EnumWindows` calls back into managed code once per top-level window — the `EnumWindowsProc` delegate is marshaled into a native function pointer the OS invokes directly. This is a real, common shape: many older Win32 enumeration APIs work by callback rather than returning a collection, because they predate any convention resembling `IEnumerable`.

### Handles from Win32 belong in `SafeHandle`, not raw `IntPtr`

Chapter 1 and Chapter 2 both leaned on the idea that Windows kernel objects are accessed through handles, and that `.NET`'s wrappers (`Process`, `FileStream`) hold those handles in a `SafeHandle` so the CLR can guarantee they're closed. Any P/Invoke call that returns a handle you're responsible for closing should follow the same pattern rather than holding a bare `IntPtr`:

```csharp
internal sealed class MyHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    internal MyHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() => CloseHandle(handle);

    [LibraryImport("kernel32.dll")]
    [return: MarshalAs(UnmanagedType.Bool)]
    private static partial bool CloseHandle(IntPtr hObject);
}
```

A raw `IntPtr` handle has no finalizer and no `Dispose` — if the code that owns it throws before closing it, or simply forgets, the handle leaks for the life of the process. `SafeHandle` ties the native resource's lifetime to the CLR's own object lifetime tracking, the same mechanism that makes `using var file = new FileStream(...)` reliable, applied to a handle you obtained yourself.

### `ref struct`, `Span<T>`, and avoiding unnecessary copies

Modern P/Invoke code increasingly favors `Span<T>` and `ReadOnlySpan<T>` parameters over arrays for buffer-passing functions, since a span can wrap a stack-allocated or pooled buffer without the extra array allocation and copy an ordinary `byte[]` parameter would require — genuinely useful in code calling native functions in a hot loop, less relevant for a one-off startup call where a small allocation is immaterial.

### When to stop and check pinvoke.net / CsWin32 instead

The example above is deliberately simple. Real Win32 signatures frequently involve nested structs, unions, variable-length buffers described by a separate size parameter, and calling conventions that are easy to get subtly wrong by hand. As covered in the first section of this chapter, reaching for CsWin32 or a verified community reference for anything beyond the simplest signatures is the practical default — hand-writing a P/Invoke signature is a reasonable exercise for understanding what's happening, and a poor habit for anything going into production code you'll maintain.
