P/Invoke is for calling loose functions in a DLL. A large and important slice of Windows — Office automation, the shell, media APIs, and much of the modern Windows App SDK — isn't exposed as loose functions at all, but as **COM objects**: a different, older interop model with its own rules, and its own newer descendant, WinRT.

### COM: interfaces, not functions

**Component Object Model (COM)** predates .NET entirely and is Windows' original answer to language-agnostic, binary-compatible object interfaces. A COM object exposes one or more **interfaces** — each a fixed, versioned table of function pointers (a vtable) — identified by a GUID, and every COM interface derives from `IUnknown`, which provides `QueryInterface` (ask an object whether it also implements a different interface you want), `AddRef`, and `Release` (COM's own reference counting, independent of the .NET GC entirely). Where P/Invoke calls a specific DLL export by name, COM interop involves the runtime locating and activating an object (often via the registry — COM objects register their class ID and implementing DLL under `HKCR\CLSID`, tying back to Chapter 4) and then calling through its interface's vtable.

### .NET's COM interop: RCWs and CCWs

```csharp
using System.Runtime.InteropServices;

// Common in older code — using a COM object registered as a type library reference
dynamic excel = Activator.CreateInstance(
    Type.GetTypeFromProgID("Excel.Application")!)!;
excel.Visible = true;
excel.Workbooks.Add();
```

When managed code calls into a COM object, .NET wraps it in a **Runtime Callable Wrapper (RCW)** — a managed proxy that translates .NET method calls into the underlying `QueryInterface`/vtable calls, and participates in COM's reference counting on your behalf as the RCW itself gets garbage collected. The reverse direction — native COM code calling into a managed object — goes through a **COM Callable Wrapper (CCW)**, letting a C# class be consumed as if it were a native COM object at all. Most application-level code only deals with RCWs; CCWs matter when you're building a component meant to be *consumed* by unmanaged code (a COM add-in for Office, for instance).

### Why COM interop specifically needs careful disposal

COM objects are reference-counted independently of the .NET GC — an RCW being garbage collected eventually calls `Release` through its finalizer, but "eventually" is doing real work in that sentence: until a GC actually runs, the underlying COM object (and, in the Excel example, the entire Excel process it may represent) can stay alive well past when the code appeared to be "done" with it. `Marshal.ReleaseComObject` (or `Marshal.FinalReleaseComObject` to force the count fully to zero) exists specifically to force that release deterministically, which is why Office automation code in particular has a long-standing convention of explicitly releasing every COM object it touches, rather than trusting the GC's timing — a genuinely common cause of "Excel.exe processes pile up in Task Manager after my script runs."

### WinRT: COM's modern, better-behaved descendant

The **Windows Runtime (WinRT)**, introduced with Windows 8 and still the foundation of WinUI 3 and the modern Windows App SDK (Chapter 8), is built on COM underneath — WinRT interfaces are COM interfaces — but adds a metadata system (`.winmd` files, structurally similar to .NET assembly metadata) that describes types precisely enough for tooling to generate strongly-typed projections automatically, rather than relying on `dynamic` or hand-written interop code. Modern .NET's WinRT interop (via `CsWinRT`, the spiritual sibling of CsWin32 from earlier in this chapter) generates these projections at build time, which is why calling a WinRT API from C# today looks like calling an ordinary strongly-typed .NET API — the COM machinery underneath is real, but almost entirely invisible.
