Chapter 1 mentioned that the Security Reference Monitor checks every kernel object access against an access token and an ACL. Files are the object type you'll interact with this system on most often, and `System.Security.AccessControl` is the managed API for it — but it only makes sense once you know it's exposing a genuinely richer model than Unix's `rwx` permission bits.

### DACLs: a list of rules, not three numbers

Unix file permissions are nine bits: read/write/execute for owner, group, and everyone else. NTFS files carry a **DACL** (Discretionary Access Control List) — an ordered list of **Access Control Entries (ACEs)**, each one granting or denying a specific set of rights to a specific user or group. Where Unix asks "which of three buckets does this caller fall into," NTFS asks "walk this list of specific grants and denials until one applies." That's a lot more expressive — you can grant one specific user write access without touching anyone else's rights — and a lot easier to get subtly wrong, because the *order* of ACEs matters.

### Reading and writing a file's ACL from C#

```csharp
var fileInfo = new FileInfo(path);
FileSecurity security = fileInfo.GetAccessControl();

// Grant a specific user read-and-execute rights
security.AddAccessRule(new FileSystemAccessRule(
    "DOMAIN\\someuser",
    FileSystemRights.ReadAndExecute,
    AccessControlType.Allow));

fileInfo.SetAccessControl(security);
```

Each `FileSystemAccessRule` is one ACE: an identity, a set of rights (`FileSystemRights` — far more granular than read/write/execute, including things like `Delete`, `TakeOwnership`, and `ChangePermissions` individually), and whether it's an `Allow` or `Deny` entry.

### Deny beats Allow, and explicit beats inherited

Two ordering rules matter more than any specific API call:

- **Deny ACEs are evaluated before Allow ACEs** at the same level of specificity, and a matching Deny wins even if an Allow for the same right also exists. This is what lets an administrator carve out an exception — "everyone in this group can read except this one user" — without restructuring group membership.
- **Explicit ACEs on the object itself take precedence over inherited ones.** Folders can propagate their ACL down to files created inside them (inheritance), but an ACE set directly on a specific file overrides what it would have inherited from its parent folder.

Getting this wrong looks like: "I granted Allow, why is access still denied?" — almost always because a Deny ACE, explicit or inherited, is present somewhere in the chain.

### Ownership is a separate concept from access rights

A file's **owner** is tracked independently of its DACL, and ownership carries an implicit right that no ACE grants explicitly: the owner can always modify the file's permissions, even if their current DACL entries deny them everything else. This is by design — it's the escape hatch that prevents a misconfigured DACL from permanently locking everyone out of a file, including whoever's responsible for it. `TakeOwnership`, one of the `FileSystemRights` values, is the right that lets someone *other* than the current owner claim ownership, which is why it's treated as sensitive enough to require its own explicit grant.

### `icacls` and the GUI Security tab are the same ACL you're editing in code

Everything `FileSecurity` exposes is the exact same DACL the Windows Explorer "Security" tab and the `icacls` command-line tool read and write — there's no separate "C# permission model." This is genuinely useful for debugging: if `security.AddAccessRule(...)` in your code doesn't seem to have taken effect, running `icacls path\to\file` from a terminal shows you the real, current ACE list, independent of whatever your C# code believes it set.
