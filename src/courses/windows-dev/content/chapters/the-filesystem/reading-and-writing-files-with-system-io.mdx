`System.IO` is where most C# developers spend the bulk of their time on Windows, and most of it — `File.ReadAllText`, `StreamReader`, `Directory.EnumerateFiles` — behaves exactly as documented with no OS-specific surprises. This section is about the parts that do carry Windows-specific behavior worth knowing before it surprises you: sharing, locking, and buffering.

### File sharing: Windows locks by default, Unix mostly doesn't

This is the single biggest behavioral difference developers hit moving from Unix-family systems. On Unix, one process can delete or rename a file another process still has open — the open handle keeps working against the old inode, and the directory entry is just gone. On Windows, whether that's allowed is decided **at open time**, by the `FileShare` flags each opener requested:

```csharp
using var fs = new FileStream(
    path,
    FileMode.Open,
    FileAccess.Read,
    FileShare.Read); // other readers OK, but writers/deleters are blocked
```

`File.OpenRead` defaults to `FileShare.Read`. If any process has the file open without `FileShare.Delete`, a second process's attempt to delete or rename it fails with a sharing violation — `IOException: The process cannot access the file because it is being used by another process` is one of the most common exceptions in Windows file code, and it is a *policy* decision baked in at open time, not a bug. Log files, config files being hot-reloaded, and anything a background watcher (next section) has open are the usual sources.

### Buffering and flushing: what "written" actually means

`FileStream` buffers writes in user-mode memory before they reach the OS. `Flush()` pushes that buffer down to the OS, but the OS itself buffers too (the Cache Manager from Chapter 1) — data can survive an application crash once `Flush()` returns, but not necessarily a power loss, unless you go further:

```csharp
using var fs = new FileStream(path, FileMode.Create, FileAccess.Write,
    FileShare.None, bufferSize: 4096, FileOptions.WriteThrough);
fs.Write(data);
fs.Flush(flushToDisk: true); // forces the OS cache to physical media too
```

`FileOptions.WriteThrough` at open time, plus `Flush(flushToDisk: true)`, is what actually gets a guarantee past the OS cache. Ordinary code writing logs or user documents doesn't need this — it matters specifically for data that must survive an unexpected power loss, like a database's write-ahead log.

### Async file I/O and why the FileOptions matter

Chapter 2 covered how genuinely async I/O avoids blocking a thread by completing through an I/O completion port. For file I/O specifically, that only actually happens if the handle was opened for overlapped (asynchronous) I/O in the first place:

```csharp
using var fs = new FileStream(path, FileMode.Open, FileAccess.Read,
    FileShare.Read, bufferSize: 4096, useAsync: true);
byte[] buffer = await fs.ReadAsync(memory);
```

Without `useAsync: true` (or the modern `FileStreamOptions.Options` including `FileOptions.Asynchronous`), `ReadAsync` still compiles and runs — but under the hood .NET falls back to running the synchronous read on a thread pool thread, which is exactly the thread-blocking behavior async I/O is supposed to avoid. This is a common, silent performance gap: code that looks async and is functionally correct, but is quietly burning a pool thread per concurrent file operation instead of using completion ports.

### Enumerating large directories

`Directory.GetFiles` materializes the entire result as an array before returning; `Directory.EnumerateFiles` streams results lazily as it walks the directory. For a directory with thousands of entries, or when you only need the first few matches, `EnumerateFiles` avoids allocating and waiting for the full listing up front — a small API choice with a real difference on large or slow (e.g., network) file shares.
