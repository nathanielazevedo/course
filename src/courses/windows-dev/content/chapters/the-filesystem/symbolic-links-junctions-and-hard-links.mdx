NTFS supports several ways for one path to point at another, and they are not interchangeable — each has different rules about what it can point to, whether it crosses volumes, and what rights are needed to create it. Confusing them is a common source of "this worked in my test but not in production."

### Hard links: two names, one file

A **hard link** is a second directory entry pointing at the same on-disk file data — not a copy, not a pointer to a path, but a second name for literally the same file. NTFS tracks a link count; the underlying data isn't freed until every hard link to it is deleted. Hard links only work within a single volume (you can't hard-link across drive letters, since the link is really just another entry referencing the same on-disk file record) and only for files, not directories.

```csharp
// No first-party BCL API — this is P/Invoke territory (Chapter 6)
CreateHardLink(@"C:\data\alias.txt", @"C:\data\original.txt", IntPtr.Zero);
```

### Symbolic links: a path that points to a path

A **symbolic link** (symlink) is closer to what Unix developers expect: a special file whose content is another path, resolved transparently by the filesystem when something opens it. Unlike a hard link, a symlink can point across volumes, can target a directory, and can point to a path that doesn't exist yet (a "dangling" symlink) — none of which a hard link can do.

```csharp
// .NET has first-party support for symlinks
File.CreateSymbolicLink(@"C:\shortcut.txt", @"D:\real\path\data.txt");
FileSystemInfo? target = File.ResolveLinkTarget(@"C:\shortcut.txt", returnFinalTarget: true);
```

The practical catch: **creating** a symlink has historically required either administrator rights or Developer Mode enabled (Settings → Privacy & Security → For Developers), unlike hard links or junctions, which don't. Code that calls `File.CreateSymbolicLink` and works fine on a dev machine with Developer Mode on can throw `UnauthorizedAccessException` the moment it runs somewhere that setting isn't enabled — a genuinely common deployment surprise.

### Junctions: symlinks' older, directory-only, no-privilege sibling

A **directory junction** (technically an NTFS reparse point, the same underlying mechanism symlinks use) points one directory to another. Unlike a symlink, creating a junction requires no special privilege — any user who can write to the parent folder can create one. Unlike a hard link, a junction can cross volumes (though not network shares — it has to be a local NTFS path). .NET has no first-party API for junctions specifically; creating one is either P/Invoke against the reparse point APIs directly, or shelling out to `mklink /J`.

### Why any of this matters in real code

Deployment tooling, build systems, and package managers use these constantly: `node_modules` deduplication, NuGet's package cache, Docker layer sharing, and profile redirection folders (`Documents` sometimes being a junction to a OneDrive-synced path) all rely on one of these three mechanisms. When code that copies or deletes files behaves unexpectedly on a path that turns out to be a link — deleting through a junction removes the junction, not the target; deleting through a hard link only removes that one name, leaving the data alive under its other names — the fix is almost always understanding which of the three you're actually looking at, which `File.ResolveLinkTarget` and `fsutil reparsepoint query` can both tell you.
