The previous section drew the line between user mode and kernel mode. This one opens up what sits on each side of that line — the pieces inside the NT kernel, and the Win32 API surface that sits directly on top of it, which is what every C# program on Windows is ultimately built from.

### The Executive: NT's kernel is a set of managers

"The kernel" is really shorthand for two layers. The **microkernel** at the very core handles the smallest primitives — thread scheduling, interrupt dispatch, low-level synchronization. Everything else lives in the **NT Executive**, a set of cooperating components that each own one concern:

- **Object Manager** — creates and tracks the typed kernel objects introduced in the last section (files, processes, sections, mutexes) and hands out handles to them.
- **Process/Thread Manager** — creates and tears down processes and threads, and owns the scheduler's bookkeeping.
- **Memory Manager** — virtual address spaces, paging, and the working-set logic behind every `byte[]` your GC allocates.
- **I/O Manager** — routes read/write/control requests to device drivers, including the filesystem drivers behind `System.IO`.
- **Security Reference Monitor** — checks every object access against the requester's access token and the object's ACL (Chapter 7).
- **Cache Manager** — the shared page cache that makes repeated file reads fast.

None of these are things you call directly from C#. They're the machinery Win32 sits on top of, and the reason certain Windows behaviors — why a locked file can't be deleted, why a process handle keeps working after the process exits, why an ACL check happens on every single file open — trace back to a specific Executive component rather than being arbitrary API rules.

### The Hardware Abstraction Layer

Below the Executive sits the **HAL**, a thin layer that hides CPU and chipset differences (interrupt controllers, timers, DMA) so the rest of the kernel can stay hardware-agnostic. You'll basically never touch it directly, but it's why the same NT kernel design has run on x86, x64, and ARM64 — including the ARM64 Windows machines that now run .NET natively.

### Win32: the stable API in front of a moving kernel

Win32 is not "the OS" — it's a **subsystem**, an API contract implemented by a set of user-mode DLLs (`kernel32.dll`, `user32.dll`, `gdi32.dll`, `advapi32.dll`, `ws2_32.dll`, and dozens more) that translate documented function calls into the syscalls the Executive actually implements. Microsoft has changed the internals of the kernel repeatedly across NT releases; Win32 is the contract that stayed backward compatible through all of it, which is why 20-year-old Win32 binaries still run on Windows 11.

### Why this matters for a C# developer

Nearly every .NET method that touches the OS is, underneath, a call into one of these DLLs. `System.Diagnostics.Process.Start` calls `CreateProcessW` in `kernel32.dll`. `Microsoft.Win32.Registry` calls `RegOpenKeyExW` and friends in `advapi32.dll`. `System.Threading.Mutex` wraps a kernel mutant object created through `kernel32.dll`. When the BCL's documentation is vague about an edge case — what happens when two processes race to create the same named mutex, say — the Win32 documentation for the underlying function almost always has the answer, because that's genuinely where the behavior is defined. Knowing this API sits between you and the kernel is also what makes P/Invoke (Chapter 6) a normal escape hatch rather than a hack: you're just calling the same DLL the BCL calls, without waiting for a managed wrapper to exist.
