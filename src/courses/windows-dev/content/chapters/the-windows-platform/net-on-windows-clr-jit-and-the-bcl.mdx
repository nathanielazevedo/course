Everything in this course happens inside the .NET runtime, so before going further it's worth being precise about what that runtime actually is on Windows, and where it stops being "just .NET" and starts being "Windows specifically."

### From C# to running machine code

A C# compiler (`csc` or Roslyn) never emits machine code. It emits **IL** (Intermediate Language) plus metadata, packaged into an **assembly** — a `.dll` or `.exe` file. Nothing about IL is Windows-specific; it's a CPU-agnostic instruction set designed for the CLR to consume. The **CLR** (Common Language Runtime) is the engine that loads an assembly, and its **JIT compiler** (just-in-time compiler) translates IL methods into real x64 or ARM64 machine code the moment they're first called, caching the result for the life of the process.

Two things fall out of this. First, IL is why a compiled DLL can, in principle, run on Windows, Linux, or macOS unchanged — the JIT, not the compiler, is what's platform-specific. Second, the JIT is why a .NET app has a brief warm-up cost the first time each method runs, and why tools like ReadyToRun and Native AOT exist to precompile some or all of that work ahead of time for startup-sensitive apps.

### The BCL: the managed wrapper around the OS

The **Base Class Library** (`System.*`) is the managed API surface — `File`, `Process`, `Socket`, `Dictionary<T,K>` — that C# code is written against instead of calling Win32 directly. Most of it is genuinely cross-platform: `System.Collections.Generic` doesn't care what OS it's running on. But a meaningful slice of it exists specifically to wrap Windows concepts: `Microsoft.Win32.Registry`, `System.ServiceProcess` for Windows Services, `System.Security.AccessControl` for ACLs, `System.Management` for WMI. That code compiles fine on any platform, but throws `PlatformNotSupportedException` at runtime if you call it anywhere but Windows.

.NET makes this explicit at the project level with **target framework monikers**. `net8.0` targets the OS-agnostic surface; `net8.0-windows` unlocks the Windows-only APIs (and lets analyzers warn you if you call a Windows-only API from a project that doesn't declare that TFM). This is the mechanism that makes "a C# app for Windows" a distinct, declared thing rather than an accident of which machine you happened to build on.

```xml
<PropertyGroup>
  <!-- Cross-platform surface only -->
  <TargetFramework>net8.0</TargetFramework>
</PropertyGroup>

<PropertyGroup>
  <!-- Unlocks Registry, WMI, WinForms/WPF, COM interop, etc. -->
  <TargetFramework>net8.0-windows</TargetFramework>
</PropertyGroup>
```

### .NET Framework vs. modern .NET, briefly

You will still encounter **.NET Framework** (4.x, Windows-only, ships as part of Windows itself) in existing codebases, alongside modern **.NET** (5 and later, cross-platform, installed side by side, the actively developed line and what this course targets). Modern .NET on Windows has effectively the same access to Windows-specific APIs that .NET Framework always had — the difference is that on .NET Framework everything is Windows-only by default, whereas modern .NET makes you opt in to that surface explicitly via `-windows` TFMs and platform compatibility analyzers.
