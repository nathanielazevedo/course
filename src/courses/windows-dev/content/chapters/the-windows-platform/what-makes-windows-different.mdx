If you learned to program against Linux or macOS, Windows will keep surprising you in small ways — not because it is more complicated, but because it made different choices at almost every layer, and those choices were made decades before yours. Understanding *why* Windows looks the way it does makes the rest of this course predictable instead of arbitrary.

### A kernel built for objects, not files

Unix treats almost everything as a file: devices, pipes, sockets — all opened, read, and written through the same file-descriptor interface. Windows NT took a different path. Its kernel is built around a general **object manager**: processes, threads, files, registry keys, mutexes, and sections are all kernel objects, each with a handle, a type, security metadata, and a reference count. A `Process` in C# and a `RegistryKey` are not the same *kind* of thing under the hood the way "everything is a file" would suggest — but they are both handled through the same object and handle infrastructure.

This shows up directly in C#. When you open a file, start a process, or create a mutex, you get back a `SafeHandle` — a managed wrapper around a kernel handle. Chapter 6 covers this in depth, but the shape of it starts here: Windows hands out handles to typed kernel objects, and .NET wraps each handle so the CLR's garbage collector can close it deterministically.

Every Windows process runs in **user mode**, isolated from the kernel and from other processes by the CPU's privilege rings. To do anything that touches hardware or shared state — open a file, allocate memory, create a thread — user-mode code asks the kernel to do it on its behalf, through a syscall. You never see this directly from C#. The call path is: your code → the .NET runtime → a Win32 API in a DLL like `kernel32.dll` → `ntdll.dll` → the kernel. Win32 is not the kernel; it's the stable public API *in front of* the kernel, and it's the layer .NET itself is built on.

### Windows was GUI-first; Unix was terminal-first

Unix-family systems grew up as multi-user terminal systems where the shell is the primary interface and everything else is layered on top. Windows NT grew up assuming a single interactive user sitting at a graphical console, with **sessions**, **desktops**, and a **window station** as first-class kernel concepts, not something bolted on later. This is why Windows has a message-loop-driven GUI model at its core (Chapter 8), why services traditionally ran without a desktop of their own, and why "headless Windows" work — running a service or a container image with no one logged in — has historically required more care than the equivalent on Linux.

### A registry instead of scattered config files

Where Unix tools default to text config files under `/etc` or a user's home directory, Windows centralizes machine and per-user configuration in the **registry** — a single hierarchical, typed database (Chapter 4). It's not inherently better or worse than flat files; it's a different tradeoff: one place to look, transactional-ish writes, and access control at the key level, at the cost of a structure you can't just read with a text editor.

### Where .NET sits in all of this

.NET on Windows is not a replacement for any of this — it's a managed layer that calls straight through it. The CLR's JIT compiler emits native code that runs in the same user-mode process as everything else; `System.IO.File` eventually calls `CreateFileW`; `System.Diagnostics.Process` eventually calls `CreateProcessW`. Nearly everything this course covers is really "here is the Win32 concept, and here is the C# API that wraps it." Knowing that a `.NET` method has a Win32 function underneath it is what lets you reason about behavior the C# documentation doesn't spell out — and reach for P/Invoke (Chapter 6) when it doesn't wrap something you need at all.
