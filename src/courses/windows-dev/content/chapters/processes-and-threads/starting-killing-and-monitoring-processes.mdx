Starting a process sounds like it should be one operation. In practice, `Process.Start` hides a handful of decisions — how the process is created, how it inherits (or doesn't) resources from you, and what "killing" it actually guarantees — that matter the moment you're doing anything beyond launching Notepad.

### Two very different ways to start something

```csharp
// ShellExecute-style: uses file associations, can elevate, can't redirect I/O
Process.Start(new ProcessStartInfo("report.pdf") { UseShellExecute = true });

// CreateProcess-style: direct executable launch, full control over I/O
Process.Start(new ProcessStartInfo("cmd.exe", "/c dir")
{
    UseShellExecute = false,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
});
```

`UseShellExecute` is the pivot point. `true` routes the request through the shell (`ShellExecuteEx`), which is what lets you "start" a document by its file association, request elevation with `Verb = "runas"`, or open a URL in the default browser — but it hands you no standard I/O streams to redirect. `false` calls `CreateProcess` directly: you get real control over the child's standard handles, working directory, and environment, but no shell resolution — the target has to be an actual executable, and if it needs elevation you have to have started *your own* process elevated already (the next section covers this properly).

### What "killing" a process actually does

`Process.Kill()` calls `TerminateProcess`, which is abrupt by design: it stops every thread in the target process immediately, at whatever point they happened to be executing, and tears down the address space. There is no `finally` block, no `using` disposal, no chance for the target to flush a file or release a lock cleanly — from the target's perspective, it simply stops existing mid-instruction. This is different from asking a process to exit gracefully (closing its main window, or signaling it through whatever IPC mechanism it listens for, covered in Chapter 10), which gives it a chance to clean up. `Kill()` is a last resort for exactly the situations where clean shutdown has already failed or isn't available.

`Process.Kill(entireProcessTree: true)`, added in modern .NET, walks the process's recorded children and kills them too — useful, but worth remembering it's walking the same informational parent-child bookkeeping from the previous section, not a kernel-enforced tree, so a child that has re-parented itself (rare, but possible) won't be caught by it.

### Monitoring: polling vs. events vs. waiting

Three different ways to know what a process is doing, each suited to a different question:

- **`Process.Exited` event** — fires once, when the process terminates, if you set `EnableRaisingEvents = true`. Best for "tell me when this is done" without blocking.
- **`Process.WaitForExit()`** — blocks the calling thread (or, with the `Task`-returning overload, awaits) until the process ends. Best when your own logic can't proceed until the child is finished.
- **Polling `Process.GetProcesses()` / `Process.GetProcessById()`** — a live snapshot of currently running processes, refreshed each time you call it, useful for "is *some* process matching this name currently running" rather than tracking one process you started yourself.

```csharp
using var proc = Process.Start(startInfo)!;
proc.EnableRaisingEvents = true;
proc.Exited += (_, _) => Console.WriteLine($"Process {proc.Id} exited with {proc.ExitCode}");
await proc.WaitForExitAsync();
```

A property worth knowing about for monitoring resource use rather than lifetime: `Process.WorkingSet64`, `PrivateMemorySize64`, and `TotalProcessorTime` read live counters the kernel already maintains per process — the same data Task Manager's Details tab shows, just through the managed API instead of the GUI.
