A process is a container; a **thread** is what actually executes. Every process starts with one thread and can create more, each with its own stack but sharing the process's address space and handle table. C#'s `async`/`await` sits on top of this model rather than replacing it, and understanding the layer underneath is what makes `async` behavior — which thread a continuation runs on, why `Task.Run` matters, why UI code can deadlock — predictable instead of mysterious.

### The kernel scheduler and thread priority

Windows schedules **threads**, not processes — the process is just the address space threads happen to execute in. Each thread has a priority (combined from the process's priority class and the thread's own relative priority) that the scheduler uses to decide which ready thread runs next on an available core. You rarely touch this directly from C# (`Thread.Priority` exists but changing it is an advanced, easy-to-misuse tool), but it's worth knowing it's there: on a busy system, thread priority — not just how much work you scheduled — affects how promptly your code actually runs.

### `System.Threading.Thread`: one OS thread, directly

```csharp
var t = new Thread(() => Console.WriteLine("running on its own OS thread"));
t.Start();
t.Join(); // block until it finishes
```

Creating a `Thread` creates a real, dedicated OS thread — with its own kernel stack, its own entry in the scheduler, real memory overhead (roughly a megabyte of reserved stack by default). This is the right tool when you genuinely need a dedicated, long-lived thread: a background loop that runs for the process's entire lifetime, or code that must run with `ApartmentState.STA` for certain COM or UI interop (Chapter 6). For short-lived, bursty work, creating a full OS thread per unit of work is wasteful — which is exactly the problem the thread pool solves.

### The thread pool: reusing threads instead of creating them

The **CLR thread pool** keeps a set of worker threads alive and hands them queued work items instead of spinning up a new OS thread each time. `ThreadPool.QueueUserWorkItem`, `Task.Run`, and most of the async infrastructure in .NET all ultimately queue work here. The pool grows and shrinks its thread count based on load (with a slow, deliberate ramp-up algorithm — a burst of work doesn't get a burst of new threads instantly, which is a common source of "why is my throughput low for the first second" confusion).

### `async`/`await` doesn't create threads

This is the point that trips up developers moving from thread-per-request thinking: `async`/`await` is about **not blocking a thread while waiting**, not about running work on another thread. An `await`ed `Task` for a genuinely async I/O operation (a file read via `FileStream` opened with `useAsync: true`, an HTTP call) completes via an I/O completion port — the calling thread is released back to the pool while the operation is in flight, and a pool thread (not necessarily the same one) picks the method back up when the I/O completes. No thread was ever blocked waiting; none was dedicated to the wait either.

```csharp
// Genuinely async I/O: no thread is blocked while this awaits
byte[] data = await File.ReadAllBytesAsync(path);

// CPU-bound work: Task.Run explicitly hands it to a pool thread
int result = await Task.Run(() => ExpensiveComputation());
```

`Task.Run` is for the opposite case — CPU-bound work with no I/O to wait on, where you deliberately want it to run on a thread pool thread so it doesn't block the caller. Calling `Task.Run` around something that's already `await`-based I/O just burns a thread pool thread for no benefit.

### `SynchronizationContext`: why UI thread deadlocks happen

WinForms and WPF (Chapter 8) install a `SynchronizationContext` that captures "the UI thread" and marshals `async` continuations back onto it by default, so code after an `await` in a button-click handler runs back on the UI thread automatically, safe to touch controls. This is also the classic deadlock source: calling `.Result` or `.Wait()` synchronously on a `Task` from the UI thread blocks that thread while the continuation is waiting to run *on that same now-blocked thread* — a self-deadlock. `ConfigureAwait(false)` (common in library code, not view code) opts out of that capture, letting the continuation run on whatever pool thread is available instead.
