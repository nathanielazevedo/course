A process is the unit of isolation Windows gives you: its own virtual address space, its own handle table, its own security token. `System.Diagnostics.Process` is the managed door into that world — but the shape of what it exposes only makes sense once you know the Win32 lifecycle it's standing in front of.

### What a process actually is, under the object model

Recall from Chapter 1 that the kernel's Object Manager tracks everything through typed objects and handles. A process is one such object: a **kernel process object** holding a virtual address space, a handle table (every file, mutex, and other kernel object *this* process currently has open), and a primary access token that says who it's running as. A process on its own does nothing — it exists only as a container. Actual execution belongs to its threads (covered later in this chapter), of which every process has at least one.

The step most developers miss is **Reap**. When a process exits, its kernel object doesn't vanish immediately — it stays alive, holding its exit code, as long as anyone still has an open handle to it. This is exactly why `Process.WaitForExit()` and `Process.ExitCode` work at all: the .NET `Process` object holds a handle from the moment it starts the child, and that handle stays valid to query after the child has already exited, until you (or the GC, via the finalizer) let it go.

### `System.Diagnostics.Process`: a handle with a friendly face

```csharp
using var process = new Process
{
    StartInfo = new ProcessStartInfo("ipconfig")
    {
        RedirectStandardOutput = true,
        UseShellExecute = false,
    },
};
process.Start();
string output = process.StandardOutput.ReadToEnd();
process.WaitForExit();
Console.WriteLine($"Exit code: {process.ExitCode}");
```

Every property here maps onto something the kernel actually tracks: `Id` is the process ID assigned at creation, `ExitCode` is the value the process object holds until it's reaped, `HasExited` is a live check against the kernel object's signaled state (a process handle becomes *signaled* — usable with wait functions — the instant the process terminates). `process.Handle` (or the `SafeProcessHandle` in newer APIs) is the actual `HANDLE` from `CreateProcessW`, wrapped so the CLR closes it when the `Process` object is disposed.

### Parent-child relationships are looser than you'd expect

Unlike some Unix shells, a Windows child process is **not** automatically killed when its parent process exits, and there's no `wait()`-style requirement that a parent must reap its child before the child's resources are released — a process's threads keep running, and its kernel object is cleaned up independently of whatever handle relationships existed at creation time. `Process.Start` records a parent-child relationship for informational purposes (visible in Task Manager's tree view), but it isn't an enforced lifetime relationship the way it can feel like it should be. Building actual "kill my children when I die" behavior requires Job Objects, which the fourth section of this chapter covers.
