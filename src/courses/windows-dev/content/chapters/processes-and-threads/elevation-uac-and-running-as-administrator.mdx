Section 1 of this chapter mentioned that a process's access token decides who it's running as. This section is about the specific, very visible case of that: **User Account Control**, and why "just running as Administrator" is more nuanced than it sounds once you're writing code that has to deal with it.

### Split tokens: even admins mostly don't run elevated

When an administrator account logs in, Windows creates **two** access tokens: a full administrative token, and a **filtered** token with admin privileges stripped out. Ordinary processes — Explorer, your browser, most things you launch by double-clicking — run with the filtered token by default, even when you're logged in as an administrator. This is the actual mechanism behind UAC: being "an administrator" doesn't mean your processes run elevated, it means you're *eligible* to elevate, on request, one process at a time.

### Requesting elevation from a C# app

There are two ways to end up with the full token: request elevation when *starting* a new process, or declare in advance that your app always needs it.

```csharp
// Request elevation for a single launched process
var psi = new ProcessStartInfo("cmd.exe")
{
    UseShellExecute = true, // required for the "runas" verb to work
    Verb = "runas",
};
Process.Start(psi); // triggers the UAC consent prompt
```

For an app that should *always* run elevated, the standard approach is an **application manifest** declaring `requestedExecutionLevel`:

```xml
<requestedExecutionLevel level="requireAdministrator" uiAccess="false" />
```

With this in the manifest, Windows shows the UAC prompt (and marks the icon with the shield overlay) the moment the executable is launched at all — there's no code path where it runs non-elevated. `asInvoker` (the default) inherits whatever the launching process's level already was; `highestAvailable` requests the highest level the current user could get without necessarily always demanding it.

### Elevation is a process-wide, all-or-nothing decision

There is no partial elevation and no elevating an already-running process. Once a process starts with the filtered token, it runs with that token for its entire life — code inside it cannot "become admin" partway through by calling some API. If your running non-elevated app hits a point where it needs admin rights (writing to a protected registry key, controlling a service), the only option is to launch a *new* elevated process (often itself, re-invoked with `Verb = "runas"`) to do that specific piece of work, and communicate the result back via some IPC mechanism (Chapter 10) — not to elevate in place.

### The false comfort of "just run the terminal as admin"

This explains a pattern from Chapter 1's setup checklist: if you launch Visual Studio or a terminal elevated, *everything* you run from inside it inherits that elevated token, because a child process's token comes from its parent's — this is a genuinely inherited attribute, unlike the parent-child *lifetime* relationship from earlier sections, which is not enforced. That's convenient for local development and exactly why elevation-dependent code can "work on my machine" and then fail the moment a teammate — or an end user — runs the same binary from an ordinary, non-elevated shell.
