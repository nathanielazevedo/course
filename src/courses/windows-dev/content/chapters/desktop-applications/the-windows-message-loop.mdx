Chapter 1 mentioned that Windows was built GUI-first, with the message loop as a core kernel-adjacent concept rather than something bolted on. This chapter is about building actual UI in C#, and it starts here — with the mechanism every framework in this chapter (WinForms, WPF, WinUI 3) ultimately sits on top of, whether or not the framework ever lets you see it directly.

### A window doesn't run code; it waits for messages

A Win32 window is, fundamentally, event-driven in a very literal sense: it has no code that "runs" on its own. It registers a **window procedure** (`WndProc`) — a callback function — and then sits idle until Windows delivers it a **message**: `WM_PAINT` (repaint yourself), `WM_LBUTTONDOWN` (the left mouse button was pressed inside you), `WM_SIZE` (you were resized), `WM_CLOSE` (the user asked to close you), and hundreds more. Every visible UI change and every input event a Windows application ever responds to arrives through this same channel, dispatched to whichever window's `WndProc` it targets.

### The message loop is single-threaded, on purpose

The loop that pulls messages off the queue and dispatches them (`GetMessage`, `TranslateMessage`, `DispatchMessage`, in raw Win32 terms) runs on one specific thread — the **UI thread** — and every window created on that thread is serviced by that same loop. This is a deliberate design, not an accident of history: it means a `WndProc` never has to worry about another `WndProc` call happening concurrently on the same window, which would otherwise make basic UI state management a genuine multithreading problem. The cost of that guarantee is the one every WinForms and WPF developer eventually learns the hard way: if code running inside a message handler blocks (a long computation, a synchronous network call, `Thread.Sleep`), the entire loop stops pulling new messages — no repainting, no responding to clicks, the window appears frozen — because there is only the one thread servicing it.

### Where WinForms and WPF hide this from you

Neither framework makes you write a `WndProc` or a message loop by hand — `Application.Run()` in WinForms and `Application.Run()`/the WPF dispatcher loop both wrap the same underlying `GetMessage`/`DispatchMessage` cycle, and both translate raw `WM_*` messages into the `.Click`, `.MouseDown`, `.Resize` events and commands you actually write code against. But the underlying model — one thread, one queue, one loop, don't block it — is exactly why Chapter 2's `SynchronizationContext` discussion mattered: async continuations captured back onto "the UI thread" are being marshaled back onto this exact loop, and a synchronous `.Wait()` or `.Result` call on that thread blocks the very loop that would otherwise be needed to complete the awaited work — the deadlock Chapter 2 described, now traceable to a specific, concrete mechanism.

### Cross-thread UI access is refused, not just discouraged

Because a `WndProc` and its window's state are only ever meant to be touched by the thread running that window's message loop, both WinForms and WPF actively detect and throw (`InvalidOperationException` / `System.InvalidOperationException: Cross-thread operation not valid`) when a different thread tries to touch a control directly, rather than silently allowing a race condition. `Control.Invoke`/`BeginInvoke` (WinForms) and `Dispatcher.Invoke`/`BeginInvoke` (WPF) both exist for exactly this: marshaling a delegate onto the UI thread's message queue so it runs safely as part of that thread's own loop, instead of touching the control directly from a background thread.
