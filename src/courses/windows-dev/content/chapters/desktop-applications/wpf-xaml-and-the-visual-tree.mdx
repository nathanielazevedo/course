The previous section described WinForms as close to native Win32 controls, with the customization limits that closeness implies. WPF makes the opposite tradeoff on purpose: it steps away from native controls almost entirely, in exchange for a rendering and layout model powerful enough to build UI that looks like genuinely anything.

### One real window, everything else drawn by WPF itself

A WPF window is, underneath, still one native `HWND` — the message loop from two sections ago still applies at that outer boundary. But everything *inside* that window — every button, every piece of text, every shape — is not a separate native control at all; it's a **visual**, part of a retained-mode scene graph WPF itself owns and renders directly through DirectX, with no corresponding Win32 window object for each individual control. This is the structural reason WPF can restyle a button into literally any shape or appearance with no owner-drawing required (the previous section's WinForms limitation): there's no native Win32 button to be constrained by in the first place, just a rectangle WPF is drawing and compositing however a style or template says to.

### XAML: a declarative description of that same visual tree

```xml
<Window x:Class="MyApp.MainWindow" ... Title="My App" Height="300" Width="400">
    <StackPanel Margin="16">
        <TextBlock Text="{Binding Greeting}" FontSize="18" />
        <Button Content="Click me" Click="Button_Click" Margin="0,12,0,0" />
    </StackPanel>
</Window>
```

XAML is not a separate technology bolted onto WPF — it's a direct, declarative representation of the same object tree you could construct by hand in C#; `<Button Content="Click me" />` and `new Button { Content = "Click me" }` produce the identical object. XAML's advantage is that it makes that tree's *structure* visually apparent in a way deeply nested constructor calls in C# don't, and it's what Visual Studio's XAML designer and hot-reload tooling are built around. Unlike WinForms' generated `.Designer.cs`, XAML is meant to be hand-edited directly as often as it's edited visually.

### Data binding: the visual tree reacting to your data, not the reverse

`{Binding Greeting}` above is WPF's data binding system — a declared link between a UI property (`TextBlock.Text`) and a data source property (`Greeting`, on whatever object is set as the element's `DataContext`), kept synchronized automatically as long as the source implements `INotifyPropertyChanged`:

```csharp
public class MainViewModel : INotifyPropertyChanged
{
    private string _greeting = "Hello";
    public string Greeting
    {
        get => _greeting;
        set { _greeting = value; PropertyChanged?.Invoke(this, new(nameof(Greeting))); }
    }
    public event PropertyChangedEventHandler? PropertyChanged;
}
```

This is the mechanism behind the MVVM (Model-View-ViewModel) pattern WPF applications commonly use: the view (XAML) binds to a view model's properties and commands, and the view model changes those properties without ever directly touching a UI element — `PropertyChanged` does the notification, and WPF's binding infrastructure does the actual UI update, dispatched onto the message loop from two sections ago the same way any other UI mutation is.

### Styles, templates, and why "restyle anything" is a real claim

A **Style** sets property values (colors, fonts, margins) applied consistently across every control of a given type; a **ControlTemplate** goes further and replaces the entire visual structure a control renders with — a `Button`'s default template is itself just XAML describing a border, a content presenter, and some triggers for hover/pressed states, and nothing stops replacing that template with an entirely different visual tree while keeping the `Button`'s click behavior and keyboard handling intact underneath. This separation of a control's *behavior* (still genuine .NET code implementing focus, keyboard activation, command execution) from its *appearance* (pure XAML, freely replaceable) is the concrete mechanism behind WPF's visual flexibility, and has no direct equivalent in WinForms' native-control model.
