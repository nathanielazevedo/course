The previous section covered talking to another machine over the network. This one is about the narrower, extremely common problem of two processes on the *same* machine talking to each other — a service and a tray app (Chapter 5's Session 0 isolation problem, finally getting its solution), two components of the same application, or a privileged helper process and its unprivileged caller.

### Why not just use a loopback socket for everything local?

A TCP socket bound to `127.0.0.1` works for local IPC and is genuinely the simplest option when you already have networking code to reuse — but it carries costs specific to being "network" traffic even when it never leaves the machine: it goes through the full network stack (Winsock, from the previous section) rather than the lighter path a same-machine IPC primitive can take, it needs port coordination (something has to agree in advance which port to use, and handle the case another process is already using it), and by default it's addressable by anything else that can reach `127.0.0.1`, which is a broader exposure than same-machine IPC strictly needs. Windows provides two primitives built specifically for the local case, each with a different shape.

### Named pipes: a byte stream with a name and real ACLs

A **named pipe** is a byte-stream connection, conceptually similar to a TCP socket, but addressed by name (`\\.\pipe\MyAppPipe`) rather than a host and port, and — critically — a real securable kernel object (Chapter 7's security model applies directly) with its own ACL controlling exactly which users or processes can even open a handle to it at all:

```csharp
// Server
using var server = new NamedPipeServerStream("MyAppPipe", PipeDirection.InOut);
await server.WaitForConnectionAsync();
using var writer = new StreamWriter(server) { AutoFlush = true };
await writer.WriteLineAsync("Hello from the service");

// Client (a separate process)
using var client = new NamedPipeClientStream(".", "MyAppPipe", PipeDirection.InOut);
await client.ConnectAsync();
using var reader = new StreamReader(client);
string? line = await reader.ReadLineAsync();
```

This is the direct, practical answer to Chapter 5's "a service has to talk to a logged-on user's UI app" problem: a service creates a named pipe server, a companion tray app (running in the user's own session, capable of showing UI) connects as a client, and the two exchange data across the session boundary neither could cross any other way, with the pipe's ACL controlling exactly who's allowed to connect — restricting it to the local machine's `Authenticated Users`, for instance, rather than leaving it open the way an unrestricted loopback socket would be by default.

### Named pipes also support impersonation directly

`NamedPipeServerStream.RunAsClient` lets a pipe server impersonate the connecting client for the duration of a callback, using exactly the impersonation mechanism Chapter 7 covered — this is, in fact, the most common real-world way that impersonation pattern actually gets triggered, tying this section directly back to that one: a service receiving a request over a named pipe, impersonating the caller, and performing a file or registry operation with the caller's own permissions rather than the service account's.

### `Mutex`, `Semaphore`, and shared memory: coordination without a data stream

Not every IPC need is "send bytes" — sometimes it's purely coordination. A **named `Mutex`** (`new Mutex(false, "Global\\MyAppSingleInstance")`) is the standard mechanism for enforcing a single running instance of an application: the second launch attempts to acquire the same named mutex, fails immediately because the first instance already holds it, and can detect that failure to signal the already-running instance instead of starting a second one. **Memory-mapped files** (`MemoryMappedFile.CreateOrOpen`) provide actual shared memory between processes — a region both can read and write directly, useful for high-throughput data sharing where marshaling everything through a pipe's stream-oriented read/write calls would add unnecessary overhead. `Global\` versus no prefix on a named object matters here too: an unprefixed name is scoped to the current session, while `Global\` makes it visible across every session on the machine — relevant again specifically because of Session 0 isolation, if a service and a user-session process both need to see the same named object.
