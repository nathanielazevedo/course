The first section of this chapter introduced the Windows Firewall as a silent failure mode for inbound connections; this section is about actually inspecting and managing that configuration, and the broader network configuration surface C# code sometimes legitimately needs to read or adjust.

### Querying firewall state with `NetFwTypeLib` (COM interop, in practice)

Programmatic firewall management on Windows is COM-based (`HNetCfg.FwPolicy2`), not a native BCL API — a direct, practical use of Chapter 6's COM interop coverage:

```csharp
using System.Runtime.InteropServices;

Type? fwPolicyType = Type.GetTypeFromProgID("HNetCfg.FwPolicy2");
dynamic fwPolicy = Activator.CreateInstance(fwPolicyType!)!;
bool firewallEnabled = fwPolicy.FirewallEnabled[NET_FW_PROFILE_TYPE2_.NET_FW_PROFILE2_DOMAIN];

foreach (dynamic rule in fwPolicy.Rules)
{
    if (rule.Name == "MyApp")
        Console.WriteLine($"Enabled: {rule.Enabled}, Direction: {rule.Direction}");
}
```

This is genuinely COM interop with an RCW involved (Chapter 6's exact model), which is why `Marshal.ReleaseComObject` discipline applies here too for anything longer-lived than a quick script. In practice, most application code that needs to *create* a firewall rule shells out to `netsh advfirewall` or uses the `NetFirewallRule` PowerShell cmdlets (as shown in the first section) from an installer, rather than driving the COM API directly — the COM interface is more commonly useful for *querying* current state diagnostically than for ongoing rule management.

### Enumerating network interfaces and adapters

For reading network configuration rather than firewall rules specifically, `System.Net.NetworkInformation` is a first-party, cross-platform BCL API, no COM or P/Invoke needed:

```csharp
using System.Net.NetworkInformation;

foreach (NetworkInterface nic in NetworkInterface.GetAllNetworkInterfaces())
{
    if (nic.OperationalStatus != OperationalStatus.Up) continue;
    Console.WriteLine($"{nic.Name}: {nic.Description}");
    foreach (var addr in nic.GetIPProperties().UnicastAddresses)
        Console.WriteLine($"  {addr.Address}");
}
```

`NetworkChange.NetworkAvailabilityChanged` and `NetworkChange.NetworkAddressChanged` are the corresponding event-based way to react to connectivity changes live (a laptop moving from Wi-Fi to Ethernet, a VPN connecting) rather than polling `GetAllNetworkInterfaces()` repeatedly — genuinely useful for an app that needs to behave differently depending on current network reachability, a background sync service pausing while offline, for instance.

### Proxy configuration: Windows has its own, separate from your code's

Windows maintains system-wide (or per-user) proxy settings, configurable through `netsh winhttp` (for WinHTTP-based traffic, which includes most system-level and many application HTTP calls) separately from the browser-facing proxy settings in Settings → Network. `HttpClient` respects the system proxy configuration by default through `HttpClientHandler.UseProxy` (true by default) unless explicitly overridden, which is why HTTP code that works fine on a home network can behave completely differently inside a corporate network with an enforced proxy — not because the code is wrong, but because it's transparently routing through infrastructure that wasn't present during local development. `netsh winhttp show proxy` from a terminal is the fastest way to check what the *system* believes the proxy configuration actually is, independent of what any specific application's own settings claim.

### Ports: what "port already in use" actually means, and how to check

`SocketException` with `WSAEADDRINUSE` (or the more readable `.NET` message "Only one usage of each socket address...") when binding a listener means another process already holds that port — `netstat -ano | findstr :5000` (or the more modern `Get-NetTCPConnection -LocalPort 5000`) shows exactly which process ID owns it, which `Process.GetProcessById` (Chapter 2) can then resolve to a name. This is a common source of confusion specifically with .NET's development server tooling, where a previous `dotnet run` that wasn't cleanly terminated can leave a port bound well after the terminal that started it appears to have closed.
