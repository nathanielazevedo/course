The previous section's named pipes and mutexes are low-level primitives — a byte stream, a lock. **Windows Communication Foundation (WCF)** was Microsoft's answer to a higher-level problem: defining a service contract once and being able to expose or consume it over several different underlying transports — including, notably, named pipes themselves — without rewriting the service logic for each one. It's still genuinely relevant to understand, both because plenty of existing Windows codebases run on it, and because knowing what it did well explains what its modern replacements deliberately kept or changed.

### One contract, multiple bindings

WCF's core idea was separating a service's **contract** (the operations it exposes, defined as a C# interface with `[ServiceContract]`/`[OperationContract]` attributes) from its **binding** (the transport and protocol actually used to reach it — HTTP/SOAP, TCP, or named pipes) and its **address** (where to find it). The same contract could be exposed over `NetNamedPipeBinding` for fast local IPC and `BasicHttpBinding` for interoperating with non-.NET clients over the network, simultaneously, from one service implementation — a genuinely powerful abstraction for its time, and part of why WCF became the default choice for enterprise Windows service-to-service communication for years.

```csharp
[ServiceContract]
public interface IOrderService
{
    [OperationContract]
    Order GetOrder(int id);
}

// One implementation, multiple possible bindings/endpoints configured separately
```

### Why WCF specifically (not just "old code") is now legacy

Classic WCF is built on **.NET Framework** and was never ported to modern .NET in its original, full form — this is a genuinely different situation from most .NET Framework APIs, which either made the jump to modern .NET directly or have a close equivalent. `CoreWCF`, a community/Microsoft-supported open-source project, provides server-side WCF-contract compatibility on modern .NET for migration scenarios, but it's explicitly a migration bridge, not a recommendation for new development — new service code on modern .NET is expected to be built on the alternatives below rather than on WCF's contract-and-binding model at all.

### gRPC: WCF's most direct conceptual successor

**gRPC** (covered in depth in the next section) is the closest thing to "what WCF was trying to do, rebuilt for modern .NET and cross-platform interoperability": a contract defined once (in `.proto` files rather than C# interfaces), strongly-typed client and server code generated from that contract, and a binary, efficient wire protocol (Protocol Buffers over HTTP/2) in place of WCF's XML/SOAP-heavy default. Where WCF's binding model let one contract span wildly different transports including in-process-adjacent named pipes, gRPC is more narrowly, deliberately focused on network RPC done well — which is a reasonable trade given how much of WCF's binding flexibility went unused in practice.

### ASP.NET Core Web API: the plain-HTTP alternative

For services that don't need RPC-style strong contracts at all, a plain ASP.NET Core Web API (JSON over HTTP, `[ApiController]`, minimal APIs) is the more common modern default — simpler to consume from any HTTP client on any platform, better tooling and ecosystem support today than WCF's SOAP-based interoperability story ever achieved, at the cost of the compile-time contract enforcement gRPC or WCF provide.

### Named pipes directly, without a framework on top

For the specific case WCF's `NetNamedPipeBinding` targeted — fast, local-machine IPC with a service-like request/response shape — modern code often skips a framework layer entirely and uses `System.IO.Pipes` directly, as the previous section covered, sometimes with a lightweight message-framing convention (length-prefixed JSON or similar) layered on top by hand. This is a reasonable choice specifically when the communication is genuinely local-only and doesn't need cross-machine reach at all — reaching for gRPC's or Web API's networking machinery for two processes that will always be on the same box is often more infrastructure than the problem actually needs.
